## 0. 结论先看

**总体判断：文档质量高，可以作为开发依据，但建议先把下面 4 个「高」问题定下来再开工。**

- 文档的主要结论我抽查了 22 处源码和数据库事实，**全部属实**（见第 5 节）。设计与需求、demo 的大方向一致，没有发现「设计把需求做反了」的硬伤。
- 发现的问题按严重程度分三档：

| 档次 | 数量 | 意思 |
|---|---|---|
| 高（H） | 4 | 定错了会返工，或者上线就出功能性错误 |
| 中（M） | 15 | 会影响细节正确性、工作量估计或验收口径（M1-M4 是冲突矛盾类，M5-M15 是遗漏类） |
| 低（L） | 10 | 文档可读性、知会类 |

- **4 个高问题一句话**：
  - H1 文件哈希大小写：客户端实际上报的是**大写**，设计里名单和库文件统一用**小写**，终端比对可能全部不命中。
  - H2 「学习数据」到底是「全盘可执行文件」还是「被执行过的文件」没说清，101 数据更像后者，这决定数据量和名单规模。
  - H3 升级脚本风险：`rpw.sql` 每张表前都是 `DROP TABLE IF EXISTS`，原样放进升级包会清空客户已有的审计日志和名单；而且缺少给 `POLICY` 表加 `POLICYTYPE`、`STATUS` 两列的语句。
  - H4 学习数据上报方式：101 数据表明客户端现在是「追加上报、靠唯一键挡重复」，不是设计推荐的 `dwith=2`「有就更新」。后果是每次重复上报都在 Java 里报一次错，而且「上报时间」永远停在第一次。

## 2. 全面吗？有没有遗漏？

### 2.1 高（定错返工 / 功能错误）

**H1 文件哈希的大小写，设计和客户端实际不一致**（已答复：统一小写，见 0.1）

- 事实：101 上 `RPW_EXECFILEINFO` 已有 15 行客户端真实上报（2026-10-14 17:10 到 18:05，终端 `836D585B…`），`FILEHASH` 全部是**大写**，例如 `A019E20B3C3AA08FED5E7B2B550B3969`，`ALGO=0`。
- 设计：5.4 规则键用「小写 `FILEHASH`」；7.3 手动添加「统一转小写」；7.7 库文件 `items[].hash` 是「小写十六进制」。
- 后果：
  1. 库文件下发到终端后，如果终端按字符串精确比较，全部不命中：白名单模式下所有进程都「不在白名单」（拦截模式会拦整台机器），黑名单模式下一个都拦不住。
  2. 进程管理页「白名单个数 / 黑名单个数」、8.4「校验规则存在于采集表」如果在 PHP 层比较会对不上。SQL 层目前因为列是 `utf8_general_ci`（不分大小写）暂时不出错，但 5.8 第 2 条如果把 `FILEHASH` 也顺手改成 `utf8_bin`，就会出错。
- 建议：定一个全链路口径。推荐「中心入库、入名单、写库文件时统一规范成一种大小写；并在 P2 要求终端比较哈希时不区分大小写」。把这条加进 P2 和 P8，并在 5.4、7.3、7.7 注明「客户端目前上报大写」。

**H2 「学习数据」的含义没定清：是全盘可执行文件，还是被执行过的文件**（已答复：是运行的进程 + 安装包，名词按需求叫「进程原始数据」「进程记录」，见 0.1）

- 需求叫「进程」「进程记录」；`rpw.sql` 注释叫「系统可执行文件采集表 进程名？？？」（原作者自己打了问号）；设计 1.2 写「终端只采集本机的可执行文件和安装包」，像是全盘扫描。
- 101 的 15 行数据：1 小时内零散上报，全是 SOC 自身的程序和脚本（`java`、`php-fpm`、`nginx`、`setup.sh`、`monitor.sh`、`elasticsearch-cli` 等），`TIME` 各不相同，更像「文件被执行时逐条上报」，不是全盘扫描（全盘扫描会在同一秒上报成百上千条）。
- 为什么重要：全盘扫描一台机器可能上万条、按执行上报只有几十到几百条。它决定进程管理页的数据量、5.8 第 7 条的索引是否够用、「按条件加白」一次加多少、以及白名单的实际大小（影响 zip 体积和终端比对性能）。另外脚本文件（`.sh`）也在里面，名单要不要管脚本，产品上要有说法。
- 建议：作为 P8 的子项明确三件事：采集触发方式（执行时 / 定时扫描 / 两者）、是否包含脚本、`EXECACTION` 的含义（101 全是 NULL，`EXECTYPE` 全是 0）。文档 1.2、5.5 按答复改写。

**H3 `rpw.sql` 直接用于升级会清空客户数据；且缺 `POLICY` 表的改列语句**（已答复：只标记、暂不改脚本，见 0.1）

- `rpw.sql` 每张表前都是 `DROP TABLE IF EXISTS`。101 上 6 张 RPW 表已经存在（我查了）。如果升级包原样执行这份脚本，客户已有的审计日志、学习数据、名单进程全部清空。5.8 的 13 条修改建议和 14.3「新装和升级脚本都要包含」都没有提这一点。
- `rpw.sql` 里「POLICY 表添加字段 policytype / status」只是一段注释，没有 `ALTER TABLE` 语句。101 上两列已存在（`tinyint(1)`，可空，默认 NULL），但加列的来源不明（脚本里没有，推测是手工加的）；新装和升级环境执行脚本后 `POLICY` 没有这两列，名单功能直接报错。
- 建议：5.8 补两条：① 升级脚本改用 `CREATE TABLE IF NOT EXISTS` + `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`（MySQL 5.x 不支持 `ADD COLUMN IF NOT EXISTS`，要用存储过程或先查 `information_schema`），绝不带 `DROP`；② 补 `ALTER TABLE POLICY ADD COLUMN POLICYTYPE TINYINT(1) NULL, ADD COLUMN STATUS TINYINT(1) NULL`。

**H4 学习数据上报方式：客户端现状和设计推荐不符**

- 事实：101 上 15 行的自增 `ID` 是 1、5、16、21、27、28、29、30、33、35、36、37、39、40、59，大量跳号。表上有唯一键 `(SGUID, FILEHASH, ALGO, PROCPATH)`；Java 目前的 `dwithWhereMap` 没有 RPW 表（我查了 `MsgService.java:61-66`，只有 4 项）。跳号说明：客户端在**重复追加上报**，重复行因唯一键冲突插入失败、消耗了自增号。也就是客户端现在用的是 `dwith=0`（追加），不是设计 10.2 推荐的 `dwith=2`（有就更新）。
- Java 的处理（`MsgService.java:437-440`）是逐条 `try/catch` 记错误日志、继续下一条，所以不会丢同批其他记录，但：① 每次重复上报都在 Java 错误日志里刷一条；② 冲突的行不会更新，`TIME`（demo 的「上报时间」）永远停在第一次，5.5 的 `MAX(f.TIME)` 就不准。
- 如果客户端改成 `dwith=2` 而 Java 没加映射，后果更严重：默认按 `eid, sguid, uniquevalue` 找旧行，`uniquevalue` 列不存在被跳过，条件只剩「企业 + 终端」，**这台终端的所有学习记录会被改成同一条**（设计 10.2 已经指出这一点，正确）。
- 建议：P8 里把「客户端当前用的是 `dwith=0`」写成已核实的事实，让客户端二选一：改 `dwith=2`（Java 必须同步加映射，两边要一起上线）或保持 `dwith=0`（Java 改用 `INSERT ... ON DUPLICATE KEY UPDATE`，否则错误日志会被刷爆）。两边上线顺序要写进 14 节。

## 4. 其他问题

1. **文档定位**：这份文档同时是「调研报告 + 设计 + 决策记录 + 问题清单」，1100 多行。开发真正要看的是 5、6、7、8、9、14 节，其他是背景。建议拆成两份：设计文档（给开发）和决策与调研记录（附录），或者至少在 0 节加一张「不同角色看哪几节」的导读表。
2. **数据量预估缺失**：没有「一台终端多少条学习数据、一个名单多少条规则、审计日志每天多少条」的估计，索引设计（5.8 第 7 条）和「按条件加白不设上限」（C8）都是在没有量级的情况下定的。H2 定了之后补一段估算。
3. **上线顺序**：中心、Java、客户端三方改动谁先谁后没写（H4 已指出 Java 和客户端必须一起换；P9 的名单报文从 2/3 改成共用 "2" 也有同样问题：中心先上、客户端还按 2/3 解析会把黑名单当白名单）。14 节补「上线顺序和兼容窗口」。
4. **安全**：
   - 名单接口参数化和范围校验（4.3）写得到位。
   - 库文件目录不能列目录已核实（L9）。
   - 建议补一条：`dpath` 相对路径只能由中心生成、不接受前端传入（7.8 对 `<gwl>` 已这样写，`<lib>` 没明说）。
5. **性能**：5.5 的聚合 SQL 对 `RPW_EXECFILEINFO` 做三列 `GROUP BY`，再按规则键去两张名单表数个数。数据量上来后（H2）这是全表扫描；建议进程管理页的「白名单个数 / 黑名单个数」改成先聚合、再对当前页 10 条做子查询，不要对全表做。
