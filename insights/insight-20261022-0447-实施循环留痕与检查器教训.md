# 计划实施循环里留痕与检查器的教训

**场景**:PL-01 用 `implement-plan` 跑了约 24 小时、7 个子任务、十几轮内审和一轮整体审。内审发现的问题大半落在主 Agent 自己写的留痕上,代码层多轮 0 问题。证据见 `changelog/log-20261021-0530-实施PL-01.md`(TK-3 内审第 1～4 轮、TK-4 内审第 1 轮、TK-5 内审第 2 轮、整改内审)。

**现象 / 坑**:

1. 状态页同一主题散在「阶段表 / 当前进行中 / 下一步 / 仓库现场」多处,只改一处的毛病复发了五六次;上传后忘了换「当前进行中」里写的文件指纹,接手的人会拿旧值当上传比对基线。
2. 为此写的检查器只在「写状态页」时才跑,一次没写状态页,检查器就形同虚设。
3. 裁决里定的连带要求(如「error 回调不再弹第二次」)只写在裁决正文,后续 TK 和审查拿不到;按「当时想到的 TK」列举又漏了同样会写这类回调的 TK。
4. 裁决引「照现有页面」时只看了回调里有没有 `hide`,没看按钮上的 `data-dismiss` 和后续弹窗,依据被内审推翻。
5. 唯一一份基线和证据放在 `/private/tmp`,本机重启后全丢,只能重采。
6. 全量验收时,早期 TK 的自测壳因后续 TK 新增依赖而跑不起来;另一个壳要用它自带的服务启动,换成纯静态服务就误报。

**结论**:

- 状态页的每个「当前事实」(含文件指纹)都要有机械检查,检查要挂进每次都跑的留痕检查器(本 loop 用 `check_trail.py` 的 STAGE 断言调用 `check_status_sync.py`)。
- 连带要求一律写进条款覆盖表,受影响的 TK 按「谁调这个接口 / 写这个回调」grep 出来,不凭记忆。
- 用现有页面做裁决依据,要走完整交互链:按钮属性、框架委托、后续弹窗。
- 工作目录、基线、证据开工就放持久目录(本项目用仓库外的 `soc-process-ctrl-work/`)。
- 自测壳随依赖它的文件一起更新,或在全量验收里写明由浏览器用例接替;运行时用它自带的启动方式。

**PL-02 补充（2026-10-22）**:恢复点过时又出现两次（内审第 1 轮 I2、第 2 轮 S1）。第一次补的断言只核状态页里「下一步」那一句，挡不住其他事实过时；改成 `tools/status_fresh.py`：changelog 最新一个 Task / 整体审段的时间不得晚于 `CurrentStatus.md` 的修改时间，写完 Task 段不改状态页就红。证据见 `changelog/log-20261022-0535-实施PL-02.md`「检查器生长（TK-1 内审第 2 轮 S1）」。

**检查清单**:

1. 每次上传后:状态页「当前进行中」「仓库现场」里的指纹换了吗?
2. 新的连带要求写进覆盖表了吗?受影响 TK 是 grep 出来的吗?
3. 检查器是挂在「每次都跑」的位置吗?改坏后能红吗?
4. 证据目录会被重启清空吗?
5. 每写一个 Task / 整体审段,紧接着覆盖状态页恢复点了吗?(断言比修改时间,不比某一句话)
