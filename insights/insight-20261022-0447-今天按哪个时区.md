# 「今天」按哪个时区算:mock、页面、后端必须同一口径

**场景**:PL-01 名单页高级查询的「本周 / 本月 / 上月」和「指定日期」。101 后端 `SCommon::getDateRanges` 先设了 `date_default_timezone_set('Asia/Shanghai')`;开发和测试在美东。证据见 `changelog/log-20261021-0530-实施PL-01.md` 22:24、22:50、04:14、04:22 段。

**现象 / 坑**:

1. mock 最初按浏览器本机日期算「今天」,美东晚上(北京已是第二天)算出的本周 / 本月与真接口相反。
2. 改裁成北京日期后,只核了「哪些验收用到今天」,漏了页面日期选择器的上限仍按本机日期——同一页面两处「今天」对不上,整体审才发现。
3. 第一次修复只换了算法、仍在页面初始化时算一次,页面开着跨过北京零点会比 mock 落后一天。
4. 本机日期和北京日期相同的时段(如美东凌晨到中午),页面抽查分不出新旧写法,看起来都对。

**结论**:

- 凡要「今天」的地方都用同一算法:当前毫秒数 + 8 小时,再用 `getUTCFullYear / getUTCMonth / getUTCDate` 读(北京无夏令时);每次用时现算,不缓存。
- 改了这类横切口径后,用 grep 找全部 `new Date()` / `getDate()` 等取日期的代码逐个核,不能只按验收清单核。
- 时区类验收必须在「本机日期 ≠ 北京日期」的时刻注入固定时间(多时区 + 跨月 / 跨年 / 跨零点),并做「改回本机日期」「只算一次」的变异证明会红。

**检查清单**:

1. 这个「今天」和后端用的是同一时区吗?
2. 全文 grep `new Date(` 和 `getDate(`,每处都核过了吗?
3. 是在用的时候现算,还是初始化时算一次?
4. 自测有没有覆盖美东晚上、奥克兰凌晨、跨零点三种时刻?
