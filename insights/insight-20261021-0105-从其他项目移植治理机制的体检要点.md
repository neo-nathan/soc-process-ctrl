# 从其他项目移植治理机制(skill/脚本/CLAUDE.md 规则)的体检要点

**场景**:2026-10-21 把 soc-cascade-syslog 的 CurrentStatus / changelog / insights 三套机制
(4 个 skill、`gen-index.py`、`check_current_status.py`、CLAUDE.md 四节规则)移植到本项目。
详细记录见 `changelog/log-20261021-0107-建立CurrentStatus-changelog-insights三机制.md`。
源项目自己的移植体检清单在 `soc-cascade-syslog/insights/insight-20260903-0342-移植CLAUDE.md体检清单.md`,本条是在它基础上的补充。

**现象 / 坑**:

- 本项目 `.gitignore` 原来整行忽略 `.claude/`,skill 和脚本拷进去也进不了 git,换机器就没了。
- 源项目 skill 里写死了它自己的规范文档(DC-03 / DC-04 / DC-08)、门号体系和数据链路文档,
  照搬后第一步就读不存在的文件。
- 源项目的目录表有 `plans/`、`implement/`、`evidence/`、`docs/`,本项目没有;写进去 Agent 会以为流程被跳过或照着新建。
- 源项目的审查报告命名规则和本项目已有的 3 份报告(`RV-20261013-0833-PL-06-v0.x.md`)冲突。

**结论**:移植的是机制,不是旧项目的现场;每一处引用都要按本项目实况重写或删除。

**检查清单**(可直接照着过):

1. 先 `git check-ignore -v <要入库的路径>`,确认 skill / 脚本不会被 `.gitignore` 吞掉;本机配置(`launch.json`、`settings.local.json`)单独忽略。
2. 按源项目的专有名词 grep 扫 `.claude/` 全目录(含 assets、scripts),一个不留;从 soc-cascade-syslog 移植时用的是
   `grep -rn -E 'DC-|docs/|PL-|GD|GI-|DEF-|syslog|外审|jar|四库'`,换源项目要换词。
3. 被引用的规范文档不搬时,把其中要紧的规则直接写进 skill,不留指向不存在文件的链接。
4. 目录表只登记本项目真实存在的目录,以后用到再加。
5. 新规则和现存文件冲突时,新规则只管以后,现存文件在规则里注明「历史命名、不改名」。
6. 改完跑一遍生成器和检查脚本,并做反例(比如 description 超 150 字)确认检查真的会拦。
7. 照搬的脚本也要拿本项目的真实数据跑边界:本次两条 insight 同在 01:05 创建,暴露出源脚本按「日期-时分」
   前缀映射 memory 会串号,且它声称的「memory 反向断链」检查其实不存在;移植后都在本项目修了,源项目仍有。
8. 机械核对所有文件里提到的路径和「章节名」引用确实存在——本次规则里引用的 CLAUDE.md 章节名就和实际标题对不上过。
9. **移植流程类 skill(编排、审查循环)时,拿本项目第一份真实计划逐个子任务推演一遍,最好派一个不参与改写的 Reviewer 来推**。
   2026-10-21 移植 `implement-plan` 时,自检扫干净了所有旧名词,独立复审拿 PL-01 一推仍抓出 7 条 important,
   全是「源项目默认成立、本项目不成立」的前提:`svn diff` 会混入同事在 101 上没提交的改动、本地 svn 副本比 101 旧
   (查调用点查出假的「零调用点」)、「与改动前一致」的回归在上传后再也看不到改动前的样子、
   计划自带默认的待确认项被写成「确认前不许开工」。这类问题 grep 扫不出来,只有对着真实计划走才暴露。
   而且**整改本身也要再审**:同日第二轮复审的 blocker 整改(新增「通过快照」)在第三、四轮又各引出 4～5 条衍生问题,
   全在新机制和旧机制的接缝处(中途合并会冲掉工作副本、审查员拿不到快照路径、`git status` 不加 `-uall` 算不出目录 md5)。
   一轮复审改完就收,等于把接缝问题留给真实执行。
   记录见 `changelog/log-20261021-0430-移植implement-plan技能.md`。
