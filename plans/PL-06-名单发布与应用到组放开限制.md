## 一、背景与拍板

### 1.1 用户需求（2026-11-10）

用户原话：

> 1. 现在是名单「有变更」就不允许「应用到组」，只有「发布」后，才能「应用到组」。需要改一下规则：只要名单发布过，就可以「应用到组」，有变更的名单也可以「应用到组」。
> 2. 现在是「已发布」的名单不能发布，撤销这条限制，[已发布]的名单也可以发布。
>
> 咱们只改前端代码 php 由别人修改。第 2 条，领导要求放开，文案上只提示「发布成功。」即可，不要多说，说多错多。

### 1.2 改后的按钮规则（本计划的核心）

| 发布状态 | 发布（改前 → 改后） | 应用到组（改前 → 改后） | 编辑、进程、删除 |
|---|---|---|---|
| `---` | 灰 → **不变**（灰） | 灰 → **不变**（灰） | 不变 |
| 待发布 | 可 → **不变**（可） | 灰 → **不变**（灰；悬停改字，Q-3） | 不变 |
| 已发布 | 灰「没有变更，不需要发布」 → **可** | 可 → 不变（可） | 不变 |
| 有变更 | 发布后进程数 > 0 可、否则灰 → **不变** | 灰「有变更还没发布，先发布再改应用范围」 → **可**（发布后进程数会变 0 的也可，F-7） | 不变 |

一句话：**「应用到组」= 发布过（已发布、有变更）就能点；「发布」= 只要有进程、且发布后进程数 > 0 就能点**（`---` 和「有变更且发布后为 0」仍灰）。

发布成功提示：**固定「发布成功。」一句**，不分有没有应用到组、不分第几次发布（用户定；现在源码已经是这样，F-3）。发布确认框（「确定发布白名单「X」吗？」）不变。

## 六、风险

| # | 风险 | 应对 |
|---|---|---|
| R-1 | **后端第 2 条没改之前前端先放开**：点「已发布」的「发布」会被拒绝，弹「错误：名单没有改动，不需要发布。」 | 不提交 svn，等后端（Q-8）；101 上同事看到会知道前端已放开 |
| R-2 | 「有变更」时应用到组，新组拿到的是上次发布的版本，没发布的增减不在里面；按 Q-1 不加提示，用户可能以为增减也下发了 | 用户已知道并选了「不多说」；行说明「有变更」仍写着「之后…还没发布，终端上跑的还是旧版本」 |
| R-3 | **「已发布」再发布对终端的影响**（推断，要后端和终端同事确认）：内容不变但会重新打包、生成新版本号，组内终端全部再拉一遍；名单的「已下发」统计会先清零（`bwlistUsedGroup.js:25` 注释引后端口径）；包名固定 `{PGUID}_{架构}.zip`，重新打包会**原地覆盖**同名文件，zip 的 md5 大概率会变——而 PL-05 问题 A 正是「终端见同名 zip md5 不同就报错、不重下载」。问题 A 修好之前，重复发布可能让已经拿到名单的终端报错 | 写进 §八 ② 请后端 / 终端确认；不阻塞前端 |
| R-4 | 脏数据：`STATUS=3` 但从没发布过的名单（F-14：黑名单 PID 39 仍在），前端「应用到组」能点，提交时后端拒绝 code 4「该名单从未发布…」 | core.js 会弹后端原因，弹窗留着；不另处理。这条名单 0 个进程，发布本来就灰（发布后为 0） |
| R-5 | 101 是共享环境，同事会整体部署 `public/`（F-8 刚发生过），上传的文件可能被覆盖 | 上传后、实测前、收尾前各核一次指纹（insight「101 共享环境联调的坑」） |
| R-6 | 页面状态是列表加载时的；别人同时改了名单，按钮状态会过期 | 后端每个接口都会再校验，前端不处理（和现在一样） |
