# 行业 SOC/终端安全产品的进程管控模式调研（v0，2026-09-22）

> 调研问题：同类产品的进程管控怎么做？「采集模式 / 审计模式 / 拦截模式」行业内怎么定义、用来干什么、和进程黑白名单是什么关系？
> 调研对象（均以官方文档 / 官方手册为准，来源见文末）：微软 AppLocker 与 App Control for Business（原 WDAC）、Carbon Black App Control、Airlock Digital、ThreatLocker、ManageEngine、fapolicyd（红帽 Linux）、奇安信天擎、深信服 aES、360 终端安全、阿里云无影、阿里云云安全中心、火山引擎飞连、腾讯 iOA。
> 本文只讲行业做法，不讲 SOC 代码；SOC 现状见 01 文档。

---

## 0. 一句话结论

1. **行业没有统一叫「采集/审计/拦截」的三个词，但几乎所有产品都有这三层含义**：先只看（可见/学习），再只记（审计），最后才拦（强制）。这是一条上线节奏，不是三个互斥的产品功能。
2. **模式管的是「命中名单之后怎么办」，黑白名单管的是「凭什么算命中」**。两者是两个独立维度：名单是规则，模式是动作。同一份名单，切换模式只改动作，不改规则。
3. **采集不是一种「模式」，而是一直开着的底座能力**。所有产品在拦截模式下照样上报运行进程。行业里真正叫「模式」的只有两档：审计（记录不拦）和强制（拦）。所谓「采集模式」在行业里对应的是「学习期 / 可见性阶段」，是白名单上线前的一个准备阶段。
4. **白名单几乎强制要求「采集 → 审计 → 拦截」三步走**，黑名单可以直接上拦截，但成熟产品仍给「仅告警」选项。
5. **黑名单和白名单在成熟产品里是一条策略二选一**，不叠加；有的产品允许两者并存，但必须定义优先级（明确禁止 > 明确允许 > 默认规则）。

## 1. 三种模式：行业各家怎么叫、怎么定义

### 1.1 对照表

| 需求里的叫法 | 行业通用叫法 | 名单是否参与判定 | 命中后动作 | 产生什么数据 | 用途 |
|---|---|---|---|---|---|
| **采集模式** | Visibility（可见）/ Learning（学习）/ Discovery（发现）/ 进程学习 / 智能学习 / 运行进程清点 | **不参与**（或没有名单） | 什么都不做 | 全量进程清单（名字、路径、哈希、签名、父进程、启动参数） | 摸清家底，自动生成候选白名单 |
| **审计模式** | Audit / Audit only / Monitor / Permissive / 仅告警不阻断 / 观察模式 | **参与** | 只记录「本该拦」的事件，可选告警，**不拦** | 「如果切到拦截会拦谁」的清单 | 验证名单有没有误杀、有没有漏配，切拦截前的彩排 |
| **拦截模式** | Enforce / Enforcement / Strict / Control / Block / 阻断 | **参与** | 阻止启动（多数产品连已运行的一起结束），终端弹窗，记录事件 | 拦截记录 | 真正防护 |

中间档（部分产品有）：
- **提示模式**（Carbon Black Medium「Prompt Unapproved」）：未知程序弹窗让用户自己选允许/阻止，已禁止的仍直接拦。
- **拦截 + 申请**（ThreatLocker、ManageEngine「未列入名单应用可被请求」）：拦住后终端弹「申请放行」，管理员审批后自动加白。

### 1.2 各家原文定义（按厂商）

**微软 AppLocker**（Windows 内置）
- 每个规则集合有一个「执行模式」：`Enforce rules`（拦，写日志）/ `Audit only`（不拦，程序照常运行，但把「本该拦」写进日志）/ `Not configured`（等于强制，微软自己建议别用）。
- 官方定位：「Audit only 帮助你在强制之前先识别哪些应用会受影响」。
- 判定顺序固定：**显式 deny > 显式 allow > 隐式 deny**（不在允许列表里的一律拦）。每个规则集合本质上是**允许列表**。
- 事件分开编号：8003 = 审计模式下「本该拦」，8004 = 强制模式下「已拦」。

**微软 App Control for Business（原 WDAC）**
- 两种运行模式：`Audit mode`「允许不受信任代码运行，同时记录事件」；`Enforcement mode`「禁止不受信任代码运行，同时记录事件」。
- 微软明确建议：**先用 Enabled:Audit Mode 跑**，从事件日志（3076 = 本该拦）里把合法软件抓出来合并进策略，删掉 Audit Mode 选项后策略自动变成强制（3077 = 已拦）。
- 实际部署建议跑 1～2 周审计（社区经验 30～60 天）。

**Carbon Black App Control**（VMware/Broadcom，应用控制的老牌产品）
- 三种「模式」：`Disabled`（不执行、不上报）/ `Visibility`（**只上报、只跟踪文件，不执行任何规则**）/ `Control`（执行规则）。
- Control 之下再分三个「执行级别」：`High` 只放行已批准文件；`Medium` 未批准的弹窗让用户选；`Low` 未批准的放行但监控。**三个级别下「已禁止（Banned）」的文件一律拦**。
- 文件三种状态：`Approved`（白）/ `Banned`（黑）/ `Unapproved`（灰，既不在白也不在黑）。这是行业里最清晰的「名单是状态、模式是动作」模型。

**Airlock Digital**（澳洲，纯白名单产品）
- `Audit Mode`：监控执行、把文件数据回传中心，不打断用户，用于「发现 + 建策略」。
- `Enforcement Mode`：主动阻止不在允许列表的程序。
- 两种模式**都记事件**，差别只在拦不拦。官方说无论规模多大，审计到切强制通常约三周。

**ThreatLocker**（美国，白名单 + 学习模式）
- `Learning Mode`：自动盘点已在运行的应用和依赖、按观察到的活动**自动生成建议策略**；管理员审完、删掉不需要的，再把终端切到「secured」（强制）状态。
- 强制后用户跑新软件：拦住 → 用户收到申请弹窗 → IT 审批（可在沙箱 VDI 里先试跑）→ 批准/拒绝。

**ManageEngine Application Control**
- `Audit Mode`：允许列表和未列入名单的都能跑，**但黑名单里的仍然拦**，同时收集事件「帮管理员了解用户实际需要什么」。官方推荐新组织从这里开始。
- `Strict Mode`：零信任，只有允许列表里的能跑，其余即时阻止并通知用户。
- 允许列表和阻止列表可以同时存在，冲突时按设置里的优先级处理。

**fapolicyd**（红帽 RHEL 内置 Linux 应用白名单）
- `permissive = 1`：拒绝事件只写审计日志、不真拦。官方用途：「在白名单建好之前一直用 permissive，避免把自己锁在系统外」。
- 默认信任来源是系统包管理器（RPM 数据库里装的都算可信），规则支持按路径、哈希、MIME 类型、信任源。

**奇安信天擎**（产品彩页）
- 「进程管理」三件事写在一起：**终端不能运行黑名单中的进程** / **终端只能运行白名单中的进程** / **终端必须运行的进程**（进程保护，被杀就拉起）。
- 系统目录和天擎自身目录进程**默认例外**。
- **终端运行的进程自动上报至管理中心**，管理员可按规则（进程名、公司名）自动分组——这就是「采集」，它是常态能力，不是模式。
- 主动防御里的进程防护「判定为恶意行为时，根据策略进行提示和拦截」——提示/拦截两档。

**深信服 aES**（用户手册 V6.0.2，2024-03）
- 「应用管控 → 应用黑名单」：选黑名单应用、生效终端、生效时间、**检测到黑名单应用时执行的处置动作**（处置动作是每条策略可选的，不是全局模式）。定位是「阻止黑名单软件运行并记录软件运行日志」。仅支持 Windows。
- 应用识别库：内置规则 + 自定义规则，自定义按数字签名、版本信息、进程描述、图标 hash、产品名称等多字段组合，可选「识别所有子进程」。
- 「服务器可信进程防护」（白名单）流程写得最完整：**先查杀 → 进程学习（1～30 天）→ 看学习结果（标出可疑/无签名）→ 可信进程确认（删不可信、补漏的）→ 生效**。添加方式分学习添加 / 手动添加 / 模板添加。
- 其他策略普遍给「仅告警，不阻断」和「自动阻断」两档，且**默认推荐仅告警**（如可疑 PowerShell）。
- 「资产清点 → 运行进程清点」：全网进程树，含 PID、路径、CPU、内存、版本、运行用户、父进程、启动参数、启动时间——这是采集能力的样子。
- 「进程阻断」是独立的响应动作，可勾选「同时阻断该终端上所有命令行相同的进程」。

**360 终端安全管理系统**（操作手册）
- 软件管理策略：「将流氓软件或管理上需要禁止运行的软件加入黑名单，开启策略后，系统会对名单内目标软件的运行进行**拦截并提醒终端用户进行卸载**」。
- 「软件防安装」按黑白名单设违规范围，靠比对已安装软件名称。
- 违规外联那类策略给「不处理 / 仅告警 / …」的分级动作，思路一致。

**阿里云无影云电脑**（帮助文档）
- 规则类型**二选一**：白名单（识别到的应用放行）或黑名单（识别到的应用拦截）。
- 匹配特征三个：进程名称、Hash、签名；组合逻辑两种：「名称 且（Hash 或 签名）」/「名称 或 Hash 或 签名」。
- 阿里云、微软和无影自身的应用**默认放行且不允许禁用**。
- 黑名单生效后，**正在运行的软件也会被阻止**。
- 记录在「安全中心 → 应用管控 → 应用阻止记录」。

**阿里云云安全中心「应用白名单」**（服务器侧）
- 三阶段：**智能学习中**（1/3/7/15 天可选，机器学习聚类进程）→ **学习完成待确认**（管理员逐个确认，打开开关才生效）→ **策略已生效**。
- 异常处理模式默认「告警」：不在白名单的程序启动就告警。文档只提告警，不提拦截。
- 进程按可信程度分三档：可信 / 可疑 / 恶意；可逐个加白、移出白名单。

**火山引擎飞连**
- 「进程运行管控」：按进程名（含/精确）、数字签名、路径、命令行参数（正则）、软件库引用来匹配，命中即拦，可开「禁止运行通知」并自定义文案。
- 白名单是**模块级例外**：加白的人或设备整体不受进程管控影响。
- 策略有 0～100 优先级，同优先级取最新修改的。进程管控本身只有「拦截」一档，没有仅记录/告警选项。
- 注意：飞连「终端安全策略概述」里的黑/白名单是**防病毒侧的全局例外机制**（按文件 Hash、路径豁免扫描或标记风险），与进程管控的白名单不是一回事。
- 记录进「事件列表」。

**腾讯 iOA**
- 「软件管控 → 软件行为管控 → 禁止运行」：选内置软件或自定义软件（进程名/路径），可设有效期。另有「提醒卸载」等动作。
- 零信任侧「应用进程控制」按发行商、签名、HASH、根证书识别，只有满足要求的进程才能访问内网资源（这是访问控制，不是启动控制）。

## 2. 三种模式分别用来做什么

### 2.1 采集（可见 / 学习）：解决「我根本不知道终端上跑着什么」

- 产出：全网进程清单 + 每个进程的识别特征（路径、哈希、签名、公司名）。
- 白名单模式没有它根本没法开始：不知道有哪些合法程序，就写不出白名单。ThreatLocker、深信服、阿里云都把它做成「自动学习 → 生成候选名单 → 人工确认」。
- 它是常态能力，不是阶段：拦截模式下终端照样上报进程（天擎「自动上报」、深信服「运行进程清点」）。**「学习期」才是阶段**，指的是「用这段时间的采集数据生成名单」。
- 学习期长度：ThreatLocker 2～4 周；深信服 1～30 天；阿里云 1/3/7/15 天；Airlock 约三周。

### 2.2 审计：解决「名单写错了会不会把机器搞瘫」

- 前提：**已经有名单**。终端按名单判定，命中只记录「本该拦」，不真拦。
- 产出的关键数据：「如果现在切拦截，会拦掉哪些」。管理员看这份清单：里面有合法软件 → 名单漏了，补白；里面全是该拦的 → 可以切拦截。
- 微软、Airlock、ManageEngine、fapolicyd 都把它定为**强制前的必经步骤**。微软甚至在事件 ID 上就把「审计中本该拦」（3076/8003）和「已拦」（3077/8004）分开，方便中心统计。
- 深信服把它做成**每条策略的动作选项**（仅告警不阻断 / 自动阻断），而不是全局开关，这样黑名单里「高危的直接拦、可疑的先告警」可以并存。

### 2.3 拦截：真正防护

- 阻止启动；多数产品**连已在运行的也结束**（无影明确写了）；终端弹窗说明原因；记录事件到中心。
- 白名单拦截 = 默认拒绝；黑名单拦截 = 默认放行。
- 配套必需项（否则运维闭环断掉）：拦截记录页 → 一键加白/加黑；终端申请放行通道；系统目录 / 自身目录默认例外；紧急回退（切回审计模式、本地解锁密码）。

## 3. 模式和黑白名单的关系

### 3.1 两个维度，正交

```
              │  没有名单       │  黑名单            │  白名单
──────────────┼─────────────────┼────────────────────┼─────────────────────
采集/学习     │  上报全量进程   │  上报全量进程      │  上报全量进程 → 生成候选白名单
审计          │  （无意义）     │  命中黑名单 → 记录 │  不在白名单 → 记录「本该拦」
拦截          │  （无意义）     │  命中黑名单 → 阻止 │  不在白名单 → 阻止
```

- **名单回答「谁算命中」**：黑名单 = 命中即坏；白名单 = 不命中即坏。
- **模式回答「命中后做什么」**：不判定 / 只记 / 拦。
- 同一份名单从审计切到拦截，规则一字不改，只改动作。这也是为什么行业把它做成一个开关。

### 3.2 黑名单与白名单本身的关系

- **一条策略二选一**（无影文档明确「规则类型互斥」；阿里云社区文章称为「双模机制」；天擎把黑名单、白名单写成两条并列能力，未明说互斥）。原因：白名单已经隐含「不在名单里的都拦」，再叠黑名单没意义。
- **允许并存的产品必须定优先级**：AppLocker 固定「显式 deny > 显式 allow > 隐式 deny」；ManageEngine 让管理员配；飞连按策略优先级数字。
- Carbon Black 用「文件状态」统一了两者：Approved（白）/ Banned（黑）/ Unapproved（灰）。Banned 在任何级别都拦，Approved 在任何级别都放，**模式只决定灰色地带（Unapproved）怎么处理**——High 拦、Medium 问用户、Low 放。这是最值得借鉴的模型。
- **白名单必须有「默认例外」**：系统目录、安全软件自身目录、微软/厂商签名的程序默认放行且不允许禁用（天擎、无影、微软默认规则）。否则白名单一开机器就起不来。
- 天擎还多一档「必须运行」（守护进程），严格说不是名单，是进程保护。

### 3.3 黑名单和白名单对模式的要求不同

| | 黑名单 | 白名单 |
|---|---|---|
| 需要采集/学习期？ | 不强制（名单来自已知威胁、管理要求） | **强制**（名单来自采集） |
| 需要审计期？ | 建议（防误配） | **强制**（防瘫机） |
| 直接上拦截的风险 | 低（范围小） | 高（范围是「其他所有」） |
| 典型场景 | 办公终端禁游戏/挖矿/未授权 IM | 服务器、研发/财务、固定用途机器 |

## 4. 对本项目需求的三点提醒

1. **需求把「采集」列为与审计、拦截并列的一种模式，行业不是这么分的。** 建议改成：采集是终端常态能力（一直上报），「模式」只有审计 / 拦截两档，另加一个「学习期」概念用于从采集数据生成候选白名单。否则会出现「切到拦截模式后进程列表就不更新了」这种反直觉设计。
2. **模式应该是策略级或名单级字段，不是全局开关。** 深信服的做法（每条黑名单策略选处置动作）和 Carbon Black 的做法（按终端策略组设执行级别）都比单一全局开关灵活，能支持「黑名单里高危的直接拦、可疑的先告警」。至少要支持按终端分组分别设模式，才能做灰度。
3. **审计日志和拦截日志要在同一张表里用字段区分「本该拦」和「已拦」**（学微软 3076 vs 3077）。中心才能出「切拦截会影响多少台」的报表，这是审计模式存在的全部意义。
