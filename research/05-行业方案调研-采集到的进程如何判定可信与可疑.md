# 行业方案调研：采集到的进程如何判定「可信 / 可疑 / 恶意」（v0，2026-09-23）

> 调研问题：终端把进程采集上报到 SOC 中心之后，凭什么说某个进程「可信」或「可疑」？行业常规做法是什么？
> 调研方式：本轮全部以各厂商 **公开官方文档** 和业界公开检测规则为准，未使用本仓库既有资料。来源见文末。
> 涉及厂商 / 项目：微软 App Control（原 WDAC）与 Defender for Endpoint、Carbon Black App Control、ThreatLocker、红帽 fapolicyd、阿里云云安全中心、奇安信天擎、腾讯 iOA；检测规则参考 SigmaHQ、Elastic、SANS。

---

## 0. 一句话结论

**行业没有一个「一刀切」的公式能判进程好坏，通用做法是「五层叠加打标签，最后人来拍板」：**

| 层 | 回答的问题 | 核心手段 | 可靠程度 |
|---|---|---|---|
| ① 身份层 | 这个文件到底是谁？ | 数字签名（签名者是谁、签名是否有效）> 文件哈希（SHA256）> 完整路径 > 进程名 | 签名最稳，进程名最弱 |
| ② 信誉层 | 别人见过它吗？口碑如何？ | 云端信誉库（微软 ISG、Carbon Black 文件信誉、奇安信云查杀、VirusTotal）+ 企业内「流行度」（多少台机器上有、首次出现时间） | 依赖联网或离线库 |
| ③ 来源层 | 它是怎么装上机器的？ | 由系统包管理器 / 受管软件分发工具装的默认可信（fapolicyd 用 RPM 数据库；微软「受管安装器」；Carbon Black「可信目录 / 更新器」） | 稳，但只覆盖规范渠道 |
| ④ 行为与上下文层 | 它跑得对不对劲？ | 路径异常（临时目录、公共目录）、伪装系统进程名、父子进程关系异常、命令行参数异常（LOLBins） | 用于把「未知」进一步分成「可疑」 |
| ⑤ 人工确认层 | 最终定性 | 前四层只产出「建议标签」，管理员在「待确认」页逐条批 | 必须有 |

**两个关键共识：**
1. **「未知」不等于「恶意」**。成熟产品一律分三态：可信（白）/ 未知（灰）/ 恶意（黑），模式只决定「灰」怎么处理。
2. **显式规则优先级最高**：明确禁止 > 明确允许 > 信誉判断。信誉（云查、机器学习）是启发式的，只用来兜「没有显式规则覆盖」的那一部分。

## 1. 各家产品的实际判定方式

### 1.1 微软 App Control for Business（Windows 内置应用控制）+ ISG 云信誉

- **ISG 不是一张名单**，而是用给 SmartScreen 和 Defender 杀毒供数据的同一套云端机器学习，把程序分成 **known good（已知好）/ known bad（已知坏）/ unknown（未知）** 三类，数据每 24 小时刷新，所以同一文件的判定会变。
- **只查显式规则没覆盖的文件**：本地先看策略里的明确允许 / 明确拒绝，再看是不是受管安装器装的，都不是才把 **文件哈希 + 签名信息** 送到云端问。云端说「known good」才放行，否则拦。
- **安装器的信誉会传给它写出来的文件**：安装包口碑好，它释放出来的所有文件自动继承信任，靠在文件上写一个内核扩展属性（origin claim）记录「这文件是谁写的、为何可信」。信任沿进程树往下传，安装器进程一退出就断。
- **官方警告**：启动关键文件必须用显式规则放行，别指望云信誉；ISG 是启发式的，安全保证不如显式规则；动态生成二进制、自更新程序常被误拦。
- **判定顺序**：显式拒绝 > 显式允许 > ISG 信誉。

### 1.2 微软 Defender for Endpoint（EDR，端点检测响应）：文件调查页

管理员看一个文件是否可疑，官方文件页给的信息就是行业「可疑判定」的典型输入：
- 哈希、大小、类型、**发布者与签名证书信息**
- **组织内流行度**：过去 30 天内有多少台设备见过、首次 / 末次出现时间
- **全球流行度**：组织外有多少设备见过
- VirusTotal 检出比、Defender 杀毒判定
- **低流行度本身是可疑信号**：全网只有极少数设备见过、且是最近才出现的文件，官方把它作为需要重点关注的对象

### 1.3 Carbon Black App Control（应用控制老牌产品）：0～10 分信誉 + 九种批准手段

- 云端「文件信誉」给每个文件一个 **信任评分 0（最低）～10（最高）或未知**，再加一个 **威胁等级：恶意 / 潜在恶意 / 未知 / 干净**。
- 评分算法考虑四个因素：**来源信任**（文件从哪来）、**发布者信任**（是否有有效数字签名、该发布者历史口碑）、**恶意软件严重度**（杀毒引擎是否报毒）、**漏洞严重度**（该文件是否有已知漏洞）。
- 发布者也有信任评分，基于「该发布者所有文件的综合表现 + 一般声誉」。
- 管理员设一个 **信任阈值**，达到阈值的文件 / 发布者自动批准；可单独关掉某个发布者或文件的自动批准。
- 文件三态：Approved（已批准）/ Banned（已禁止）/ Unapproved（未批准，灰）。
- **批准手段分九层**，官方建议组合使用：预批准、可信目录、可信发布者、更新器（Windows Update 等装的自动信任）、信誉规则、手工批准单个文件、可信用户 / 组、本机本地批准、自定义规则。逐个哈希批是最后手段。

### 1.4 ThreatLocker（白名单产品）：内置应用定义 + 学习期

- 维护 **15,000+ 条厂商整理的内置应用定义**，每条由「跑这个应用需要的所有文件哈希 + 证书」组成。
- 部署后进入学习期，自动把环境里的软件归类到这些定义里；学习期自动生成的规则 **默认用哈希**（最严），有签名的可改用证书。
- 五个匹配参数：哈希、证书、路径、进程、创建者；规则里填了的参数必须全部匹配。

### 1.5 红帽 fapolicyd（Linux 内置应用白名单）：包管理器即信任源

- **核心思想：由系统包管理器（RPM）正确安装、登记在 RPM 数据库里的程序就是可信的。** 不在里面的一律不信。
- 额外可信文件写在信任库里，每条 = **完整路径 + 文件大小 + SHA256**。
- 运行时做完整性校验，三档可选：只比大小（防误覆盖，防不了故意篡改）、用 IMA 扩展属性里的 SHA256、实时算 SHA256。
- 文件在磁盘上被改过（和 RPM 记录不一致）就会被标为不可信，这一点可以用来发现「系统程序被替换」。

### 1.6 阿里云云安全中心「应用白名单」（服务器场景）

- 进程分 **可信 / 可疑 / 恶意** 三档，对应「可信程度」**100% / 60% / 0%**。
- 靠「机器学习引擎自动聚类和搜集告警数据」判定；**官方文档没有公开具体规则**。
- 哈希用于「判断进程的唯一性，避免程序被恶意伪造」；路径用来帮管理员核对来源。
- 流程：建策略 → 选服务器 → 选学习时长 1/3/7/15 天 → 「学习中」→ 「学习完成待确认」→ 手动打开开关生效 → 之后不在白名单的启动就告警，告警页可「加入白名单 / 取消白名单」。

### 1.7 奇安信天擎（国内终端安全）：云查杀 + 未知文件鉴定

- 隐私白皮书写明云查杀上传的内容，等于它的判定输入：**文件名、路径、版本、产品名、签名者、运行参数、文件指纹（哈希）**。
- 官方对「可疑程序」的定义：**「不在云端木马 / 恶意样本黑库里，也不在白库里，但存在一定风险」的文件**；对敏感位置、启动项里的可疑脚本会送云端做「未知文件鉴定」（沙箱等）。
- 云查杀引擎收录 **200 亿+ 流行样本特征**；隔离内网可部署「锡安本地化平台」，内置样本库 + AI 引擎 + 沙箱，离线提供云查杀和未知文件鉴定。
- 进程管理里：**系统目录和天擎自身目录进程默认例外**；终端运行的进程自动上报，可按「进程名、公司名称」自动分组（公司名称 = 签名 / 版本信息里的厂商名）。
- 「软件管理」模块的目标就是「来源可信」：从内网软件库统一分发，避免未知来源。

### 1.8 腾讯 iOA

- 病毒查杀是「本地 TAV 引擎 + 云查」双引擎；禁止运行软件支持内置软件库和自定义（进程名 / 路径 / 进程参数匹配）。
- 零信任侧的「可信应用」按发行商、签名、哈希、根证书识别。
- 公开文档 **没有** 描述进程「可疑」的自动判定规则。

### 1.9 深信服 aES

- 本轮在公开网页上 **没有** 找到「学习结果里怎么标可疑 / 无签名」的官方说明，官方用户手册为 PDF 未逐页核实。**此项存疑，不作为依据。**

### 1.10 轻量做法：Sysinternals Sigcheck / Autoruns

- 微软自家工具的思路就是行业最小方案：`sigcheck -u` 列出 **所有无签名文件**（「大多数可信程序都有签名，无签名即可疑」），再用 `-vt` 把哈希送 VirusTotal 看有没有引擎报毒；Autoruns 也内置 VirusTotal 查询。

## 2. 行为与上下文特征：把「未知」进一步分成「可疑」

这一层来自 EDR 和公开检测规则库，是行业公认的「不用云也能本地判」的特征。

| 特征 | 规则示例 | 说明 |
|---|---|---|
| **伪装系统进程名** | SigmaHQ：进程名以 `\svchost.exe` 结尾，但路径不是 `C:\Windows\System32\` 或 `SysWOW64\`，且文件内部 OriginalFileName 也不是 svchost.exe → 高危 | MITRE ATT&CK T1036.005（伪装成合法名称或位置）。误报极少 |
| **从异常目录运行** | Elastic 规则列了 60+ 个「正常不该有可执行文件」的目录：`Users\Public`、`Windows\Tasks`、`Windows\Fonts`、`Windows\Prefetch`、`Windows\Help`、`PerfLogs`、`Intel\`、`AMD\Temp` 等 | 攻击者爱把恶意程序藏在「看着可信」的系统目录里 |
| **从临时 / 下载目录运行** | `%TEMP%`、`Windows\Temp`、下载目录、压缩包解压后直接运行 | Splunk 等把「从 Temp 目录执行」列为标准检测项 |
| **父子进程关系异常** | SANS「Know Normal, Find Evil」：`svchost.exe` 父进程必须是 `services.exe`；`services.exe` 父必须是 `wininit.exe`；`lsass.exe` 不应有任何子进程；Office 进程拉起 cmd / PowerShell 属异常 | 系统核心进程的父子关系、实例数、运行账号、启动时间都是固定的 |
| **无签名 + 异常位置** | Sigma：无签名 DLL / 可执行文件从可疑位置加载 | 两个弱信号叠加变强信号 |
| **合法程序被滥用（LOLBins）** | `certutil.exe` 下载文件、`mshta.exe` / `rundll32.exe` / `regsvr32.exe` 执行远程脚本、PowerShell 编码命令 | **微软签名、信誉极好，但命令行参数才是恶意所在**。说明只看文件身份不够，采集时必须带命令行参数 |
| **企业内低流行度** | 全网只有 1～2 台机器出现、且是最近首次出现 | Defender 和 Carbon Black 都把它作为核心信号 |

## 3. 行业常规的判定管线（把上面拼成一条流程）

```
终端采集上报：进程名 / 完整路径 / SHA256 / 签名状态与签名者 / 文件版本与公司名 / 父进程 / 命令行 / 运行账号
        │
        ▼
① 命中显式黑名单？ ──是──► 恶意（最高优先级，任何模式都拦）
        │否
        ▼
② 命中硬例外或显式白名单？ ──是──► 可信
   （系统目录、安全客户端自身目录、包管理器 / 受管分发工具装的、管理员手工加白）
        │否
        ▼
③ 签名有效，且签名者在「可信发布者」列表？ ──是──► 可信（自动建议加白）
        │否
        ▼
④ 查哈希信誉（云端或离线库）
   known bad ──► 恶意
   known good ──► 可信
        │未知
        ▼
⑤ 未知（灰）→ 上下文打分，任一命中即标「可疑」：
   无签名 / 签名无效
   路径在临时、下载、公共、Fonts、Tasks 等异常目录
   进程名撞系统进程但路径不对
   父进程关系异常
   命令行含下载 / 编码 / 远程执行等 LOLBins 特征
   全网只在极少数终端出现且是首次出现
        │
        ▼
⑥ 人工确认页：建议可信 / 可疑 / 恶意 三个标签 + 依据说明 → 管理员逐条批 → 进正式白 / 黑名单
```

配套原则（各家一致）：
- **学习期结束前先做一次全盘查杀**，否则会把已经潜伏的病毒学进白名单（天擎云查杀、阿里云、ThreatLocker 的流程都隐含这一步）。
- **信誉判定要定期复查**：微软 ISG 每 24 小时刷新、重启后可清缓存重查；Carbon Black 信誉会撤销。「今天可信」不等于「永远可信」。
- **文件一改，信任作废**：微软 origin claim 与文件绑定，改了就重评；fapolicyd 大小 / 哈希不符即不可信。所以名单条目要绑哈希或签名，不能只绑路径。

## 4. 对本项目 SOC 中心的落地提醒

> 以下是把行业做法映射到「SOC 是控制台、客户端做采集」这个架构上的建议，不是行业结论。

1. **采集字段决定判定上限**。行业判定至少要这些字段：进程名、完整路径、**SHA256**（MD5 已有碰撞风险，行业主流是 SHA256；若客户端只出 MD5，建议同时上报两个）、签名状态（无签名 / 有效 / 无效）、签名者名称、文件版本信息里的公司名、父进程名与路径、命令行、运行账号。缺父进程和命令行，第 ④ 层和 LOLBins 就做不了。
2. **签名校验只能在客户端做**。SOC 没有文件本体，只能存客户端算好的枚举值；SOC 侧能做的是「签名者是否在可信发布者列表」这种字符串比对。
3. **信誉层要考虑隔离内网**。政企内网多数不通公网，天擎用「锡安」离线库解决；SOC 若要做哈希信誉，要么对接内网的杀毒 / 云查服务，要么先做「企业内流行度」（全网终端数、首次出现时间）这种不需要外部数据的信号。
4. **SOC 侧可以纯靠数据库做的规则**（不需要客户端新能力）：
   - 签名有效 + 签名者在可信发布者表 → 建议可信
   - 全网出现终端数 ≥ N 且路径在 `Program Files` / `System32` 等标准目录 → 建议可信
   - 无签名 / 签名无效 / 路径命中异常目录表 / 进程名命中系统进程名表但路径不匹配 / 出现终端数 ≤ 1 且首次出现在 7 天内 → 可疑
   - 同一进程名对应多个不同哈希且部分无签名 → 可疑（伪装或被替换）
5. **列表页要给「依据」**。行业产品在「待确认」页都会写清楚为什么建议可信 / 可疑（Carbon Black 给分数和因素，Defender 给流行度和签名者）。只给一个标签管理员没法拍板。
6. **系统目录与客户端自身目录必须硬例外，且不可删**（天擎、微软一致），否则白名单一开机器起不来。
