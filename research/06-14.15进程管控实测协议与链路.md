# 14.15 进程管控实测协议与链路（v0.2，2026-11-04）

> 调研问题：14.15（测试环境，最新代码）上「中心下发策略和名单 → 终端收到并执行 → 上报入库」这条链路实际是什么样，和设计文档 01、客户端协议 `others/policy/policy.md` 有哪些不同。
> 调研方式：只读。SSH 读 14.15 的 PHP 明文代码、只读查库和 Redis；SSH 读终端 13.18、13.220 的文件和客户端日志。访问参数只在 `CLAUDE.local.md`，本文不写口令、zip 密码这类后端常量，也不写企业号、终端号。
> 出处标法：**读代码** = 14.15 上 `/opt/BDFZ/ESM/data/web/` 下的文件:行（北京 11-04 13:14 的版本，指纹见 `implement/PL-05/baseline/fingerprint-14.15.txt`）；**实测** = 只读查库 / Redis / 终端得到的结果；**推断** = 由前两者推出、还没直接验证。
> 来源：[摸底 changelog](../changelog/log-20261103-2150-14.15全链路测试只读摸底.md)、[实施 PL-05 changelog](../changelog/log-20261104-0016-实施PL-05.md)、`implement/PL-05/baseline/`。测试计划见 [PL-05](../plans/PL-05-进程管控全链路测试计划.md)。
> v0.1 是 TK-1 初版（按摸底写）；v0.2（TK-7）按 PL-05 全链路实测补第 8 节，并改正第 0、2、6、7 节被实测推翻或被同事改动的说法。实测用了两轮：第一轮 `202611041327`、回归 `202611040242`，证据在 `implement/PL-05/<轮次>/<用例>/`。`policy.md` 是客户端给的原件，不改；**14.15 的实际格式以本文为准**，设计 01 在版本记录、11.1 实测补充和 12.1 P25、P26 指向本文；7.4、7.7、10.1 正文不改。

## 0. 一句话结论

- 链路的骨架和设计一致：中心改库 → 写 Redis 组缓存 `pgl_<组号>` → 改终端版本号 → 终端心跳时拉取 → 终端按 `dpath` 下载名单库 → 终端上报审计日志入库。终端收到的策略文件和 Redis 里的内容逐字节一致（实测 md5 相同）。
- 名单报文和设计、`policy.md` **不一样**：节点是 `<userlibs>`，按 6 种 CPU 架构各给一个 md5；目录是 `ruc/libs/w|b/u`；北京 11-04 14:29 前，白黑名单的报文 `policytype` 分别是 `"2"`、`"3"`（设计暂定都用 `"2"`；14:29 后都是 `"2"`，见下一条）。
- 黑名单报文 `policytype` 原来是 `"3"`，终端查不到、不下载。北京 11-04 14:29 同事改了 14.15 后端，白、黑都发 `"2"`（第 6 节）；改后实测黑名单 18～49 秒就下载到终端（E-8）。
- **全链路实测的主要结论**（第 8 节）：策略、名单都能按时送到终端，但①**用户名单（白、黑）在终端上匹配不上**，白名单里的进程照样记「不在白名单」，黑名单里的进程不记；②名单下发过一次以后再改内容、再发布，**终端不会下载新内容**。所以需求的「审计 → 修正误报 → 拦截」在 14.15 上走不通，要客户端同事配合定位。

## 2. 下发报文

外层和现有产品一样：Redis `pgl_<组号>` 是一个 JSON 数组，每项 `policyproductid`、`grouptype`、`policytype`、`policyver`、`policymaincontent`（XML 再 base64）。进程管控的项 `policyproductid` = PROCM 的 GUID `2DA19BD4-5E8D-4397-B233-D9F95CD29DB3`。（实测 `baseline/redis-procm-baseline.txt`）

### 2.1 进程策略（`policytype="1"`）

```xml
<?xml version="1.0" encoding="UTF-8"?>
<root>
  <procaudit>
    <enable>1</enable>
    <auditmode>2</auditmode>   <!-- 1 学习，2 审计，3 拦截 -->
    <notify>1</notify>
    <uptimer>70</uptimer>
  </procaudit>
</root>
```

- 这是默认策略 PID 3 的现值（审计、上报间隔 70）。`policytype="1"` 和设计 v1.0 一致。（实测）
- 没有 `<gwl>` 节点：系统白名单不是通过进程策略里的节点下发的，终端是怎么拿到 `ruc/libs/w/sys/` 下文件的还没查清。（实测；方式未查）

### 2.2 名单（11-04 14:29 起白、黑都是 `policytype="2"`，之前黑是 `"3"`）

```xml
<?xml version="1.0" encoding="UTF-8"?>
<root>
  <procaudit>
    <userlibs>
      <type>2</type>                       <!-- 1 白名单，2 黑名单 -->
      <dpath>ruc/libs/b/u</dpath>          <!-- 白名单是 ruc/libs/w/u；只到目录 -->
      <version>17936901662502</version>
      <platform>linux</platform>
      <name>F2FF19EE8F7865F929087AB5388BD0C7</name>   <!-- 名单 PGUID -->
      <lib><md5>FAB1CE8674116848B74B4D6073D385CD</md5><arch>aarch64</arch></lib>
      <lib><md5>9FB5AD2B9ECC9721A833A749EEA89904</md5><arch>loongarch64</arch></lib>
      <lib><md5>C8B0A8D4CB89AA2A20A4A606A4A19A7F</md5><arch>mips64</arch></lib>
      <lib><md5>87FEEFDFE939558EA657615957397C02</md5><arch>x86_64</arch></lib>
      <lib><md5>27286A6A735BCFD2C40CF1C9CF5CABF8</md5><arch>loongarch64_3c6000</arch></lib>
      <lib><md5>ABC0B34CB474FF68DAE569336D790E18</md5><arch>sw_9916</arch></lib>
    </userlibs>
  </procaudit>
</root>
```

- 上面是同事的黑名单 `Test_b` 的值，原样摘自 TK-0 基线时的 Redis（实测）。之后这一项外层 `policytype` 由 `3` 变成 `2`，XML 内容和版本号不变（实测，TK-5 比对）。
- 终端下载地址推断为 `<dpath>/<name>_<arch>.zip`，例如 `ruc/libs/b/u/F2FF19EE…_aarch64.zip`；中心上这个文件存在，md5 和报文一致（实测）。终端只取自己架构的那个（推断，13.18、13.220 都是 aarch64，只下载过 `_aarch64.zip`）。
- md5 是 zip 文件的 md5，大写（实测）。
- 组从名单里移出时下发「空名单」：`{"root":{"procaudit":{"userlibs":{}}}}`（读代码 `Procmanager.php:558-561` `PROC_EMPTY_WBLIST_JSON`）。

## 6. 黑名单报文编号和终端不一致（已被同事修掉，E-8 实测）

- 13.18 北京 11-04 10:04:07 收到 `type="2" delete="1"`（删白名单项）和 `type="3" delete="0"`（加黑名单项），紧接着 `QueryPolicy failed 80004004 … nType=2`，之后没有任何下载；13.220 在 11-03 15:17、11-04 10:03 也有同样的失败。（实测，日志）
- 两台终端都从没下载过 `ruc/libs/b/u` 下的库；中心上的黑名单库存在，md5 和报文一致。（实测）
- 推断：客户端只按 `policytype=2` 读名单，中心给黑名单发的是 `3`，于是黑名单库不下载、不生效，而原来的白名单项又被删了。这正是设计 12.1 P9 ① 担心的不一致。
- **后续（实测）**：北京 11-04 14:29:54 有人改了 14.15 的 `models/BaseDA/Procmanager.php`（md5 `e807d9de…` → `2e22b6cf…`。旧值就是 TK-0 版本：它和本地源码相同，TK-0 基线记的是同一文件的 sha256 前 8 位 `02d795aa`。本地源码没有这次改动。13:14～14:12 之间还有过一次只加兜底函数 `normalizeLibType` 的改动，正常流程下发内容不变。复核见 `implement/PL-05/202611041327/env-drift/fingerprint-recheck.txt`），Redis 名单项白、黑一律 `policytype=2`，黑白靠 `<userlibs><type>` 区分，和设计 P9 ① 一致（diff 见 `implement/PL-05/202611041327/env-drift/Procmanager.php-local-vs-1415-1429.diff`）。改后 E-8 两轮实测：黑名单项 `policytype=2`、`<type>2`、`dpath=ruc/libs/b/u`，13.18 分别 18、49 秒下载到黑名单 zip。改动前的旧代码没有用实际进程验证过这个断点。黑名单下载以后**仍不生效**，是另一个问题（第 8.5 节问题 B）。

## 8. 实测结论（PL-05 TK-7）

> 环境：14.15 中心 + 终端 13.18（aarch64）；13.220 只读、全程没变。两轮：第一轮 `202611041327`（北京 11-04 13:34～15:25），回归 `202611040242`（15:42～16:40）；另有中断还原演练 `202611040227`（15:27～15:41）。后两个轮次号误用了本机美东时间，北京时间以括号为准。E-6 主体（14:24～14:30）跨过同事 14:29:54 改后端的时刻；E-6 补跑（14:32）、E-7 两次运行、E-8 及之后，测的都是改过的后端（第 6 节）。证据目录 `implement/PL-05/<轮次>/<用例>/`，下文只写「第一轮 / 回归」+ 用例号。

### 8.1 时延

| 段 | 实测 | 用例 |
|---|---|---|
| 页面保存 → 库、Redis、终端版本号 | 页面返回时已写好（秒级） | 全部 |
| 中心改动 → 终端收到策略（`ptfile` 和 Redis 一致） | 1～300 秒：进程策略 32 / 189 秒（E-2），白名单 185 / 33 秒（E-5），换名单 269～300 秒（E-5b），改审计 268 / 283 秒（E-6），黑名单收到 17 / 48 秒、zip 到 18 / 49 秒（E-8），删名单 190 / 239 秒（E-11），移回根管理组两轮 1 / 16 秒、演练 267 秒（E-12） | 两轮 |
| 终端收到 → 下载名单 zip | 收到策略的同一秒开始下载；用例按「收到」和「zip 到」分别计时，两者只差 0～1 秒 | E-5、E-8 |

| 学习数据入库 | 运行后立刻有（同一路径只入一次，见问题 D） | E-3 |

- 终端**每 5 分钟最多处理一次策略变化**，多次变化排队、逐个补收：第一轮 E-5、E-5b 共切了 5 次名单，终端在 14:03、14:08、14:13、14:18、14:23 依次处理，14:28 才收到审计模式。连续改动时生效时间会叠加。
- 用例等待上限 7 分钟，两轮都没有因为太慢超时；超时的只有 E-7（问题 A）、E-9（问题 B）。

### 8.2 学习、审计、拦截在终端上的表现

| 模式 | 实测 | 用例 |
|---|---|---|
| 学习（`auditmode=1`） | 终端上报运行过的程序进 `RPW_EXECFILEINFO`：哈希大写 MD5、`ALGO=0`；同一路径只有一行，再运行不新增，`TIME` 停在第一次 | E-2、E-3 第一轮 |
| 审计 + 白名单 | 不在白名单的 `pl05-unknown` 放行、出日志 `PROCACTION=0`、`ACTIONREASON=2`，哈希 = 终端上算的；**在白名单里的 `pl05-learn` 也出了同样的日志**（问题 B） | E-6 第一轮 |
| 审计 + 黑名单 | 黑名单下载、加载（`procwlu.lib` 是 `type:2`，内容是 `pl05-black` 的 MD5，加载内容只在第一轮存了证）；名单外的 `pl05-normal` 不出日志；**黑名单里的 `pl05-black` 也不出日志**（问题 B） | E-9 两轮 |
| 拦截 | 没测：没有不依赖心跳、在终端本机关掉拦截的办法，开拦截有把 13.18 锁死的风险（E-10 BLOCKED） | — |

- `EPSTATE procaudit` 实测：学习 1、审计 + 白 2、审计 + 黑 3，和设计 5.7 一致；但这个值只说明模式，**不说明名单真的生效**（E-6、E-9 名单都没生效，值照样是 2、3）。`procdef` 两轮一直是 0。

### 8.3 没有用户名单时终端判不判断（E-1b）

- 第一轮（黑名单还按 `policytype=3` 发，终端没加载任何用户名单，`procaudit=2`）：`pl05-probe`、`pl05-normal` 各出 1 条 `ACTIONREASON=2`（不在白名单）；同一时期本计划的 SSH 登录 `sshd-session`、系统命令 `route` 也被记成「不在白名单」（第一轮 `E-6/log-page-unknown.json`，北京 13:42:43、13:45:58；E-1b 用例自己那段「同期 sshd-session 审计日志」查到 0 条，原因没细查）。说明**终端手里没有可用的用户名单时，按「不在白名单」判断、照样出日志**，和设计 11.1 S3「没有名单时终端不判断，不会误报」不符；系统白名单（`procwls.cfg`）也没覆盖 `sshd-session`、`route`。
- 回归（同事改后，`Test_b` 黑名单按 `policytype=2` 下发并加载，`procaudit=3`）：两个程序都不出日志，和 E-9 的 `pl05-normal` 一致。
