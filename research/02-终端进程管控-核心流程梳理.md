# 终端进程管控 — 核心流程梳理（v0，2026-09-22）

> 依据：`requirements/requirements-raw.md`、`screenshot/01-09` 原型截图、`research/01` 调研。
> 本文只回答四个问题：怎么采集进程、怎么定制黑白名单、怎么下发、终端怎么执行。外加"误杀怎么恢复"。

---

## 0. 一句话结论

整个功能是一个四步闭环：

```
① 采集：终端定期上报进程 ──► SOC 进程列表（按 MD5 聚合）
② 定制：从进程列表/手工录入 ──► 中心级"名单表"（白名单库 / 黑名单库）
③ 下发：策略选模式 + 引用一张名单表 ──► 走现有策略链路到终端；名单明细客户端定期拉
④ 执行：终端按模式（采集/审计/拦截）匹配名单 ──► 放行 / 只告警 / 阻断，日志回传 SOC
```

原型比原始需求多出来、且决定架构的三个点：

1. **名单是中心级"名单表"**（一张表一个名字，可开关、可分操作系统），策略只**引用**名单表，不把进程明细写进策略。
2. **模式三档**：采集 → 审计 → 拦截，逐级加严；黑/白名单模式二选一，且只有审计或拦截模式下才能选。
3. **两个周期**：客户端每 N 秒上报进程，每 M 秒同步名单。名单同步是**独立于策略下发**的通道。

## 2. 四步核心流程

### 2.1 ① 采集：终端 → SOC

**目的**：先看清全网跑着什么，名单才有来源。这是后面一切的基础，任何模式下都在采集。

```
终端客户端
  每 N 秒（策略"上报间隔"，默认 360）扫一遍本机进程
  对每个进程算：进程名、完整路径、文件 MD5、数字签名状态、文件描述、所在操作系统
  打包上报 ──► SOC Api/ApiServer.php（日志上报入口）
                ──► Redis 队列 control_exchange_fanout
                ──► Java 后台 MsgService 按 logtype=表名 通用入库（新表零改动）
                ──► 表 PROCM_PROCDETAIL（名字按骨架表头定）
SOC 页面
  按 (进程名, 路径, MD5, 操作系统) 聚合 ──► "按进程显示"，终端数 = COUNT(DISTINCT 终端)
  不聚合 ──► "按详情显示"
```

**和现有"活动进程"（截图 02，资产管理）的区别**：

| | 资产管理 → 活动进程 | 进程管控 → 进程列表 |
|---|---|---|
| 触发 | 管理员点"扫描进程"任务，一次性快照 | 客户端定时持续上报 |
| 字段 | 进程 ID、命令行、启动时间（运行时信息） | MD5、签名、描述（文件身份信息） |
| 用途 | 看这台机器现在跑什么 | 攒名单、判断可疑 |
| 终端 | Windows 资产 | Windows + Linux |

两者字段重心不同，**不要合并**，新建表。

**采集要定的事**（客户端侧）：
- 上报是全量还是增量？全量最简单，但 360 秒一次 × 全网终端，量不小；建议客户端本地去重，只报"新出现的进程指纹"，SOC 端更新 LASTSEEN 时间。
- 签名校验在客户端做（SOC 没有文件，做不了），SOC 只存结果枚举。

### 2.2 ② 定制：SOC 上攒名单表

**目的**：把"认识的进程"整理成可复用的名单，供策略引用。

名单进程的三个来源：

| 来源 | 操作 | 截图证据 |
|---|---|---|
| A. 从进程列表勾选 | 勾选 → "加入白名单/黑名单" → 选目标名单表 | 截图 03 有勾选框，按钮未画出，**需确认** |
| B. 名单页手工录入 | 名单行 →「添加进程」→ 填进程名/路径/MD5/签名 | 截图 06/08 |
| C. 从日志页一键加白/加黑 | 审计模式跑出来的告警 → 直接加进名单 | 日志页无截图，**需确认**；这是运维闭环最关键的一步 |

名单表本身：
- 一张名单 = 名字 + 操作系统 + 开关 + 一堆进程条目。
- 每条进程条目建议字段：`name`（进程名）、`path`（路径，支持通配符）、`md5`、`signer`（签名者）、`memo`。一期客户端若只认名+路径+MD5，signer 留空即可。
- 存表建议：`PROCM_LIST`（名单头：ID/名称/类型黑或白/操作系统/开关/版本号/创建时间）+ `PROCM_LISTITEM`（条目，外键名单 ID）。**版本号**是关键，客户端拉名单时靠它判断变没变。

**推荐上线节奏**（行业标配，写进用户手册）：
1. 全网先跑**采集模式** 1-2 周，进程列表攒满。
2. 从进程列表勾选正常软件建白名单；从可疑/签名无效的建黑名单。
3. 试点组切**审计模式**，看日志里"本该拦什么"，把误报加进名单。
4. 误报清零后切**拦截模式**。

### 2.3 ③ 下发：SOC → 终端

下发的东西分两部分，走**两条通道**：

```
【通道 1：策略】（现有链路，零改动）
  策略页保存 ──► Policycenter/editPolicy
    ──► POLICY / POLICYOBJECT 表
    ──► JSON→XML→base64 → Redis（全局 p_global / 组 pgw_|pgl_ / 终端 p_info）
  终端心跳带 p_ver ──► Api/Ipolicy 比对版本 ──► 变了就下发
  策略内容 = 开关 + 模式 + 名单类型 + 名单表 ID + 弹窗开关 + 两个周期
  （注意：只有名单表 ID，没有进程明细）

【通道 2：名单明细】（新建）
  客户端每 M 秒（"同步时间"，默认 360）请求 SOC：
    "我策略里引用的名单表 ID=X，我本地版本是 v3，有更新吗？"
  SOC 查 PROCM_LIST.VERSION：
    没变 ──► 回"无更新"
    变了 ──► 回全量条目 + 新版本号（一期全量，量大再做增量）
    名单被关闭 ──► 回"停用"，客户端清空本地名单
```

**为什么分两条通道**：名单会频繁改（运维天天加白），策略不常改。名单塞进策略 XML 的话，名单一改就得给所有引用它的策略 bump 版本，策略 XML 也会随名单膨胀到上百条。原型里单独画了"客户端同步时间"，说明产品也是这么想的。

**备选方案（一期偷懒版）**：名单展开进策略 XML，走通道 1 一条路。名单保存时把引用它的所有策略 pstamp 更新一下即可。优点：客户端不用新增拉名单接口；缺点如上。**哪条路取决于客户端团队愿不愿意新做一个接口**，要先对齐。

**下发粒度**：沿用现有策略对象粒度 —— 全局 / 分组 / 单终端。所以"服务器组用白名单模式，办公组用黑名单模式"是天然支持的。

### 2.4 ④ 执行：终端按模式动作

```
进程启动（或定期扫描到运行中的进程）
  │
  ├─ 策略未开启 / 采集模式 ──► 只采集上报，不匹配名单
  │
  ├─ 先过"硬例外"：系统关键进程、客户端自身 ──► 直接放行（不可配置，防瘫机）
  │
  ├─ 白名单模式：在名单里？ ──► 是：放行
  │                          ──► 否：命中 ──┐
  ├─ 黑名单模式：在名单里？ ──► 否：放行     │
  │                          ──► 是：命中 ──┤
  │                                        ▼
  │                        审计模式：放行 + 记告警日志上报（+ 弹窗可选）
  │                        拦截模式：阻止启动（已在跑的是否杀，需确认）+ 记拦截日志上报（+ 弹窗可选）
  │
  └─ 告警/拦截日志 ──► ApiServer 上报 ──► Redis ──► Java 入库 PROCM_ALARMLOG
                       ──► SOC 日志 tab（按详情 / 按进程 / 按终端，含"告警类型"列）
```

**匹配规则要定死**（客户端和 SOC 必须一致）：名单条目有 name / path / md5 / signer 四个字段，一条命中是"四个全对"还是"填了的都对"还是"任一对"？建议：**填了的字段全部匹配才算命中**（空字段不参与），这样"只填 MD5"和"填名+路径"都能用。

**模式与名单的组合矩阵**：

| 模式 \ 名单 | 白名单 | 黑名单 |
|---|---|---|
| 采集 | 不匹配，只采集 | 不匹配，只采集 |
| 审计 | 非白名单进程 → 告警 | 黑名单进程 → 告警 |
| 拦截 | 非白名单进程 → 阻断+告警 | 黑名单进程 → 阻断+告警 |

## 3. 误杀了怎么恢复（需求最后一问）

分三档，前两档 SOC 能管，第三档只能靠客户端自身设计：

| 场景 | 恢复手段 | 谁负责 |
|---|---|---|
| 误杀了某个业务进程，机器还在线 | SOC 上把该进程加白（名单版本+1）→ 客户端下次同步拿到 → 放行。或策略切回审计模式 → 心跳下发 | SOC，已有链路 |
| 误杀面大，想一键停 | 已有紧急命令 `procrtl:close`（cmdId 0xA001，lib/Model/Cmd.php:14-29）→ 客户端立刻停止管控。策略上也可整体关闭 | SOC，命令已存在 |
| 白名单太窄，开机就拦了系统进程，机器起不来 / 断网收不到指令 | SOC 无能为力，必须客户端内置：① 系统进程 + 客户端自身硬编码例外，名单里删不掉；② 白名单里没有系统基础项时客户端拒绝进入拦截模式，降级为审计；③ 与 SOC 失联超过 T 分钟自动降级为审计；④ 本地带口令的紧急关闭工具；⑤ 安全模式不加载拦截模块 | 客户端 |

结论：**SOC 侧默认策略必须是"采集模式"或"审计模式"，绝不能出厂就是拦截**；拦截模式要客户端有兜底才敢放。

## 4. 原型里的疑点（要跟产品 / 客户端对齐）

1. **两处"模式"打架**：名单表自己有"模式"列（截图 06/08），策略里又选一次模式（截图 09）。终端到底听谁的？建议名单表上的"模式"只是展示"当前被哪种模式的策略引用"，或者干脆去掉，模式只在策略里定。
2. **名单绑操作系统的粒度太细**：CentOS 7.6 和 7.9 要分两张白名单？建议粒度放到 Windows / Linux 两大类，或允许"通用"。否则国产化环境一堆发行版会把名单数量炸开。
3. **一个策略只能引用一张名单表**（下拉单选）。实际运维会想叠加"系统基础白名单 + Web 服务白名单"。建议下拉改多选，客户端合并；或者一期就单选，二期再放开。
4. **进程列表勾选后的操作按钮**没画，"加入白名单/黑名单"入口需确认。
5. **日志 tab** 没截图。骨架导出表头已定三个视角（按详情/按进程/按终端），日志页需不需要"一键加白/加黑"要定。
6. **拦截模式下已在运行的进程是否结束**：无影是"策略生效就杀"，天擎是"只拦新启动"。客户端要定，SOC 文案要对应。
7. **名单同步通道**：是新接口客户端主动拉（原型画法），还是展开进策略走心跳（偷懒版）？直接影响客户端工作量。
8. **进程列表数据保留多久**：持续上报会无限增长，要定过期清理（比如 LASTSEEN 超过 30 天删）。
