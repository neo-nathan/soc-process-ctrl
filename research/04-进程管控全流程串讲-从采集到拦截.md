# 进程管控全流程串讲：从采集到拦截（v0，2026-09-23）

> 目的：把「采集 → 候选白名单 → 进程黑白名单 → 审计 / 拦截」几个零散名词串成一条线，方便理解和对齐。
> 依据：`research/02`（核心流程梳理）、`research/03`（行业调研，来源为各厂商官方文档）。本文未重新上网核实各厂商细节。
> 本文只讲「概念怎么串」，不讲 SOC 代码落点；代码落点见 02 文档第 5 节。

---

## 0. 一句话结论

推荐参考 **Carbon Black App Control 的「三态名单」模型**（白 / 黑 / 灰），配合深信服、阿里云的 **「学习 → 人工确认 → 生效」** 上线流程。

> **采集**负责「看见」，**候选白名单**负责「整理草稿」，**黑白名单**负责「定规矩」，**审计**负责「彩排」，**拦截**负责「动真格」；审计和拦截的日志再回流到名单，形成闭环。

最关键的一点：**名单和模式是两件事**。名单回答「谁算违规」，模式回答「违规了怎么办」。

## 2. 用「小区门禁」类比

| 环节 | 小区门禁 | 进程管控 |
|---|---|---|
| ① 采集 | 头一个月保安只登记进出的人，谁都不拦 | 终端把运行中的进程上报给 SOC：进程名、路径、MD5（文件指纹）、数字签名 |
| ② 候选白名单 | 月底翻登记本，把常来常往的人整理成「疑似住户」草稿，还没盖章 | SOC 把采集结果整理成待确认清单，系统先自动打标签，再由人审核 |
| ③ 黑白名单 | 物业逐个核对后盖章：住户名单（白）、禁止入内名单（黑），剩下没核对的是陌生人（灰） | 人工确认后形成正式名单，带版本号下发到终端 |
| ④ 审计 | 保安开始对着名单查人，但陌生人照样放进，只在本子上记一笔「按规定本该拦」 | 终端按名单判断，违规的只记日志，不拦 |
| ⑤ 拦截 | 本子上记的「本该拦」确认都是该拦的人，才真正不让进 | 终端阻止违规进程运行，并上报拦截记录 |
| 闭环 | 拦错了住户，住户投诉，物业补登记，保安换班时拿到新名单 | 在日志里一键加白 / 加黑，名单版本 +1，终端下次同步拿到新名单 |

## 3. 每个环节的输入、输出、是否生效

| 环节 | 在哪一端 | 输入 | 输出 | 名单是否参与判定 |
|---|---|---|---|---|
| ① 采集 | 终端 → SOC | 本机运行的进程 | 进程指纹（名 / 路径 / MD5 / 签名状态 / 描述） | 不参与 |
| ② 候选白名单 | SOC | 采集结果 + 自动打标规则 | 待确认清单（建议加白 / 可疑 / 未知） | 不参与（草稿不下发） |
| ③ 黑白名单 | SOC → 终端 | 人工确认结果 | 正式名单（带版本号） | 参与，动作看模式 |
| ④ 审计 | 终端 | 名单 + 模式 | 「本该拦」日志 | 参与，只记录不拦 |
| ⑤ 拦截 | 终端 | 名单 + 模式 | 「已拦」日志 | 参与，拦并记录 |

## 4. 各环节要点

### 4.1 ① 采集：摸清家底

- **采集一直开着，不算一种「模式」**。审计和拦截期间终端照样上报（天擎「自动上报」、深信服「运行进程清点」都是常态能力）。
- 采集的重点是**文件身份**（MD5、签名），不是运行时信息（PID、命令行）。所以它和资产管理里的「活动进程」是两回事（见 02 文档 2.1 节）。
- 「学习期」是一个**时间段**，指用这段时间的采集数据生成候选名单。常见时长：深信服 1～30 天，阿里云 1/3/7/15 天，ThreatLocker 2～4 周，Airlock 约三周。

### 4.2 ② 候选白名单：把采集结果整理成草稿

- 它是连接「采集」和「名单」的桥。缺了这一步，采集和名单在概念上就接不上。
- 系统先自动打标签，人再审核。行业参考：阿里云分「可信 / 可疑 / 恶意」，深信服在学习结果里标出「可疑 / 无签名」。常见打标规则：

| 特征 | 建议 |
|---|---|
| 有可信签名（微软、正规厂商），且全网多台终端都在跑 | 建议加白 |
| 无签名、签名无效 | 标可疑，人工看 |
| 只有一台终端上出现 | 标可疑，人工看 |
| 路径在临时目录、下载目录等 | 标可疑，建议加黑或人工看 |

  > 上表是行业常见思路的归纳，具体阈值（比如「多少台」算多）需要产品自己定。

- **候选 ≠ 白名单**：草稿不下发、不生效，只有人确认过才进入正式名单。

### 4.3 ③ 黑白名单：定规矩

**Carbon Black 三态模型**（行业里最清晰的「名单是状态、模式是动作」模型）：

| 状态 | 含义 | 在各模式下的处理 |
|---|---|---|
| 白（Approved，已批准） | 明确可信 | 任何模式都放行 |
| 黑（Banned，已禁止） | 明确禁止 | 任何执行级别都拦 |
| 灰（Unapproved，未知） | 没审过 | **模式只决定灰色怎么处理**：高级别拦、中级别弹窗问用户、低级别放行但监控 |

**白名单模式与黑名单模式拦的范围相反**：

| | 白名单模式 | 黑名单模式 |
|---|---|---|
| 拦谁 | 不在名单里的全拦（默认拒绝） | 只拦名单里的（默认放行） |
| 拦的范围 | 大 | 小 |
| 必须先采集 / 审计吗 | **必须**，否则机器容易起不来 | 建议审计，可以较快上拦截 |
| 典型场景 | 服务器、固定用途机器 | 办公终端禁游戏、挖矿、未授权软件 |

**白名单必须有「硬例外」**：系统进程、客户端自身默认放行，且不能被删掉（天擎、无影、微软默认规则都这么做）。

### 4.4 ④ 审计：彩排

- 名单已经参与判定，只是动作换成「记录」。
- 它存在的全部意义是回答：**「现在切到拦截，会拦掉谁？」**
  - 日志里有正常软件 → 名单漏了，补白
  - 日志里全是确实该拦的 → 可以切拦截
- **审计日志和拦截日志要放同一张表，用一个字段区分「本该拦」和「已拦」**。微软用不同事件编号区分：App Control 3076 表示本该拦、3077 表示已拦；AppLocker 8003 / 8004 同理。这样 SOC 才能出「切拦截会影响多少台」的报表。

### 4.5 ⑤ 拦截：动真格

- 阻止进程运行，终端弹窗提示，上报拦截记录。
- 已在运行的进程是否结束：无影会结束，天擎只拦新启动（见 02 文档疑点 6，需要跟客户端对齐）。
- 必须配套的兜底：硬例外、一键切回审计、紧急停止命令（现有 `procrtl:close`）、与 SOC 失联自动降级等（详见 02 文档第 3 节）。

### 4.6 闭环：日志回流名单

```
审计 / 拦截日志 ──► SOC 日志页 ──► 一键加白 / 加黑 ──► 名单版本 +1 ──► 终端下次同步拿到新名单
```

这一步是运维最常用的操作。少了它，误报就只能靠人工去名单页手工录入。

---

## 5. 最容易混的 3 个点

1. **采集不是模式**，是底座能力。行业里真正叫「模式」的只有审计和拦截两档。
2. **候选白名单 ≠ 白名单**：前者是草稿，后者是盖了章、会下发的。
3. **名单和模式互相独立**：同一份名单从审计切到拦截，名单一个字都不用改，只换动作。

## 6. 对照当前原型的缺口与建议

| # | 缺口 | 建议 |
|---|---|---|
| 1 | 原型和需求里**没有「候选白名单」这一环**。唯一来源是「进程列表勾选加白」，而这个按钮在截图里还没画出来 | 不用新做页面：**进程列表加一列「名单状态：白 / 黑 / 未知」**，支持按「未知」筛选 + 批量加白 / 加黑。进程列表本身就成了候选池，也对上三态模型。**这是过渡方案，成熟做法见第 8 节** |
| 2 | 策略页把「采集模式」和审计、拦截并列 | 采集常开；模式只保留审计 / 拦截两档（03 文档第 4 节已提） |
| 3 | 日志页没有截图，「一键加白 / 加黑」入口未确认 | 必须有，这是闭环的最后一步（02 文档疑点 5） |
| 4 | 审计 / 拦截日志是否区分「本该拦」和「已拦」未定 | 同一张表加字段区分（见 4.4） |
| 5 | 审计模式下黑名单也只告警 | 可选参考 Carbon Black / ManageEngine：黑名单在审计阶段也直接拦，审计只作用于灰色进程。**需与产品确认**，这会改变模式的定义 |

## 7. 推荐上线节奏（给用户手册用）

1. 全网开启采集，跑 1～2 周，进程列表攒满。
2. 在进程列表按「未知」筛选，参考自动标签，确认白名单 / 黑名单。
3. 试点组切**审计模式**，看日志里「本该拦」的有哪些，把误报加进名单。
4. 「本该拦」里不再出现正常软件后，试点组切**拦截模式**，再逐步推广到其他分组。

默认策略必须是采集或审计，**不能出厂就是拦截**。

## 8. 行业成熟方案：「采集 → 候选」到底怎么做（2026-09-23 补）

> 第 2 节和第 6 节里「进程列表加一列状态、按未知筛选 = 候选池」是最小改动的讲解模型，**不是成熟产品的做法**。本节记录成熟产品怎么做。
> 来源：03 文档引用的官方文档；标 ※ 的是一般了解，本轮未重新核实。

### 8.1 一句话

成熟产品把**「学习」做成一个有生命周期的对象**：先建学习任务（选机器组、定天数），系统跑完自动生成「待确认清单」，管理员在独立页面逐条批，批完才生效。**候选是任务产出的，不是列表筛出来的。**

### 8.2 共同骨架：一个状态机

```
创建策略/任务 ──► 学习中（N 天）──► 学习完成，待确认 ──► 已生效（审计 或 强制）
   选机器范围        终端持续上报          管理员逐条批              命中才产生事件
   选学习时长        系统自动聚类/打标      可删、可补、可改规则       新程序 → 申请/加白
```

| 特点 | 说明 |
|---|---|
| 学习有**范围** | 按一组机器学，不是全网一张表。Web 服务器组学出来的白名单只给 Web 服务器组用 |
| 学习有**起止** | 明确学习天数（1～30 天），到期进「待确认」，不会一直漂着 |
| 候选是**规则**不是**条目** | 系统把进程聚成「签名者 = Microsoft 全放行」「路径 /usr/sbin/* 全放行」这类规则，几百个进程压成几十条规则 |
| 确认是**独立页面** | 专门的「待确认」页，标出可疑项、无签名项，可一键全部确认或逐条删 |

### 8.3 代表性产品的实际流程

**阿里云云安全中心「应用白名单」**（服务器场景）
- 新建策略 → 选服务器 → 选智能学习时长（1 / 3 / 7 / 15 天）
- 「智能学习中」：终端上报的进程被机器学习聚类
- 「学习完成待确认」：进程按可信 / 可疑 / 恶意三档标出，逐条决定，然后打开开关
- 「已生效」：默认处置是告警；告警页可加白 / 移出

**深信服 aES「服务器可信进程防护」**
- **先病毒查杀**（否则会把病毒学进白名单）→ 进程学习（1～30 天）→ 查看学习结果（标出可疑 / 无签名）→ 可信进程确认（删不可信、补漏的）→ 生效
- 添加方式：学习添加 / 手动添加 / **模板添加**（厂商预置的通用系统进程模板）
- 处置动作普遍两档：仅告警不阻断 / 自动阻断，**默认推荐仅告警**

**ThreatLocker「Learning Mode」**
- 装上即学习：自动盘点已运行应用及其依赖，**自动生成建议策略**（按发布者、按应用，不是进程条目）
- 管理员审完 → 切 Secured（强制）
- 强制后跑新软件：拦住 → 终端弹「申请放行」→ 管理员审批（可先沙箱试跑）→ 批准自动加白。**「申请」是闭环的另一条腿**，不只靠看日志

**微软 App Control / AppLocker** ※
- 策略先以 Audit Mode 下发 → 「本该拦」写进事件日志（3076）→ 用工具**从事件日志反向生成规则**（`New-CIPolicy -Audit` / WDAC Wizard 合并审计日志）→ 合并进策略 → 去掉 Audit 变强制
- AppLocker 有「从参考计算机自动生成规则」向导
- 规则优先级：**发布者 > 路径 > 哈希**。有签名用签名，没签名用路径，实在不行才用哈希

**Carbon Black App Control** ※
- 代理安装时**初始化**：当时已存在的文件全部「本地批准」，把安装那一刻当基线，省掉学习期
- 之后新文件是 Unapproved（灰），Visibility / Low 级别下只跟踪不拦
- 批准手段分层：按发布者 / 可信目录 / 更新器（Windows Update 装的自动信任）/ 信誉服务 / 用户申请后审批。**逐个 MD5 批是最后手段**

### 8.4 对照本项目讲解模型

| 讲解模型（第 2、6 节） | 成熟方案 |
|---|---|
| 全网一张进程列表，按「未知」筛 | 按**机器组**建学习任务，候选只属于这个组 |
| 学习没有起止 | 明确学习天数，到期进「待确认」状态 |
| 候选 = 一行行进程（MD5） | 候选 = **规则**（签名者 / 路径 / 哈希） |
| 系统建议只是一个标签 | 建议 + **预置模板** + 先查杀再学习 |
| 只有「日志里一键加白」一条回流路 | 还有**终端申请 → 管理员审批** |
| 名单和进程列表在同一页 | 学习结果 / 待确认有**独立页面**和独立状态 |

### 8.5 往成熟方案靠的最小改动（建议）

1. 把「学习」做成对象：策略里加「学习 N 天」，到期状态变「待确认」，SOC 上有一个待确认页。
2. 名单条目支持三种匹配类型：**签名者 / 路径（通配）/ MD5**，优先级签名者 > 路径 > MD5，候选数量才压得下去。
3. 出厂带「系统基础白名单模板」（Windows / Linux 各一），学习前先套模板，学习只处理业务进程。
4. 学习前强制先跑一次病毒查杀（可联动现有病毒查杀模块）。

这四条会推翻第 6 节「进程列表 = 候选池」的建议；第 6 节保留作为过渡方案，产品定型以本节为准。
