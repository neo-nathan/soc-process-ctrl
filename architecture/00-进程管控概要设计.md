## 0. 一页纸

**要做的事**：给 SOC 中心加一个「进程管控」子产品，管理员能控制 Linux 终端上哪些程序可以运行。用法是四步走：先让终端**学习**（把运行过的程序报上来），管理员据此攒出**白名单或黑名单**，再切到**审计**（违规只告警）试跑，确认没误杀后切到**拦截**（违规直接拦住）。

**一期范围**

| 做 | 不做（一期） |
|---|---|
| Linux 终端的进程策略：关闭 / 学习 / 审计 / 拦截 | Windows 终端（结构上预留） |
| 学习模式采集运行过的程序和安装包，进程管理页按「路径 + 哈希」跨终端汇总 | 安装包的页面展示（只入库） |
| 白名单、黑名单的增删改、发布、应用范围（只能选分组）、删除 | 名单直接挂到单台终端（二期） |
| 审计日志查询，从日志加白、加黑 | 终端视角页面（二期） |
| 全局白名单：随安装包、升级包部署，通过策略告诉终端去哪下载 | 全局白名单的上传入口 |
| 权限：主账号 / 副账号 / 组管理员三级 | 远程开关按钮（命令保留在后端）、级联、导出、首页大屏、报告 |

**方案一句话**：进程管控沿用已登记的 PROCM 子产品身份。进程策略直接走现有的策略中心，和病毒查杀一样。白名单、黑名单也存在策略表里，但登记成「另一个产品」的策略，所以不会出现在策略中心，一个组只能挂一个名单也由现有机制自动保证。名单明细不塞进策略，打成 zip 文件让终端自己下载。学习数据和审计日志走现有的日志上报通道，由 Java 后台按表名自动入库。

**现状**：客户端已按协议开发；前端骨架已提交；后端在 101 上刚起步，和本设计有偏差，正式开发时按设计逐条对齐；101 开发环境已建表、已有测试终端在上报。还有 13 项要和客户端、产品、数据库脚本维护方、项目负责人、运维对齐（第 11 节），其中 4 项决定能不能开工。

## 1. 名词（大白话）

| 名词 | 意思 |
|---|---|
| 进程策略 | 告诉终端「进程管控开不开、用什么模式」的配置。一个总开关加三选一的模式 |
| 学习模式 | 终端把本机**运行过的程序**（路径 + 文件哈希）和**安装包**报给中心，不判断、不拦截。不是扫全盘 |
| 审计模式 | 终端按名单判断，违规的程序**放行但记日志**，可选弹框提示用户 |
| 拦截模式 | 终端按名单判断，违规的程序**拦住并记日志**，可选弹框提示用户 |
| 进程规则 | 「程序路径 + 文件哈希」两项都相同才算同一条。哈希就是文件的指纹 |
| 进程原始数据 | 学习模式下终端报上来的原样数据。入库时按「终端 + 路径 + 哈希」去重，每台终端每个程序只留一行 |
| 进程记录 | 把各终端的原始数据跨终端合并后的结果：同一个程序在多少台终端出现过。展示在「进程管理」页 |
| 白名单 / 黑名单 | 允许 / 禁止运行的进程规则清单。挂白名单时，不在清单里的算违规；挂黑名单时，在清单里的算违规 |
| 库文件 | 协议里的叫法：名单明细写成一个文件、压成 zip，终端按中心给的路径下载 |
| 全局白名单 | 专门团队制作的「可信程序清单」文件，随 SOC 安装包、升级包部署到中心，页面看不到，终端按策略里的地址自己下载 |
| 发布 | 把名单当前内容**定稿**。定稿不等于下发；已经有应用范围的名单，定稿后自动下发 |
| 应用范围 | 名单挂在哪些分组上。选了范围就会下发 |
| 组级 / 终端级 | 策略挂在分组上叫组级，组里终端都继承；单独挂在某台终端上叫终端级，终端级优先。名单只有组级 |
| 心跳 | 终端每隔一段时间（默认 5 分钟）主动联系中心一次，顺便问「策略有没有变」 |
| 主账号 / 副账号 | 主账号就是用户名为 optAdmin 的账号；其他同级别账号都算副账号 |
| 组管理员 | 只能管创建时勾选的那几个分组的账号 |

详细设计 1.2。

## 2. 总体架构

### 2.1 组成

```
管理员浏览器
  ├ 左侧菜单「进程管控」：概览（页签：概览 / 日志 / 策略）、进程管理、白名单、黑名单
  └ 策略中心：产品下拉里多一个「进程管控」（只有 Linux）
        │
SOC 中心（PHP）
  ├ 新增：进程管控模块（概览、日志、进程管理）、名单模块（名单和名单里的进程）
  ├ 复用：策略中心（策略的存储、应用到组 / 终端、继承、换组、下发），只加一道「进程管控专用」的权限校验
  ├ 数据库：策略表、策略应用范围表（现有）；名单进程表、学习数据表、审计日志表（新建）；终端状态表（现有）
  ├ 缓存：各组的策略缓存、各终端的策略版本号——下发全靠「改版本号」
  └ 文件目录：名单库文件 zip、全局白名单文件，终端按相对路径下载
        │ 心跳：版本号对不上就整包下发        ▲ 上报：学习数据 / 审计日志 / 终端状态
Linux 终端（进程管控模块）                   │
                                  Java 后台程序（定时拉起）
                                    ├ 消费上报队列，按「消息里的表名」通用入库
                                    └ 每天定时按保留天数清理日志
```

### 2.2 六条数据流

| # | 流向 | 怎么走 | 什么时候 |
|---|---|---|---|
| ① 策略下发 | 中心 → 终端 | 改策略 → 重建这个组的策略缓存、改组内终端的版本号 → 终端下次心跳发现版本不一样，整包拉取 | 保存策略、改策略的应用范围 |
| ② 名单下发 | 中心 → 终端 | 和 ① 同一条通道，内容只是「库文件说明」；终端发现库版本变了，再按路径下载 zip、校验 | 已应用的名单发布、改应用范围、删除名单 |
| ③ 学习数据 | 终端 → 中心 | 终端上报 → 队列 → Java 按「终端 + 路径 + 哈希」有就更新、没有就插入 | 学习模式下 |
| ④ 审计日志 | 终端 → 中心 | 终端上报 → 队列 → Java 追加写入 | 审计 / 拦截模式下发现违规程序 |
| ⑤ 状态上报 | 终端 → 中心 | 终端报自己实际在用的模式、名单类型、远程开关状态 → 终端状态表 | 状态变化时 |
| ⑥ 日志清理 | 中心内部 | Java 每天按保留天数删审计日志 | 定时 |

**要点**：中心从不主动推送，只改版本号；终端每次心跳拿自己的版本号和中心比，不一样就整包重拉，直到对上为止。所以下发没成功不需要管理员补救，也不设「重新下发」按钮。

### 2.3 复用和新建

| 部分 | 复用现有 | 新建 / 修改 |
|---|---|---|
| 产品身份 | PROCM 已登记的配置、菜单开关、前端路由 | 补齐策略中心等处的登记；收紧菜单的级别判断（现有放行了多一个级别）；旧版残留按新 demo 重写，概览模板那段保留在原位改，不整段删 |
| 进程策略 | 策略中心全部 | 进程管控自己的策略页、权限校验、默认策略 |
| 名单 | 策略表、应用范围表、缓存重建和版本号机制、分组树组件、文件下载和打包的先例 | 名单进程表读写、发布（生成库文件）、名单页面和接口、一个公共的「重建组缓存」函数 |
| 概览 | 各产品共用的概览数据层、在线数、策略来源 | 策略模式筛选、名单列 |
| 学习数据 / 审计日志 | 上报通道、队列、Java 通用入库；日志页照道系统的进程审计日志 | Java 加两处配置；查询接口和页面 |
| 日志清理 | 日志清理表 + Java 定时清理程序 | 插一行；日志保留设置页加前缀映射 |
| 权限 | 接口登记网关、主账号判断、组管理员的所辖分组、二次认证 | 接口登记、产品校验、所辖范围校验的公共函数 |
| 全局白名单配置项 | 现有的中心配置表 | 新写一个刷新函数 |

## 3. 管理员怎么用

按需求的操作流程，一个分组从零到拦截要经过四个阶段：

```
① 学习        主账号在策略中心建一条「学习」策略 → 应用到分组 G
              G 里的终端下次心跳拿到策略 → 开始上报运行过的程序和安装包
              「进程管理」页看到跨终端汇总的进程记录，概览页「策略模式」列显示「学习」

② 攒名单      进程管理页勾选（或按条件）加白 → 名单显示「+N」「待发布」
              点「发布」→ 「已发布」，生成库文件。此时还没下发到任何终端

③ 审计        把 G 的策略改成「审计」→ 把名单应用到 G（两步顺序可以颠倒）
              终端分别收到策略和库文件说明，下载 zip
              违规的程序放行 + 上报审计日志；「日志」页看到
              误报：日志页勾选 → 加白 → 名单「有变更」→ 发布 → 自动下发新版

④ 拦截        策略改成「拦截」→ 下次心跳生效，违规程序被拦住
              误杀：策略改回「审计」→ 修名单 → 发布 → 再改「拦截」
```

日常会遇到的几种情况：

| 情况 | 结果 |
|---|---|
| 终端换组 | 直接用新组的策略和名单，新组没有名单就没有；单独分配给这台终端的进程策略保留（现有机制如此，需求措辞和它不一致，P18） |
| 给已经挂了名单的组再挂一个（进程策略同理） | 自动替换，不弹确认 |
| 新建子组 | 自动带上父组的策略和名单 |
| 组从「不继承」改成「继承」、移动分组 | 整体照抄（新）父组的策略和名单，本组原来的名单没了（待产品确认，P21） |
| 删除名单、把组移出应用范围 | 组内终端下次心跳拿到的策略里没有名单，就清掉本地名单 |
| 个别终端要特殊处理 | 一期名单不能挂到单台终端。只是被误拦：在策略中心给它单独分配「审计」策略；确实要用不同名单：单独建个组挪进去 |

详细设计 11.1（场景走查 24 条）、7.10。

## 4. 关键设计决定

每条写「决定是什么、对使用者意味着什么、为什么」。编号 D1-D14 是本文的，括号里是详细设计的编号。

| # | 决定 | 对使用者意味着什么 | 为什么 |
|---|---|---|---|
| D1（K1） | 沿用已登记的 PROCM 产品身份，只做 Linux。数据库表名前缀保持 RPW | 已登记的配置和菜单开关沿用；授权要导入，策略中心、分组、Java 等处的产品清单要补登记。表前缀 RPW 和产品代号 PROCM 不一致，日志保留设置页要加一条映射才能显示进程管控的日志表 | 产品答复；客户端已按 RPW 前缀开发 |
| D2（K2） | 进程策略直接走策略中心，和病毒查杀一样 | 新建、编辑、复制、删除、应用到组、应用到终端、继承、换组全部复用。进程管控自己的策略页只能改**分组**的策略，给**单台终端**分配要去策略中心 | 需求「使用 SOC 原有策略体系」 |
| D3（K3、K4） | 白名单、黑名单也存在策略表里，但登记成**另一个产品**的策略（一个只在中心数据库里用的「名单产品号」），给终端的下发内容仍然标 PROCM | 名单不会出现在策略中心；一个组只能挂一个名单（白黑合计）由现有「同一产品先删旧的再挂新的」规则自动保证；策略中心现有的找策略、删旧关联等代码不用为名单改；终端看不出区别 | 曾考虑同用 PROCM、靠一个类型字段区分，要给十几处共用代码加条件，还漏了复制、导入等入口，国产库缺列时整个策略中心报错；项目负责人 10-15 选定 |
| D4（K5） | 名单明细不塞进策略，走**库文件下载**：策略里只放文件说明（类型、文件名、下载路径、校验值、版本），明细打成 zip | 名单再大，策略体积和心跳流量不变；只有库版本变了终端才下载 | 客户端协议定的 |
| D5（K13） | **名单只挂组**，不能挂单台终端 | 一台终端的名单就是所在组的名单，最多一个，不分白黑、不分先后，换组不用特殊处理 | 需求；产品确认。按终端挂名单放二期 |
| D6（K7） | 「发布」= 定稿，「应用范围」= 下发。发布状态（-- / 待发布 / 已发布 / 有变更）由名单进程表的数据推导，不单独维护 | 状态和内容永远对得上 | 「发布 = 定稿、应用范围 = 下发」和按钮规则是需求定的；「状态由数据推导、不单独维护」是设计决定 |
| D7（K11） | 给已挂名单的组再挂一个，**自动替换**，不弹确认；给已挂进程策略的组或终端再挂一条，同理 | 和策略中心现有的替换逻辑一致 | 产品答复 |
| D8（K6） | 不设「清除名单」命令，也不设「重新下发」按钮。清除靠「下一轮下发里没有它」，重发靠心跳比版本号 | 生效时间是**下次心跳**（在线终端默认 5 分钟内，离线终端上线后），页面文案不说「立即」 | 远程命令 30 分钟过期，离线终端收不到；心跳机制本来就会自动重拉 |
| D9（K8） | 只有主账号能改名单、进程管理、加白加黑、进程策略（**包括在策略中心里**），后端拦截，不只是前端藏按钮 | 副账号、组管理员只读 | 产品答复；现有「副账号只读」只靠前端藏按钮，直接调接口就能改 |
| D10（K9） | 学习数据每台终端每个程序只留一行；跨终端汇总在进程管理页查询时现算，不写 Java 汇总程序。删除终端、卸载终端都不清学习数据 | 表只增不减，百台规模几万行，够用；超过千台再考虑定时汇总表 | 产品答复 |
| D11（K14） | 文件哈希全链路**小写**；程序路径**区分大小写** | Linux 下 /opt/App 和 /opt/app 是两个程序；客户端现在报的是大写哈希，要改 | 哈希小写是产品答复；路径区分大小写是 Linux 本来的行为 |
| D12（C4） | 全局白名单由专门团队制作，随安装包、升级包部署，**没有上传入口**；写进每一条进程策略里下发。全局白名单优先于用户黑名单 | 升级包带了新文件时，所有 Linux 终端下次心跳拿到新的全局白名单地址；文件没变就不重下 | 产品答复；「写进每条进程策略下发」是项目负责人 10-15 选定 |
| D13（A8） | 出厂默认策略是**关闭** | 默认策略自动挂到所有分组，出厂开启的话装了客户端的终端会立刻进入某种模式 | 产品答复 |
| D14（K12） | 终端视角页面、按终端挂名单放二期；Windows（结构预留）、级联、导出一期不做。一期概览页点终端名只弹提示；远程开关命令保留在后端，不做页面入口 | 一期功能边界 | 终端视角、挂终端、远程开关是产品答复；Windows 按需求「一期只做 Linux」；级联、导出按推荐 |

详细设计 0 节「14 条核心设计决定」。

## 5. 权限

### 5.1 谁能做什么

| 功能 | 主账号 | 副账号（同级别其他账号） | 组管理员 | 系统管理员 / 审计管理员 |
|---|---|---|---|---|
| 看到「进程管控」菜单 | 能 | 能 | 能 | 不能 |
| 概览（终端列表） | 全部终端 | 全部终端 | 仅所辖分组 | — |
| 日志：查看 | 全部 | 全部 | 仅所辖分组 | — |
| 日志：加白 / 加黑 | 能 | 不能 | 不能 | — |
| 策略：查看（概览→策略页签、策略中心） | 能 | 能 | 能（所辖分组） | — |
| 策略：修改 / 新建 / 删除 / 应用（**包括在策略中心里**） | 能 | 不能 | 不能 | — |
| 进程管理、白名单、黑名单（菜单和全部接口） | 能 | 菜单不显示 + 后端拒绝 | 同左 | — |

补充：
- 历史遗留的超管级别按主账号对待。
- 组管理员的所辖分组只包含创建账号时勾选的组，**不自动包含子组**，和其他子产品一致。「包含子组」只在所辖组里展开。
- 分组管理里「改继承」「移动分组」会让组整体照抄父组的策略和名单。这两个是所有产品共用的分组功能，副账号、组管理员也能用，进程管控不单独拦，视为「组跟着父组走」的正常结果（待产品确认，P21）。

### 5.2 怎么保证（四道门）

| 门 | 管什么 | 做法 |
|---|---|---|
| ① 菜单门 | 看不看得到 | 后端按级别算出「是否显示进程管控」，二级菜单再按主账号判断 |
| ② 按钮门 | 页面里的按钮 | 非主账号不渲染：加白加黑、策略页「应用」、继承勾选框、策略中心里进程策略行的编辑 / 复制 / 应用 / 删除、新建 / 复制策略时产品下拉里的「进程管控」 |
| ③ 接口登记门 | 接口能不能调 | 每个接口在接口权限表里登记允许的角色：只读接口给副账号和组管理员；名单、进程管理、加白加黑只给主账号 |
| ④ 产品校验门 | 能改到策略的**通用**接口 | 策略中心的编辑、新建、删除、应用范围、导入，以及分组树上的「开启继承」等入口，后端按策略的真实产品号判断：属于进程管控而当前不是主账号 → 拒绝；属于名单 → 一律拒绝，名单只能走名单自己的接口。另有一个不走策略中心存储的旧策略编辑入口，对进程管控策略和名单都一律拒绝，主账号改进程策略只走策略中心 |

第 ④ 道门必须有：策略中心的编辑接口现在不校验用户身份，产品号也是前端传的，可以造假，后端要按记录编号从数据库查出真实产品号再判断。

组管理员的范围校验做成公共函数，所有带终端编号或组编号参数的新接口都调它；现有代码没有这样的公共函数，有几处写法有越权漏洞，新代码不照抄（第 12 节）。

### 6.2 策略表里的三种记录

| | 进程策略 | 白名单 | 黑名单 |

| 产品号 | PROCM | 名单产品号 | 名单产品号 |
| 类型列 | 不写 | 2 | 3 |

### 6.3 名单进程表

一行 = 名单里的一条进程规则，带三种状态：0 已确认（在已发布版本里）、1 新增（上次发布后加的）、2 待移除（标记了、还没发布）。规则唯一键 = 算法 + 哈希 + 路径。不存进程名称，页面显示时取路径最后一段。

名单列表里的「进程数 base +N -M」：base = 状态 0 和 2 的行数，+N = 状态 1，-M = 状态 2，发布后的进程数 = base + N − M。

| 键 | 用在哪 | 取值 |
|---|---|---|
| `procaudit` | 概览「策略模式」列 | 0 关闭、1 学习、2 审计、3 拦截（脚本已定，101 上客户端已在上报） |
| `proclib` | 概览「策略模式」列的名单标签 | 0 没有、1 白名单、2 黑名单 |

### 6.5 数据库脚本要改什么

脚本由客户端侧逐渐完善；真正上线用的是安装包里按数据库种类各一份的建库脚本（MySQL、Polardb 的是加密的），不在中心 PHP 仓库，要交给数据库脚本维护方。**必改**的：修正注释写法（现有脚本里有数据库不认的注释格式）；路径列改成区分大小写；名单进程表加唯一键、加标记人和标记时间；审计日志表、运行程序表加索引；日志清理表插一行；安装包名列改非空；策略表加类型、状态两列（现有脚本里没有）。不改存储过程。其他库种（达梦、神通、金仓）的升级方式和大小写行为没有先例，上这些库种前要和维护方实测（P19）。

**数据量估算**：一台 Linux 服务器运行过的程序几十到几百个，100 台也就几万行学习数据；审计日志按 100 台、每台每天 1000 条、保留 60 天算约 600 万行，索引够用；超过千台要缩短保留期或分表。

## 7. 功能设计

### 7.1 进程策略

**内容**（按协议）：总开关、模式三选一（学习 / 审计 / 拦截）、是否弹框提示用户、上报间隔（默认 360 秒，暂定 60 到 86400）。demo 里「审计」「拦截」两个卡片各有一个提示勾选框，其实是**同一个**开关，两处绑定同一个值。另外中心自动写入一段全局白名单说明（文件名、路径、校验值、版本），页面不展示，保存策略时后端补上，不依赖前端提交的内容。

**默认策略**：必须有一条 Linux 默认策略，否则删除用户策略时现有逻辑会报错。新装、升级、新建组三处都要补：新装和升级由同一个 PHP 函数插入（没有才插，可重复执行），不改存储过程；升级时按组判断，没有进程策略的组才挂默认策略，不要照抄现有某个「有一条关联就整体跳过」的写法。出厂值关闭。

**在哪改**：进程管控→概览→策略页签，左树只有分组，右侧显示该组生效的策略，主账号可改；策略中心能做全部操作，是给单台终端分配策略的唯一入口。**策略是共享的**：在某个组的策略页点「应用」，改的是这条策略本身，所有用它的组都受影响，所以「应用」前弹窗提示「该策略同时应用于 X 个组、Y 台终端」。X 是用这条策略的组数，Y 是单独分配了这条策略的终端数，不是组内终端数，和名单的「N 个组 M 台终端」口径不同，两处文案不要混用。

**对策略中心通用代码的改动**：名单用了独立产品号之后，策略中心现有的查询、删旧关联、列表、复制、重名检查一处都不用改。只改进程管控自己的事：策略中心所有能改到策略的接口和分组树「开启继承」入口都加产品校验门（第 5.2 节第 ④ 道门），「开启继承」还要改为从数据库重建缓存；保存策略时后端补全局白名单说明；策略中心前端和各处产品清单加上「进程管控」，客户端类型只给 Linux；策略中心删除策略、删除终端策略的两个已知缺陷建议一起修（第 12 节）。

**生效时间**：中心不推送，终端下次心跳才拉取。文案统一为「在线终端下次心跳（默认 5 分钟内）生效，离线终端上线后生效」。

详细设计 6。

### 7.2 黑白名单

白名单和黑名单逻辑完全一样，只有类型值和终端判定方向相反。

**发布状态和按钮**（需求定稿）

| 发布状态 | 什么情况 | 发布 | 应用到组 | 删除 |
|---|---|---|---|---|
| --（灰） | 一个进程都没有 | 灰 | 灰 | 可 |
| 待发布（蓝） | 没发布过，有新增 | 可：只定稿 | 灰：先发布 | 可 |
| 已发布（绿） | 定稿了，没有待发布的增减 | 灰 | 可：选完 / 改完自动下发 | 可 |
| 有变更（橙） | 发布过，之后有增减 | 可：没应用时只定稿；已应用时定稿并自动下发 | 灰：先发布 | 可 |

前端置灰只是体验，后端每个接口按同样规则再校验一遍。

**名单里的进程怎么增删**
- 手动添加：路径要是 Linux 绝对路径；哈希 32 位（MD5）或 64 位（SHA256），统一转小写。撞上已有规则：已有的是正常或新增 → 提示不用重复添加；已有的是待移除 → 提示点恢复即可。
- 移除：已发布版本里的进程标记「待移除」，记标记人和时间；新增的直接删。**发布过的名单，移除后至少要剩 1 个进程**，否则当场拦住：要清掉整条名单请直接删除它。没发布过的名单可以删光，状态回到 --。
- 恢复：只对待移除的。
- 从进程管理页、日志页批量加入：不存在的插入，待移除的改回正常，已有的跳过并计入「已存在」。
- 同一条名单上的写操作**排队执行**（发布、改范围、删除、增删进程都先锁住名单记录），两个管理员同时操作不会把数据弄乱。

**发布做什么**：校验状态和进程数 → 把待移除的删掉、新增的转正 → 生成新版本号 → 用全部正常行生成库文件并压成 zip（先写临时名、成功后改正式名，终端不会下到半个文件；失败就回滚，名单状态不变）→ 更新策略记录（库文件说明、版本、状态）→ 如果名单已有应用范围，重建这些组的缓存、改终端版本号，终端下次心跳就能拿到 → 清理旧 zip，每条名单只保留最新 2 个版本，给正在下载上一版的终端留余地。

**应用范围**：只有「已发布」状态能改；只能选分组；弹窗直接调策略中心的公共分组树组件，策略中心本身不改。提交勾选的全部组，后端算差集：新加的组先删掉这个组上的旧名单（白黑都算）再挂本名单（自动替换）；去掉的组删关联；然后对涉及的全部组重建缓存。弹窗里不显示「继承」勾选框，因为那个框改的是进程策略的继承，放在名单弹窗里会让人误解。「应用范围：N 个组 M 台终端」，M 是这些组里装了进程管控的 Linux 终端数。

**删除**：任何状态都能删。有应用范围时提示「删除后这些终端下次拉取策略时会清掉本地名单」。顺序是先在一个事务里删掉关联、进程行、名单记录并提交，再重建原来那些组的缓存通知终端，最后删 zip 文件。不能反过来先清缓存再删库：删库失败的话两边对不上，下一次任何重建都会把名单又加回来。

**下发失败怎么办**：不用管理员补救。终端每次心跳带版本号和中心比，不一样就整包重拉，直到对上。中心写缓存那一步本身失败（缓存服务刚好断开）是所有产品共有的极小窗口，不单独补救：发布、改范围时接口会报错（缓存服务断开报「Redis 异常」，写入返回失败报「数据已保存、下发缓存写入失败」），原样再提交一次应用范围即可；删除时名单已经没了没法补提交，原来那些组要等下次任何一次重建，这期间终端照旧按旧名单工作，不会出错，接受。

详细设计 7.1-7.6。

### 7.3 名单下发格式

策略里的库文件说明：类型（1 白 2 黑）、zip 里那个文件的名称、zip 的下载相对路径、zip 的校验值、版本。zip 放在中心 web 根目录下的一个专用目录，文件名带名单标识和版本号，新旧版本并存；路径只由中心生成，终端照抄下载，不自己拼。

库文件内容暂定 UTF-8 的 JSON：类型、版本、条目数组（路径、哈希小写、算法）。如果专门团队做的全局白名单已有固定格式，库文件直接沿用那个格式，终端只需要一个解析器。格式、路径、命名、校验值大小写都待客户端确认（P2、P3）。

详细设计 7.7。

### 7.4 全局白名单

专门团队制作 JSON，手动打进安装包和升级包，提交到源码库的一个固定目录随 web 包部署。中心在新装、升级后处理时做三件事：算文件校验值和上次比，没变就不重新压缩（否则每次升级所有终端都要重下一遍）；把文件信息记到配置表；刷新所有进程策略里的全局白名单说明，再对全部组重建缓存、改版本号；单独分配了进程策略的终端也要重建终端缓存，否则这些终端拿到的还是旧地址。中心没部署这个文件时，策略里就不写这段，终端按「只有用户白名单」判断。新装时这一步失败只记日志，不能拖垮装机。

详细设计 7.8。

### 7.5 终端判定规则（待客户端确认，P9）

| 模式 | 终端生效的名单 | 程序情况 | 终端动作 | 上报 |
|---|---|---|---|---|
| 关闭 | 任意 | — | 不采集、不判断 | 只报状态 |
| 学习 | 任意（名单下发了也不用） | — | 只采集 | 运行过的程序、安装包 |
| 审计 | 白名单 | 在全局白名单或用户白名单里 | 放行 | 无 |
| 审计 | 白名单 | 不在 | 放行 + 可选提示 | 审计日志（原因：不在白名单；动作：告警） |
| 审计 | 黑名单 | 在用户黑名单里且不在全局白名单里 | 放行 + 可选提示 | 审计日志（原因：在黑名单；动作：告警） |
| 审计 | 黑名单 | 其他 | 放行 | 无 |
| 拦截 | 白名单 | 在全局或用户白名单里 | 放行 | 无 |

## 12. 现有代码的坑

调研时发现的现有问题，不修的话进程管控也会受影响。

**必修**：移动分组时现有代码会把组的 Linux 策略缓存删掉、把 Linux 内容写进 Windows 的键，而且不改企业级缓存版本。后果是移动分组后组内 Linux 终端拿不到任何组策略，进程管控被当成关闭、名单被清，其他 Linux 子产品同样丢策略。101 上 606 个分组有 600 个开着继承，影响面不小。改法是移动分组时调公共的「重建组缓存」函数。

**建议一起修**：删除策略后缓存写回的还是旧内容；删除终端策略会把终端整份策略缓存删掉；批量分配策略时数组没重置；分组树勾父组时孙子组勾选状态会翻转（名单的应用范围弹窗也用这棵树）；候选终端过滤在没有任何终端装该产品时被跳过。

**新代码不照抄**：几处范围校验有越权漏洞；一处拼查询条件的写法在所辖分组为空时报错；另一处把终端上报的状态值直接拼进查询，有注入风险；私有的重建缓存函数有三个缺陷（组上没关联时写进错误值、把所有产品的版本都换掉导致代理中心删掉其他产品的下发记录、不改企业级版本）；一处读缓存用错了命令类型，取不到数据；通用概览取终端总数时漏传了账号级别，复用到进程管控概览页时要补上，筛选也不走字符串拼接；策略中心改应用范围时对保留下来的组不清下发记录，公共的「重建组缓存」函数对每个组都清。

**知会**：终端视角越权（所有子产品都受影响，本次不处理）；菜单授权只看开始时间不看过期；分组树上的继承开关后端没有二次认证；策略中心「应用到组」有一个前端分支不弹二次认证；国产库上升级插默认策略的覆盖从没生效过；一个删终端入口调的存储过程不存在；主菜单的副账号判断在某种部署环境下不执行，本设计在模板和前端里自己判断主账号、不依赖它；101 上有几百行应用范围记录指向已不存在的策略，新代码要容忍；操作日志里「进程管控-概览」的功能码和道系统的一个导出共用；升级时补默认策略的现有写法是「有一条关联就整体跳过、一条没有就给所有组补」，用户换过策略再升级会多挂一条默认策略，进程管控按组判断、不照抄。

## 13. 二期留档

- **终端视角**：和普通页面是同一个单页应用，网址带终端编号。可照病毒查杀的结构做概览、策略、审计日志、进程四个子页。两个前置问题：终端视角的菜单按数组下标隐藏，中间插新菜单会错位，要先改成按类型查找；道系统已有一个叫「进程管控」的子页，重名要定。入口校验有越权漏洞，二期新接口要自带范围校验。
- **按终端挂名单**：一期报文已经白黑共用一个类型，组层和终端层同时有名单时终端按通用规则只用终端层的，客户端不用加规则。二期要做「应用到终端」弹窗和两个接口，先修「删终端策略会删掉整份缓存」「批量分配数组没重置」两个坑，还要把策略中心「从终端缓存里去掉某产品」改成按「产品 + 类型」去掉，否则取消终端的进程策略会把终端级名单一起删掉。需求里改成「只挂组」的三处要改回去；概览名单列恢复「分配」来源。
- 还要定：同类型能否覆盖（组 W1、终端 W2）、顺序反过来谁优先、换组时终端单独的名单是否保留。
