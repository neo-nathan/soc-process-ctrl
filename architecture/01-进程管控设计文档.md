## 1. 范围与名词

### 1.1 一期做什么、不做什么

| 做 | 不做（一期） |
|---|---|
| Linux 终端的进程策略（关闭 / 学习 / 审计 / 拦截） | Windows 终端（结构上预留） |

| 白名单、黑名单的增删改、发布、应用范围（只能选组）、删除 | 级联（上下级中心同步进程管控策略 / 名单） |
| 审计日志查询、从日志加白 / 加黑 | 导出（demo 里没有） |
| 全局白名单：中心部署文件、通过策略告诉终端去哪下载 | 全局白名单的上传入口（随安装包、升级包手动打包） |
| 权限：主账号 / 副账号 / 组管理员 | 终端视角（二期，15.1）；名单按终端挂（二期，15.2）；`procrtl` 开关按钮；首页、大屏、报告 |

### 1.2 名词（大白话）

| 名词 | 意思 |
|---|---|
| 进程策略 | 告诉终端「进程管控开不开、用什么模式」的配置。总开关 + 三选一模式 |
| 学习模式 | 终端采集本机**运行过的进程**（文件路径 + 文件哈希）和**安装包**，报给中心，不判断、不拦截。不是扫全盘的可执行文件。协议里叫「采集」（`auditmode=1`） |
| 审计模式 | 终端按名单判断，不合规的进程**放行但记日志**（可选弹框提示用户） |
| 拦截模式 | 终端按名单判断，不合规的进程**拦住并记日志**（可选弹框提示用户） |
| 进程规则 | 「进程路径 + 文件哈希」两项都相同才算同一条。哈希就是文件的「指纹」，全链路用小写（K14） |
| 进程原始数据 | 学习模式下终端上报的原样数据（需求用语）：运行过的进程、安装包。入库时按「终端 + 路径 + 哈希」去重，每终端每程序只留一行（5.5） |
| 进程记录 | 进程原始数据跨终端聚合去重后的结果（需求用语）：同一「路径 + 哈希」在多少台终端出现过。展示在「进程管理」页，聚合用 SQL 查询做（8.4） |
| 白名单 / 黑名单 | 允许 / 禁止运行的进程规则清单。挂白名单时，不在清单里的算违规；挂黑名单时，在清单里的算违规 |
| 库文件 | 协议里的叫法：把名单明细写成一个文件、再压成 zip，终端按路径下载 |
| 全局白名单 | 专门团队制作的「可信进程清单」JSON 文件，随 SOC 安装包、升级包部署到中心，页面看不到，终端按策略里给的地址自己下载 |
| 发布 | 把名单当前内容「定稿」。定稿不等于下发；已经有应用范围的名单，定稿后自动下发 |
| 应用范围 | 名单挂在哪些组上（只能选组）。选了范围就会下发 |
| 组级 / 终端级 | 挂在分组上（组里终端都继承）叫组级；单独挂在某台终端上叫终端级，终端级优先。名单只有组级 |
| 心跳 | 终端每隔一段时间（默认 300 秒）主动联系中心一次，顺便问「策略有没有变」 |
| 主账号 / 副账号 | 主账号就是用户名为 `optAdmin` 的账号；其他 level 8 账号都算副账号（系统里没有「副账号」字段，只能比用户名） |
| 组管理员 | level 10 账号，只能管创建时勾选的分组 |
| `procrtl` 命令 | 远程立即打开 / 关闭终端上的进程管控，和病毒查杀的「文件监控开关」是同一类，和策略是两件事（3.4） |

## 2. 总体架构

### 2.1 组件关系

```
浏览器（public/esm，jQuery）
  ├ 左侧菜单「进程管控」：概览（页签：概览 / 日志 / 策略）、进程管理、白名单、黑名单
  └ 策略中心：产品下拉里多一个「进程管控」（只有 Linux）
        │  AJAX，先过 ACL 网关（AclHelper，没登记的接口一律拒绝）
        ▼
PHP 5.6 + Yaf（esmCenter/）
  ├ 新增 Procmanager（概览 / 日志 / 进程管理）、Procbwlist（名单）
  └ 复用 Policycenter（策略中心），加「进程管控专用」的权限和条件判断
        │
        ├─ MySQL RS_ESM_LOG：POLICY / POLICYOBJECT / RPW_* / EPSTATE
        ├─ Redis：企业级 hash heid_<eid>（字段 p_global 全网、pgl_<组号> Linux 组、pgw_<组号> Windows 组）
        │         终端级 hash hep_<eid><sguid>（字段 g_info 所在组、p_info 终端级策略、p_ver 版本号）
        │         下发记录 hash hpgl_<eid>_<产品>_<组号>（字段 sguid → 已拉到的版本）（config/const.php:41-79）
        └─ 文件目录：名单库 zip、全局白名单（终端按相对路径下载）
        ▲
终端接入层 Api/（PHP）
  ├ 心跳：版本不一致就整包下发三层策略（消息类型 2003）
  └ 终端上报（消息类型 2002）→ 原样塞进 Redis 队列
        ▲                          │
Linux 终端（进程管控模块）          ▼
                         Java backprogram_new（crontab 拉起）
                           ├ MsgService：消费队列，按「logtype = 表名」通用入库
                           └ DelLogData：每天 01:00 按 LOG_CLEAN 清日志
```

### 2.2 六条数据流

| # | 流向 | 走哪条路 | 触发 |

### 3.4 `procrtl` 远程开关命令（和进程策略是两件事）

- **一期处理**：后端命令保留，不改；页面不放按钮（产品 10-14 的答复）；概览页的「策略模式」列显示终端上报的**实际**状态，被远程关掉的终端会显示「未开启」。
- 待客户端确认：终端用哪个 EPSTATE 键上报这个开关状态。101 上已经有一个 `proctrl` 键（值 0 / 1，注意拼写和命令 `procrtl` 不同），很可能就是它（5.7、P8）。

其他要点：
- 101 上 `POLICYTYPE`、`STATUS` 两列已存在，但**默认值是 NULL，现有 27 行全是 NULL**（rpw.sql 注释里写的「0 默认值」和实际不符，E7）。「普通策略」一律写成 `IFNULL(POLICYTYPE,0)=0`。
- 名单行的 `PTYPE` 固定为 1，所以现有「按 PTYPE=0 取默认策略」的查询（model:199、844、1172）不会误取到名单。
- **报文 `policytype` 用 0 的排查**（101 实测：现有 27 行策略的报文 `policytype` 都从 1 开始，0 没有先例）：
  - 进程管控会走的路径只做 `==` 比较，没有把 0 当空值：策略中心保存（ctl:536、577）、缓存替换（ctl:448、641、1457）、继承开关（`controllers/Group.php:281`）。级联接口（`modules/Apisoc/controllers/Apiset.php:275、342`）也一样，不过一期不支持级联。终端接入层 `Api/` 不读 `policytype`。

- **全网缓存 `p_global` 不能放 PROCM 的项**：model:526（主副标题、资产登记）和 `models/BaseDA/Edr.php:65`（EDR）会遍历 `p_global`，**只按 `policytype` 是 2 或 3 就整项替换，不看产品**。PROCM 的进程策略只挂组和终端、名单只挂组，都不进 `p_global`，现在不冲突；新代码也不要往 `p_global` 里放 PROCM 的项。所以 PROCM **没有全网级**，终端实际只收到组级和终端级两层。

### 5.3 `POLICYOBJECT`：挂在哪里

- `OBJTYPE=1` 是组，`OBJID` 是组 ID；`OBJTYPE=2` 是终端，`OBJID` 是终端 SGUID（终端唯一编号）。101 已核实。
- **进程策略**：每个组 / 终端最多一条（沿用现有「先删同产品同系统的旧关联，再写新关联」，加上「只看普通策略」的条件）。组上没有用户策略时挂默认策略。
- **名单**：只挂组，不挂终端（K13）。每个组最多一条名单关联（白、黑合计）。挂新名单时先删掉这个组上 `POLICYTYPE IN (2,3)` 的旧关联，**自动替换，不弹确认**（K11）。组上没有名单就没有关联行，不挂默认名单。
- **终端实际生效的进程策略** = 终端级 > 所在组的组级（现有机制，终端自己合并；通用规则还有「全网级」一层，PROCM 不进 `p_global`，用不上，见 5.2）。
- **终端实际生效的名单** = 所在组的名单，没有就是没有（K13，7.10）。中心在概览页按同样规则显示。
- **继承**：
  - 组勾了「继承」（`GROUPINFO.ISINHERIT=1`）的，在应用范围弹窗里勾父组会连带勾上子组，每个子组各写一行（和策略中心 `strategy/tree.js:276-315` 一样）。
  - 新建子组时，现有代码把父组的关联行（包括名单）整体复制一份（`models/BaseDA/Policy.php:681-705`），新子组自动继承父组的名单。
  - 策略中心分组树上的「开启继承父组策略」开关（`Group/pOpenClose`，`controllers/Group.php:239-303`）按「产品 + 系统」取父组的**一条**关联（`getRow`）。加上 6.4 的条件后，它对 PROCM **只同步进程策略，不同步名单**；名单只在应用范围弹窗里勾选时跟随继承。不加条件的话，父组同时挂了进程策略和名单时，可能取到名单行，把子组的进程策略换成名单。
- **换组**：现有逻辑只改终端的组号和版本号，组级策略和名单自然换成新组的；单独分配给终端的进程策略保持不变（`models/BaseDA/Group.php:294-378`，B4 已定）。

### 5.4 名单进程表 `RPW_WPROC` / `RPW_BPROC`

一行 = 名单里的一条进程规则。`BWID` 指向 `POLICY.PID`（名单行）。

| `STATUS` | 含义 | 页面标签 |
|---|---|---|
| 0 | 已确认（在已发布版本里） | 无 |
| 1 | 新增（上次发布之后加的，还没发布） | 「新增」 |
| 2 | 待移除（在已发布版本里，已标记移除，还没发布） | 「移除」（删除线） |

**规则唯一键** = `ALGO` + 小写 `FILEHASH` + `PROCPATH`（Linux 路径区分大小写，原样比较）。同名不同路径、同路径不同哈希、同哈希不同路径，都是不同的规则（demo「白名单进程列表」提示原文的口径）。

**哈希全链路小写（K14，产品 10-14 答复）**：名单进程表、库文件（7.7）、审计日志、终端比较都用小写十六进制。手工添加、从进程管理页和审计日志页加白加黑，中心写名单进程表前一律 `strtolower()`。读采集表不加 `LOWER()`：`FILEHASH` 列是 `utf8_general_ci`（101 核实），比较和分组本来就不分大小写，客户端没改小写之前也能对上（101 核实客户端现在上报的是大写，如 `A019E20B…`，要改成小写，P8）。

数量口径（名单列表的「进程数 base +N -M」）：
- base = `STATUS IN (0,2)` 的行数（已发布版本里有多少条）
- +N = `STATUS=1` 的行数；-M = `STATUS=2` 的行数
- 发布后的进程数 = base + N − M

名单规模估算：规则来自学习数据，一台服务器几十到几百个程序，一张名单覆盖一类服务器，通常几百到几千条；按每条 100 字节算，库文件 JSON 几十 KB 到几百 KB，压成 zip 更小，终端一次下载没有压力。

### 5.5 学习数据表

**定位**（产品 10-14 答复，审查 H2、H4，方案 A）：终端上报的是「进程原始数据」（运行过的进程、安装包），表里**每终端每程序只留一行**，靠唯一键去重；「进程记录」（跨终端聚合）不另建表、不写 Java 聚合程序，进程管理页查询时用 SQL `GROUP BY` 现算。

- `RPW_EXECFILEINFO`：唯一键 `(SGUID, FILEHASH, ALGO, PROCPATH)` **保留**，同一终端同一程序只留一行，再次上报就更新 `TIME`（客户端带 `dwith=2`，10.2）。
- `RPW_PACKAGEINFO`：唯一键 `(SGUID, PACKAGENAME)`，同理。
- 这两张表是「终端上运行过什么、装过什么」的清单，不是日志：**不登记到 `LOG_CLEAN`，删除终端、卸载终端时都不清**（产品 10-14 答复，C6 改；v0.8 审查 H2 提的「删除时清」不做）。
  - 所以终端删除走的存储过程 `rssp_del_logdata`（`Ep/removeep` → `models/BaseDA/Ep.php:128-140`；Java 定时清理过期终端 `CleanClientService.java:76`）**不用改**。
  - 已删终端（`EPINFO` 里已经没有这一行）、已卸载终端（`EPINFO.UNSET=1`，2005 消息只改这个标志，`Api/Api.php:1122-1135`）的学习数据留在表里，页面查询一律 `JOIN EPINFO ... AND UNSET=0`，不显示它们；进程管理页的「终端数」和「进程所属终端」弹窗（8.4）也不算它们。
  - 代价：表只增不减。按下面的估算，百台规模几万行，可以接受；以后终端频繁增删、表变大了再考虑定期清理（二期）。
- 审计日志表 `RPW_PROCESSAUDITINFO` 是日志，登记 `LOG_CLEAN`、按 61 天自动清理（5.8 第 8 条）；删除终端时也不另外清，到期自然删掉。日志页按范围先取终端（8.2，照 `XAVLog::getSguids`，全网、分组都只取 `UNSET=0` 的终端，`models/BaseDA/XAVLog.php:57-142`），已删、已卸载终端的日志不显示，和病毒查杀日志一致。
- 数据量估算：一台 Linux 服务器运行过的程序通常几十到几百个，100 台终端也就几万行，`GROUP BY` 现算够用；超过千台再考虑定时汇总表（二期）。
- `EXECTYPE`（101 上全是 0）、`EXECACTION`（101 上全是 NULL）的含义，以及脚本算不算「进程」，一并问客户端（P8）。一期不处理「文件删除」动作：学习数据不清（终端删除时也不清，C6），程序卸载后它的记录会一直留着。
- 进程管理页的聚合 SQL（示意，实际要分页、加筛选）：

```sql
-- 跨终端按「路径 + 哈希 + 算法」聚合，只看 Linux 终端
SELECT f.PROCPATH, f.FILEHASH, f.ALGO,
       COUNT(DISTINCT f.SGUID) AS EPNUM,          -- 终端数
       MAX(f.TIME)             AS LASTTIME
FROM RPW_EXECFILEINFO f
JOIN EPINFO e ON e.SGUID = f.SGUID AND e.UNSET = 0 AND e.SYSTYPE LIKE 'linux%'
GROUP BY f.PROCPATH, f.FILEHASH, f.ALGO;
-- FILEHASH 列是 utf8_general_ci：大写、小写的同一个哈希会分到同一组，不用 LOWER()（K14）；
--   不加 LOWER() 才能用上 5.8 第 7 条的 (PROCPATH(255), FILEHASH) 索引
-- PROCPATH 列改成 utf8_bin 后区分大小写：/opt/App 和 /opt/app 是两条（5.8 第 2 条）
-- 返回给页面、写进名单进程表时，PHP 再 strtolower() 一次哈希
-- 白名单个数 / 黑名单个数：只对当前页的几十条，再按同一个规则键去 RPW_WPROC / RPW_BPROC
-- 数 COUNT(DISTINCT BWID)，只数 STATUS IN (0,1)；不要对整表做关联子查询
```

## 6. 进程策略

### 6.1 策略内容（按协议，加暂定的 `<gwl>`）

协议（`others/policy/policy.md`）规定的进程策略体，加上本文暂定的全局白名单节点 `<gwl>`（P5 已答复：节点名还没定，暂用 `gwl`）：

```xml
<root>
  <procaudit>
    <enable>1</enable>        <!-- 总开关：1 开启，0 关闭 -->
    <auditmode>1</auditmode>  <!-- 管控模式：1 采集（页面叫「学习」），2 审计，3 拦截 -->
    <notify>1</notify>        <!-- 弹框提示用户：1 提示，0 不提示。审计时提示告警，拦截时提示拦截 -->
    <uptimer>360</uptimer>    <!-- 上报间隔，单位秒（协议叫「告警间隔」，是同一个意思） -->
    <gwl>                     <!-- 暂定：全局白名单文件说明，字段同 <lib>（7.7），中心自动填写，页面不展示 -->
      <name></name>           <!-- 文件名 -->
      <dpath></dpath>         <!-- 下载相对路径 -->
      <md5></md5>             <!-- 文件 md5 -->
      <version></version>     <!-- 文件版本 -->
    </gwl>
  </procaudit>
</root>
```

数据库 `POLICYJSON` 里存 JSON，下发时由现有代码转成上面的 XML（`lib/Util/XMLProcess.php:11-21`，`@value` 转成标签里的文本，`Array2XML` 输出带缩进）：

```json
[{"productid":"2DA19BD4-5E8D-4397-B233-D9F95CD29DB3","policytype":"0",
  "policymaincontent":"<base64 后的下面这段>"}]

{"root":{"procaudit":{
  "enable":{"@value":1},"auditmode":{"@value":1},"notify":{"@value":1},"uptimer":{"@value":360},
  "gwl":{"name":{"@value":"<文件名>"},"dpath":{"@value":"<相对路径>"},"md5":{"@value":"<md5>"},"version":{"@value":"<版本>"}}
}}}
```

- 中心没有部署全局白名单文件时，不写 `<gwl>` 节点。
- `<gwl>` 由中心在保存进程策略、安装 / 升级后处理时自动写入（7.8）；页面表单里没有这几项，保存时后端要把它补上，不能被前端提交的内容覆盖掉。

demo 和协议的对应（P6、P7 已答复）：

| 协议字段 | demo「策略详情」 | 结论 |
|---|---|---|
| `enable` | 「开启进程管控」总开关 | 一致 |
| `auditmode` | 管控模式三选一：学习 / 审计 / 拦截 | 叫法不同（采集 = 学习），取值 1/2/3 |
| `notify` | 审计卡片里「开启告警提示用户」、拦截卡片里「开启拦截提示用户」 | **同一个开关**，demo 只是按模式分组显示。页面照 demo 画两处，两处绑定同一个 `notify` 值；照 demo，只有当前选中的模式卡片里那个能点，其他置灰；切换模式时勾选状态跟着走。学习模式没有这个选项，`notify` 原值照存，终端在学习模式下不用它 |
| `uptimer` | 「上报间隔：客户端每 360 秒上报一次进程信息」 | **同一个意思，以 demo 为准**：页面叫「上报间隔」，默认 360 秒。取值范围 demo 没写（输入框没有上下限），本文暂定 60 到 86400 秒的整数，前后端都要校验（P14）。学习模式下它是「每隔多久报一次进程原始数据」还是「攒多久批量报一次」，和「按事件报还是周期快照」一起问客户端（P8） |
| `gwl`（暂定） | 页面不展示 | 中心自动填写（7.8） |

## 7. 黑白名单

白名单和黑名单逻辑完全一样，下文以白名单为例。区别只有：`POLICYTYPE` 为 3、进程表 `RPW_BPROC`、`<lib>` 的 `type` 为 2、终端判定方向相反（7.9）。报文 `policytype` 两者都是 `"2"`。

### 7.1 发布状态

**由数据推导**。「发布过」= `POLICYJSON` 不是 `[]`。

| 发布过？ | 名单进程表的情况 | 发布状态 | `STATUS` 缓存 |
|---|---|---|---|
| 否 | 一行都没有 | `--`（灰） | 0 |
| 否 | 有行（只可能是 `STATUS=1`） | 待发布（蓝） | 1 |
| 是 | 没有 `STATUS` 为 1 或 2 的行 | 已发布（绿） | 2 |
| 是 | 有 `STATUS` 为 1 或 2 的行 | 有变更（橙） | 3 |

每次增、删、恢复进程，以及发布，都在同一个事务里调用 `refreshListStatus($pid)` 重算并写回 `STATUS`。

### 7.2 按钮规则（需求表格 + demo）

| 发布状态 | 发布 | 应用到组 | 删除 |
|---|---|---|---|
| `--` | 灰：空名单不能发布 | 灰：先添加进程并发布 | 可 |
| 待发布 | 可：只定稿 | 灰：先发布 | 可 |
| 已发布 | 灰：没有变更 | 可：选完 / 改完自动下发 | 可 |
| 有变更 | 可（发布后进程数必须 > 0）：没应用时只定稿；已应用时定稿并自动下发 | 灰：先发布 | 可 |

前端置灰只是体验，**后端每个接口都按同样的规则再校验一遍**。

**不设「重新下发」按钮**（产品 10-14 答复，v0.8 审查 H3 的建议不采纳）：下发没成功不用管理员补救，终端下次心跳会自己重新拉，见 7.4 末尾「下发失败怎么办」。

### 7.3 名单里的进程怎么增删

| 操作 | 条件 | 数据变化 |
|---|---|---|
| 手动添加 | 路径校验按名单的系统类型分支写（一期只有 Linux：以 `/` 开头且最后一段不为空；Windows 二期再补盘符规则，不要写死）；哈希是 32 位（MD5，`ALGO=0`）或 64 位（SHA256，`ALGO=8`）十六进制，统一转小写（K14）；进程名取路径最后一段 | 插入 `STATUS=1` |
| 添加时撞上已有规则 | 规则键相同 | 已有的是 0/1：提示「不用重复添加」；已有的是 2：提示「已被标记移除，点恢复即可」 |
| 移除「新增」进程 | — | 直接删除这一行（还没发布过） |
| 移除普通进程 | **移除后「已发布 − 待移除 + 新增」必须 ≥ 1**，否则当场拦住并提示「至少保留 1 个进程；要清掉这条名单请直接删除它」 | `STATUS` 0 → 2，写 `UPDATEUSER`、`UPDATETIME`（页面悬停显示「某某 于 某时间 标记移除」） |
| 恢复 | 只对待移除的 | `STATUS` 2 → 0，清空 `UPDATEUSER`、`UPDATETIME` |
| 从进程管理 / 日志批量加入 | 见 8.2、8.4 | 不存在：插入 1；存在且为 2：改回 0；存在且为 0/1：跳过，计入「已存在」 |

「至少保留 1 个」只对**发布过**的名单生效；没发布过的名单把进程删光，状态回到 `--`，这是允许的。

**加锁**（v0.8 审查 M10）：上表所有操作，和发布（7.4）、改应用范围（7.5）、删除（7.6）一样，事务开头先 `SELECT ... FROM POLICY WHERE PID=? FOR UPDATE` 锁住名单行，再改数据、重算 `STATUS`。这样同一条名单上的写操作一个接一个执行；锁到之后发现名单已被删掉（查不到行），返回「名单不存在或已删除」。批量加入多个名单时，按 `PID` 从小到大依次加锁，避免两个请求互相等待（死锁）。

### 7.4 发布

```
publishList(pid)：
  1. 开事务，锁住名单行（SELECT ... FOR UPDATE）
  2. 校验：状态是「待发布」或「有变更」，且发布后进程数 = base + N − M > 0（兜底防并发）
  3. 名单进程表（RPW_WPROC / RPW_BPROC）：DELETE STATUS=2 的行；UPDATE STATUS=1 → 0
  4. 生成新版本号 version（格式待客户端定，P3；暂照 MD5 专项库用 time()，即 Unix 秒数，天然递增）
  5. 用 STATUS=0 的全部行生成库文件（内容格式待客户端定，P2），压成 zip
     （照 MD5 专项库 Enppackages.php:2300-2310 的写法：调中心自带的 7za 命令压缩（Executor::executeSafe），
      先写临时文件再改名，避免终端下到半个文件；压缩失败就回滚事务，返回「生成库文件失败」）
  6. 计算 zip 的 md5（md5_file；专项库先例转成了大写，大小写待客户端定，P3）
  7. UPDATE POLICY SET POLICYJSON = <lib> 说明（7.7）, POLICYVER = version, STATUS = 2（已发布，这是 POLICY.STATUS，和第 3 步的进程行 STATUS 不是一回事）, UPDATETIME, UPDATEUSER
  8. 提交事务；提交失败就回滚，并删掉第 5 步刚生成的 zip（不留残留文件）
  9. 如果这条名单有应用范围：调 rebuildListGroups(这条名单当前关联的全部组)（见下）
 10. 清理旧 zip：在 ruc/procm/lib/ 下只看文件名前缀等于「本名单 PGUID + _」的 zip，
     按文件名里的版本号从大到小排，保留最大的 2 个（给正在下载上一版的终端留余地），其余删掉；
     按 PGUID 前缀过滤，不会误删别的名单的文件；不需要数据库另记「上一版版本号」
```

**`rebuildListGroups(组列表)`：重建名单所在组的缓存**（v0.8 审查 M10 和第 4 节第 3 条）。名单的三个写入口——发布（本节第 9 步）、改应用范围（7.5）、删除（7.6）——都在**事务提交之后**调这一个函数，不各写一份：
- 对列表里每个组：从数据库重建组缓存（照 ctl:906-924 `updateRedisGroupVal`，6.4）、改组内终端的版本号、清掉这个组的 PROCM 下发记录 `hpgl_<eid>_<PROCM>_<组号>`（照 `editPolicy` 改策略内容时的做法，ctl:614；「已下发」只数 `hpgl_` 里的终端、不比版本，不清的话旧版本的记录会被当成已下发）。
- 只读数据库、只写 Redis，不改数据库，所以**可以反复调用**，结果一样（幂等）。

**下发失败怎么办：不用管理员补救，终端下次心跳自己重新拉**（产品 10-14 答复；v0.9 核实源码和 101）。不设「重新下发」按钮和接口。
- **心跳机制（源码）**：终端每次心跳带上自己手里的策略版本号 `pstamp`，中心拿它和 Redis 里这台终端的版本号 `p_ver` 比，**不一样就把三层策略整包发下去**（`Api/Ipolicy/Policy.class.php:174-186` `getAllPolicy`），并在响应头里带上中心的版本号（`Api/Api.php:197`）。终端没收到、没处理完，手里的版本号就还是旧的，下次心跳再比还是不一样，就再发一次，直到对上为止。中心不需要知道终端有没有收到。
- **101 实测（2026-10-14）**：离线 4 到 24 天的终端，Redis 里的 `p_ver` 仍是最新的版本号（和在线终端一样），中心记的版本号不会过期，它们上线后第一次心跳就会整包拉新策略；当天上过线的一台 Windows 终端，`hpgw_` 里记的「已拉到的版本」和组缓存当前版本一致。Redis 开了快照持久化（`save 900 1` / `300 10` / `60 5000`，`appendonly no`），重启后缓存还在（快照之间的最后几分钟改动可能丢，这是现有机制，所有产品一样）。
- **中心写缓存这一步本身失败的情况**：中心的 Redis 封装（`lib/Store/Redis.php:35-45`）出任何错都直接记日志、输出「Redis异常，请联系管理员」并结束请求，没有「写库成功、写缓存失败、返回失败」这种中间结果；而且每个请求进来先过 ACL 网关，网关也读 Redis，Redis 不可用时请求在改数据库之前就失败了。只剩一个很小的窗口：事务刚提交、正在重建缓存时 Redis 恰好断开，这时数据库是新的、缓存是旧的，终端比对版本号发现不了变化。这是策略中心所有产品共有的情况（`editPolicy` 也是先改库再写 Redis），进程管控不单独做补救。真遇到了：
  - 发生在发布、改应用范围时：原样再提交一次这条名单的应用范围（7.5 规定提交后对提交的全部组都重建，差集为空也重建）。
  - 发生在删除时：名单已经删了，没法再对它操作；原来那几个组的缓存里还留着它，直到这些组下次被重建（任意名单的应用范围提交到这些组，或升级后处理全量重建）。请求在重建那一步就结束了，第 5 步删 zip 也没执行，终端照旧能下载、按旧名单工作，不会出错。极少见，接受。

### 7.5 应用范围（只能应用到组，复用策略中心「应用到组」弹窗）

**规则**
- **名单只能应用到组，不能单独应用到终端**（K13，产品 10-14 确认；需求第 39、46、50 行已改）。demo 里白名单 / 黑名单列表的「应用到终端」按钮暂时保留，用来演示区别，**本期不实现**。
- **只有「已发布」状态能改**（需求拍板第 1、2 条）。
- 提交勾选的全部组，后端在一个事务里（先锁名单行，7.3）算差集：
  - 新加的组：先删掉这个组上已有的名单关联（`POLICYTYPE IN (2,3)`），再写本名单的关联（**自动替换**，不弹确认，K11）；
  - 去掉的组：删掉关联。
- 提交事务后，对**提交的全部组 + 去掉的组**调 `rebuildListGroups`（7.4）：重建组缓存、改组内终端版本号、清 PROCM 的组下发记录 `hpgl_*`，让「已下发」状态重新统计。保留下来的组也重建（多几个组、开销很小），这样差集为空时原样再提交一次，也能把缓存重建一遍（7.4 末尾说的极端情况）。
- 「应用范围：N 个组 M 台终端」：N = 关联的组数，M = 这些组里装了 PROCM 的 Linux 终端数（demo 原文：「已下发到这些终端」）。
- **新建子组自动带上父组的名单**：新建组时现有逻辑会把父组的全部 `POLICYOBJECT` 关联和组缓存复制一份给子组（`models/BaseDA/Policy.php:675-705` `addNewDefaultPolicy`），名单关联也在其中。这是预期行为，不另写代码；但 6.4 给现有 SQL 加「只看普通策略」条件时，**这一处不能加**，否则子组带不上名单。复制不会写子组的 `hpgl_` 下发记录，「已下发」从 0 开始数，符合实际。

### 7.6 删除名单

- 任何状态都能删。有应用范围时提示「该名单已应用到 N 个组、M 台终端。删除后，这些终端下次拉取策略时会清掉本地名单（在线终端默认 5 分钟内，离线终端上线后）」（需求第 86 行的口径）。
- 执行（v0.8 审查 M10 改了顺序，和 7.4「先提交事务，再重建缓存」一致）：
  1. 开事务，锁住名单行（7.3）；记下它关联的组列表；
  2. 同一个事务里：删除关联行 → 删除名单进程表（`RPW_WPROC` 或 `RPW_BPROC`）里本名单的行 → 删除 `POLICY` 名单行；
  3. 提交事务；失败就回滚，什么都没变；
  4. 对第 1 步记下的组调 `rebuildListGroups`（7.4），组内终端下次心跳拿到没有名单的策略；
  5. 删除这条名单的全部 zip（文件名前缀是本名单 PGUID）。删文件失败只记日志，不影响结果：文件名带 PGUID，不会被别的名单用到。
- 为什么不能先重建缓存再删库（v0.8 的顺序）：如果后面删库失败，缓存里已经没有这个名单、数据库里还有，两边对不上，而且下一次任何重建都会把名单又加回来，管理员看到的结果反复变化。
- **「下发清除」的真实含义**：中心没有「删除名单」指令。终端下次拉到的策略里不再有这个名单项，就清掉本地名单（P9）。名单只挂组，删除后组内终端就是「没有名单」（B5）。

### 7.7 下发格式：`<lib>` + 库文件（按协议，方案 B 已确认）

协议（`others/policy/policy.md`）规定的名单策略体：

```xml
<root>
  <procaudit>
    <lib>
      <type>1</type>        <!-- 1 白名单库，2 黑名单库 -->
      <name></name>         <!-- 库文件名称（注意：是 zip 里面那个文件的名称，不是 zip 的名称） -->
      <dpath></dpath>       <!-- 库文件下载相对路径 -->
      <md5></md5>           <!-- 库文件的 md5（压缩后的，即 zip 的 md5） -->
      <version></version>   <!-- 库文件版本 -->
    </lib>
  </procaudit>
</root>
```

数据库里存的 JSON（下发时转成上面的 XML）。报文 `policytype`：白名单、黑名单都是 `"2"`，白黑由 `<lib><type>` 区分（5.2）。下面是白名单的例子：

```json
[{"productid":"2DA19BD4-5E8D-4397-B233-D9F95CD29DB3","policytype":"2",
  "policymaincontent":"<base64 后的下面这段>"}]

{"root":{"procaudit":{"lib":{
  "type":{"@value":1},
  "name":{"@value":"<PGUID>.json"},
  "dpath":{"@value":"ruc/procm/lib/<PGUID>_<version>.zip"},
  "md5":{"@value":"<zip 的 md5，大写>"},
  "version":{"@value":"<version>"}
}}}}
```

**文件约定（P3 暂定，照 MD5 专项库先例 `controllers/Enppackages.php:2300-2352`）**

| 项 | 暂定 |
|---|---|
| 存放目录 | `ruc/procm/lib/`，和软件分发的 `ruc/SoftDown/`、MD5 专项库的 `ruc/esm/hashlib/` 同在中心 web 根目录的 `ruc/` 下（`controllers/Othersoft.php:184`） |
| `dpath` | 相对中心 web 根目录，例如 `ruc/procm/lib/<PGUID>_<version>.zip`。**只由中心生成**，终端照抄下载，不自己拼路径；目录不可列举（101 `/opt/BDFZ/ESM/conf/nginx.conf:151` `autoindex off`，已核实） |
| zip 文件名 | `<PGUID>_<version>.zip`。带版本号，新旧版本并存，正在下载旧版的终端不受影响（7.4 第 10 步按 PGUID 前缀只留版本号最大的 2 个）。`version` 是同样位数的 Unix 秒数，按数字比大小 |
| `name`（zip 里的文件名） | `<PGUID>.json` |
| `version` | 发布时的 `time()`（Unix 秒数，字符串），天然递增；和 `POLICY.POLICYVER` 一致 |
| `md5` | zip 文件的 md5，32 位**大写**十六进制（专项库就是 `strtoupper(md5_file())`）。这是下载校验用的 zip 指纹，大小写按 P3 定；和 K14 说的「进程文件哈希小写」是两回事 |
| 压缩 | 调中心自带的 `7za` 命令（专项库先例） |

**库文件内容（P2 暂定）**：UTF-8 编码（不带 BOM）的 JSON。

```json
{
  "type": 1,
  "version": "1760425800",
  "items": [
    {"path": "/usr/sbin/sshd", "hash": "<32 位小写十六进制>", "algo": 0},
    {"path": "/usr/bin/python3", "hash": "<64 位小写十六进制>", "algo": 8}
  ]
}
```

| 字段 | 含义 |
|---|---|
| `type` | 1 白名单，2 黑名单，同 `<lib><type>` |
| `version` | 同 `<lib><version>`，终端可以用它和策略里的版本对一下 |
| `items[].path` | 进程完整路径，区分大小写，原样比较 |
| `items[].hash` | 文件哈希，小写十六进制（K14）。终端拿本机算出的哈希比较时也按小写比（P2 要和客户端说清） |
| `items[].algo` | 哈希算法，0 MD5、8 SHA256（同 rpw.sql 的 `ALGO` 定义） |

如果专门团队做的全局白名单 JSON 已经有固定格式，库文件直接沿用那个格式更省事，终端只需要一个解析器。等拿到全局白名单的样例后再定。

其他：
- 校验：终端下载后用 `md5` 比对 zip。策略通道整体是加密的（`lib/Util/Common.php:56-82`），md5 值不会被篡改。
- 文件名带 PGUID 和版本，不容易被猜到（MySQL 的 `UUID()` 带时间成分，不算完全随机；需要更严可以加一段随机串）。内容只有路径和哈希，敏感度不高。
- 这样做的好处：名单明细不进策略缓存，名单再大，策略缓存和心跳下发的体积都不变；只有库版本变了，终端才下载 zip。

### 7.8 全局白名单

- 由专门团队制作 JSON 文件，**手动打进 SOC 安装包和升级包**，没有上传入口（产品 10-13、10-14 的答复）。中心只负责部署和下发。
- 部署位置：安装 / 升级时放到固定目录 `ruc/procm/global/`（暂定），和名单库同一套下载方式。目录在 101 `nginx.conf:150` 的 `location ^~ /ruc/` 下，`autoindex off`（`:151`），不用加规则；但 `:154` 对 `/ruc/` 下文本类文件有专门的 `SoftDown` 规则，zip 不受影响，**如果全局白名单最后定成直接下载 JSON、不压 zip（P5），要先核实 JSON 走不走那条规则**。
- 怎么告诉终端：在进程策略的 `<procaudit>` 里加 `<gwl>` 节点（P5 已答复：节点名还没定，暂用 `gwl`），字段同 `<lib>` 去掉 `type`：`name / dpath / md5 / version`（6.1）。
- 文件约定（暂定，跟名单库一致）：压成 zip 下发，`name` 是 zip 里的 JSON 文件名，`md5` 是 zip 的大写 md5，`version` 用专门团队给的版本号（没有就用部署时的 `time()`）。如果客户端希望直接下载 JSON、不压缩，`md5` 就改成 JSON 文件本身的 md5。
- 文件跟着安装包、升级包落到中心目录；之后由一个 PHP 函数 `refreshGlobalWhitelist()`（新写，放在 `models/BaseDA/Backstage.php`）做三件事：
  1. 把文件压成 zip、算 md5；
  2. 把元信息（文件名、相对路径、md5、版本）记到一个配置项；
  3. 刷新所有 PROCM 进程策略行（默认策略和用户策略）里的 `<gwl>` 节点，然后重建**全部组**的组缓存（`heid_*` 里的 `pgl_*`）和**有终端级进程策略的终端**的终端缓存（`hep_*` 里的 `p_info`），改版本号，终端下次心跳拿到新地址。只重建组缓存的话，单独分配了策略的终端拿到的还是旧地址。
  - 中心没部署全局白名单文件时，跳过第 1、2 步，第 3 步照做（策略里不写 `<gwl>`，6.1），这样新装、升级后的组缓存总是和数据库一致。
- 谁调这个函数（v0.8 审查 H1 更正：v0.8 写「照 `Backstage.php` 新装部署」，但 `Backstage.php` 没有新装流程）：
  - **新装**：三份 `activeUser` 的末尾，4 个初始组建完之后调（6.2）。不能放在建组之前：建组时初始组的缓存是照 `config/defaultNewPolicy.php` 写的，没有 `<gwl>`，要等组建完再从数据库重建。这时还没有终端，第 3 步只重建初始组的组缓存。
  - **升级**：`Updateposttask.php` 的 `insertDefaultUserAction` 里，排在补默认策略和关联（6.2 `addDefaultProcmPolicy`）之后调一次；第 3 步顺带完成升级要求的「全部组重建缓存、改版本号」。
- 保存进程策略时（策略中心新建、编辑、复制），后端从配置项读出元信息写进 `<gwl>`，不用前端提交的值（6.1）。
- 优先级：用户黑名单和全局白名单冲突时，**全局白名单优先**（C4 已定）。

| 拦截 | 黑名单 | 其他 | 放行 | 无 |
| 审计 / 拦截 | **没有名单** | — | 不判断（避免误拦整台机器） | 无。中心已下发名单、终端还没用上时，概览页显示不一致感叹号（8.1）；两边都没有名单时不提示（P17 已定） |

- 匹配：按名单条目的算法（MD5 或 SHA256）算文件哈希，「路径 + 哈希」都相同才算命中（P2 一并确认终端支持两种算法）。
- 进程策略里没有 `<gwl>` 节点（中心没部署全局白名单，6.1）时，上表的「全局白名单」按空集算：白名单只看用户白名单，黑名单不做全局白名单豁免（P5 一并告诉客户端）。
- 「在白名单里的进程不产生日志」（demo 原文）和上表一致。
- 拦截只拦新启动的进程，不结束已在运行的（P11）。


### 7.10 名单只挂组：一台终端只会有一个名单

**规则**（需求第 39 行；产品 10-14 确认）：名单只能应用到组，不能单独应用到终端。一台终端的名单就是它所在组的名单，所在组没有就是没有。

**为什么这样就够了**（已核实）：
- 中心下发时不合并，把全网、组、终端三层原样打包发给终端（`Api/Ipolicy/Policy.class.php:155-166` `getPolicyInfo`）。代理中心拿的也是中心的原始缓存，在代理那边自己拼报文（`Api/ApiProxy.php:221-241、341-366`）。
- 组这一层，终端只取自己**直属组**的缓存（`Policy.class.php:68` `getGroupPolicy`，按 `g_info` 取 `pgl_<组号>`），不会叠加上级组。
- 每个组最多挂一个名单（K11）。终端那一层（`p_info`）永远不会有名单项：名单没有「应用到终端」入口，`Policycenter/*` 也拒绝操作名单行（4.2）。
- 所以一台终端最多收到一个名单项，不分白黑、不分先后，直连中心和走代理中心都一样。不需要客户端在白黑名单之间取舍，也不需要中心在下发时过滤。

**多一层保险：白黑共用 `"2"` + 终端级优先**（v0.7，已核实中心侧）：
- 中心把三层拼成一个平铺数组放进 2003 消息（`Api/Common/rsfunc.php:26-64` `constructInfoNew`，顺序是全网、组、终端），每项带 `grouptype` 标明层级：全网 0、组 1、终端 2（全网：`models/BaseDA/Edr.php:56`、model:535；组：ctl:916；终端：ctl:983）。101 全网缓存里现有的那一项（EDR 地址）是 99，来源没查到，PROCM 不进全网缓存，不受影响。
- 101 实测：一台 Windows 终端（所在组 1）的终端级缓存有病毒查杀第 1、2、3 项，组缓存 `pgw_1` 里也有同产品的第 1、2、3 项，两份每次都一起下发。现有产品就是靠终端「同一产品 + 同一类型，取终端级」来保证终端策略优先的。这一步在客户端，中心源码看不到，并入 P9 请客户端书面确认。
- 名单报文统一为 `"2"` 后，即使将来组层和终端层同时出现名单，按这条通用规则也只会生效一个。一期名单不挂终端，用不上这条；二期按终端挂名单时直接可用（15.2）。

**各种情况**

| 情况 | 结果 |
|---|---|
| 终端换组：手动换组 `Group/moveComputer`、删除组时组内终端被挪到根管理组 `Group/delGroup`、自动入组 `Group/autoAGroup` 和 `autoAll`、外部主机同步 `Proindex/host` | 终端直接用新组的名单，新组没有就是没有。这 4 个入口在名单这件事上都不用改（v0.4 的冲突检查全部取消）。换组、删组时「清旧组下发记录」的产品清单要加上 PROCM，那是接入任何新子产品的常规改动，不是名单引起的（S7、14.1） |
| 组换名单（白换黑、换另一个白名单） | 自动替换（K11），组内终端下次心跳换成新名单 |
| 父组、子组挂不同的名单 | 各管各的组内终端，不冲突 |
| 新建子组 | 现有逻辑复制父组的关联行，子组带上父组的名单（5.3） |
| 删除名单、把组移出应用范围 | 组内终端下次拉到的策略里没有名单项，清掉本地名单 |

**个别终端要特殊处理怎么办**（一期的代价）：
- 只是被误拦：在策略中心给这台终端单独分配一个「审计模式」的进程策略，只告警、不拦截，不用挪组。
- 确实要用不同的名单：给它单独建一个组再挪进去。注意终端属于哪个组是所有产品共用的，挪组会连带改变它在其他产品里的组策略。
- 按终端挂名单放到二期（15.2）。

- 按钮：
  - 选中加白、选中加黑：后端接收规则键（路径 + 哈希 + 算法），并校验这些规则确实存在于采集表里。
  - 按条件加白：后端用当前筛选条件重新查询；执行前弹窗显示「将加入 X 条」，确认后执行。不设上限（C8）：按 5.5 的估算，百台规模下聚合后的进程记录是几千到几万条，一次加完可以接受；插入用一条批量 `INSERT`，不要逐条。
  - 没有「按条件加黑」，照 demo。
- 接口：`Procmanager/getProcList`、`getProcReportTerminals`、`getProcInLists`、`Procbwlist/addProcsToLists`，全部 8m。

### 10.2 终端往中心报什么（2002 消息，按推荐暂定，P8）

Java 的通用入库规则（`MsgService.java:303-437`）：`logtype` = 表名；JSON 键 = 表列名小写；`eid / sguid / systype / inserttime / logedate` 由中心自动填（`Api/Api.php:562-568`、`MsgService.java:384-393`）；`dwith` 由终端在消息里指定：0 追加，1 先删该终端旧数据再插入，2 按条件「有就更新」。

表名大小写：Java 写库时把表名统一转成大写（`backprogram_new` 的 `dao/mysql/LogDataDao.java:101、107`），查列名走 `information_schema`。101 的 `lower_case_table_names=0`（表名区分大小写），实际表名是大写的 `RPW_*`。所以 `logtype` 写大写、小写都能入库，本文推荐写成和表名一样的大写。

| logtype（= 表名） | 字段（按 rpw.sql 的列名；另有 `eventtype / eventlevel / eventsource / category / username / description` 6 个通用列，可不填） | 入库方式 |
|---|---|---|
| `RPW_EXECFILEINFO` | time, exectype, execsize, inode, filechangetime, filehash（小写）, algo, procpath, procname（5.8 第 5 条）, execpackage, execaction | 2：Java 的 `dwithWhereMap` 加 `rpw_execfileinfo → eid, sguid, filehash, algo, procpath` |
| `RPW_PACKAGEINFO` | time, packagename, packageversion, maintainer, packageuptime, filecount, ptype | 2：加 `rpw_packageinfo → eid, sguid, packagename` |
| `RPW_PROCESSAUDITINFO` | time, pid, ppid, cmd, procuser, filehash（小写）, algo, procpath, procname, actionreason, procaction | 0：追加 |
| `epstate` | epkey, value（`value2` 本功能不用，5.7） | Java 已固定为「有就更新」 |

**学习数据的上报方式：`dwith=2`（有就更新），这是设计，不是现状**（K9，方案 A）。101 核实（2026-10-14，`RPW_EXECFILEINFO` 15 行，自增 ID 跳号 1、5、16、21…）：客户端现在是追加上报（`dwith=0`），重复行被唯一键挡住，Java 逐条 `catch` 记错误日志（`MsgService.java:437-440`），`TIME` 不更新。**客户端要改成 `dwith=2`**（P8）。

- 注意：`dwith=2` 的表如果没在 `dwithWhereMap` 里登记，Java 默认按 `eid, sguid, uniquevalue` 三列找旧数据（`MsgService.java:420`），RPW 表没有 `UNIQUEVALUE` 列，找不到的列会被直接跳过（`MsgService.java:421-428`），更新条件就只剩「企业 + 终端」，**这台终端的所有学习记录会被改成同一条**。所以上表那两行必须加，而且 Java 要**先于**客户端上线（14.6）。
- 不用 `dwith=1`（先删该终端旧数据再插）：如果客户端是周期全量快照，每 `uptimer` 秒整表删插一遍，自增 ID 很快刷爆、进程管理页的「上报时间」也丢。
- 还要客户端说清（P8）：学习数据是**按进程启动事件报**（启动一次报一条）还是**周期全量快照**（每隔 `uptimer` 秒把当前运行的都报一遍）。两种在 `dwith=2` 下入库结果一样，区别是报文量和「上报时间」的含义。
- 哈希统一小写上报（K14；101 上现在是大写）；`procname` 由终端报，Java 不截取（5.6）。

EPSTATE 键（5.7）：`procaudit`，`value` 填 0 关闭 / 1 学习 / 2 审计 / 3 拦截（rpw.sql 已定，101 已有上报）；`proclib`，`value` 填 0 没有 / 1 白 / 2 黑（rpw.sql 已定），`value2` 不用；远程开关状态：101 上已有的 `proctrl`（0 / 1）是不是它、`procdef` 是什么，问客户端（P8）。

## 15. 二期留档

一期不做，下面是调研结论，供二期参考。

### 15.1 终端视角

- **机制**：终端视角和普通页面是同一个单页应用，区别在网址里带 `&c=<SGUID>`（`core.js:134`）。左侧菜单由 `Epbase/getMenu` 读 `esmCenter/conf/epTab.json` 过滤后返回，按授权、级别、终端已装产品、系统类型决定显隐（`Epbase.php:40-310`）。
- **病毒查杀的做法**：左侧「病毒查杀」下有概览（`Epxav/*`）、策略（`Policycenter/getEpPolicy`）和 5 个日志页（`Xavlog/*` 传 `objtype=2`）。进程管控可以照这个结构：概览、策略、审计日志、进程（这台终端学到的进程）。
- **两个前置问题**：
  - `Epbase.php` 按**数组下标**隐藏菜单（写死了 `[0][3]`、`[1]`~`[10]` 等）。在中间插入新菜单会全部错位，要先改成「按菜单类型查找」。
  - 道系统（LDAO）在「基本信息」下已有一个子页叫「进程管控」（`epTab.json:29-35`），会和新菜单重名（二期再定）。
- **越权**：入口校验不看分组（第 13 节第 11 条），二期的新接口要自带范围校验。
- 二期要回答：子页清单；「进程」子页谁能看；终端视角里的策略页能不能编辑 / 删除终端级策略（病毒查杀允许）；demo 由谁画。


### 15.2 按终端挂名单

一期名单只挂组（K13）。v0.7 起名单报文白黑共用 `"2"`（10-14 讨论过的「办法 3」，已采纳），组层和终端层同时有名单时，终端按「同一产品 + 同一类型，取终端级」的通用规则只用终端层的，客户端不用加特殊规则（7.10）。中心下发时不合并三层（`Api/Ipolicy/Policy.class.php:155-166`），代理中心拿的是原始缓存、自己拼报文（`Api/ApiProxy.php:221-241、341-366`），这条规则对两者都适用。

二期要做的事：名单的「应用到终端」弹窗（截图 19）和 2 个接口；先修第 13 节第 2、3 条（删终端策略会删掉整份 `p_info`、批量分配时数组没重置），否则终端级名单会被误删或串到别的终端；需求第 39、46、50 行改回去；概览「白名单/黑名单」列恢复「分配」。

另外还要定：同类型能否覆盖（组 W1、终端 W2）、顺序反过来时谁优先（10-14 的答复是「终端优先、不分先后」）、换组时终端单独的名单是否保留。这些在 v0.4 第 12 节 P15、P16 讨论过，可作参考。
