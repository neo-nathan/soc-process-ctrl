## 一、这个 skill 要解决什么问题

**目标口径**:发现 **90% 的核心关键问题**,其余交用户拍板。**不追求 0 漏洞**
(2026-07-25 需求方定调)。追求 0 漏洞会掉进无底洞——每堵一个洞就加一个机制,
机制自己又会长出新的失效面。

**唯一真失效**是:**集体偏离 → 全员沉默 → 静默 PASS**。
其余一切只需做到:**发现问题 → 提醒用户 → 用户拍板。**

**前提是"Agent 会偶尔犯错",不是"Agent 是嫌疑犯"。**
主 Agent 是流程核心,要给它编排、委派、裁决、决策、形式审查与验证的权力。
犯错由内审 / 整体审 / 外审三层兜底,**不靠剥夺它的权力来预防**——
那会把自动化退化成手动,得不偿失。

### 砍掉的机制与理由

| 砍掉的 | 理由 |
|---|---|
| **context bundle 冻结**(2340 行 helper + 逐件 hash + `BASELINE_CHANGED`) | 机制自己就是一次事故的成因:I1 第 2 轮因 `CLAUDE.md` 改了 14 行被机械判 `BASELINE_CHANGED`,逼得**回写文件迁就冻结副本**,回写又造出新缺陷。Reviewer 原话:「整改改变了判自己的尺子」。**保留的是"全文供给禁切片"这条原则(成本近 0),砍掉的是 hash 冻结这套机制。** |
| **两本登记簿 + 双人升级闸门 + `anchor_key`/`occurrence_id` schema** | 它防的是"主 Agent 偷偷降级 Reviewer 结论"。而 I1 逐轮记录显示:T1「无一条降级或删除」、T2「无一条降级、删除或升级」、T3「8 条对 8 条全部 kept」「3/3 kept」、T4「4/4 kept」、整体审「核准全 kept,零降级」——**整个 loop 降级次数是 0,实际发生的全是升级**。防的是一个不存在的敌人。替代:降级/删除时**贴出设计原句**(不是坐标),写进 changelog,用户能一眼看出凭什么没的。 |
| **证据链仪式**(候选目录 / `session_nonce` / 证据审 Reviewer / 五步 publish verifier) | 成本极高,而它要防的"数字造假"用一条零成本规则就能覆盖:**报告里每个数字必须附产生它的命令**。 |
| **`state.json`** | 旧文档自己写着"不承担跨崩溃续跑职责"。那它只剩"给 changelog 抄数字"一个用途,直接写 changelog 即可。 |
| **每轮同步 `CurrentStatus.md`** | I1 整体审 6 条 important 里有 3 条是状态页数字对账——纯自造工作量。改成门收尾时更一次。 |

| **拆解门** | 移交给独立的 `/plan-to-task`。拆解跟实现绑在一个循环里时,每次补拆都要重跑全链,才会跑出 5 轮的雪球。 |

### 做减法时踩过的坑(下次照做)

**砍一个机制,必须追到它的全部消费者**——references 文件、判例登记、自检断言、state 字段、
其他 skill 里的引用。只砍主文会让"为旧机制服务的结构"换个形状留下来,复杂度并没有真的降。
(同一个坑在 implement-plan 上踩过三次。)

## 四、改本 skill 的规矩

1. **新增任何机制必须挂靠一次真实事故**,写进第二节或第三节。无事故支撑的不许进。
2. **每次改进同回合必须回答"这次能删掉/合并哪几条"**,答不出要写明理由。
3. **改完先自检、再派独立 Reviewer 复审**——自检不能替代 Reviewer(验证不到"新写的对不对",
   实证:一次自检全绿的瘦身被独立 Reviewer 一轮抓出 4 个 blocker),但**能替**顺手就能抓到的
   自相矛盾:改了一个术语/字段/判据的定义,grep 一下全文还有没有别处在用旧定义;
   改了"必带 XX",prompt 模板里有没有接得住的占位符。
   ⚠️ 反例就是这条规矩本身补上的那次:整改 B1(改 ACTUAL 判据)时没做这步,
   自己新造了 2 处矛盾(旧注释与新规则打架、返回字段没跟上新判据),
   靠用户额外要求"再自检一次"才被抓到——**派 Reviewer 前的自检省的是 Reviewer 的一轮,
   不是 Reviewer 本身**。
4. ⚠️ **但要自设收敛条件**。改治理文档极易滑进"给锤子做锤子"的递归:
   实测某次 4 轮复审 56 条 findings 里只有 29% 与核心相关。
   判据是一句话:**"这条不修,真实任务的结果会有差别吗?"** 答案是否,就不修。
5. 新增任何交付件后跑一遍 `git check-ignore -v <新文件>`,确认没被 `.gitignore` 吞掉
   (旧项目 `.claude/` 是白名单模式,漏补 `!` 行静默漏交付、复发三次;本项目 `.gitignore`
