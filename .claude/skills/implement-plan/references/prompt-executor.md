   ### 7.1 自检——**把自己改的东西 diff 出来,一处一处重新读一遍**

   ```
   # SOC 源码(svn 工作副本;svn 的环境变量和必带参数按全局 svn-creds skill)
   cd /Users/nick/Workspace/ESMCenterST && svn status && svn diff <你改的文件>
   # FILES 给了对照基准的文件改用:diff <对照基准> <当前文件>
   # 本仓库文档
   git status --short -uall && git diff
   # 新建的文件逐个打开重读
   ```

   **对着 diff 逐处问这五句**(不是扫一眼,是真的一处一处过):

   | # | 问自己 | 典型翻车 |
   |---|---|---|
   | 1 | 这次要解决的问题,**真的解决了吗**? | 改了个相邻的地方,原问题还在 |
   | 2 | **同类的地方都改了吗**? | 三处一样的写法只改了被点名的那一处(文档里同一个接口名出现 18 次只改了 15 次) |
   | 3 | **有没有改出新问题**?改动周边的逻辑还成立吗? | 改了公共函数的参数,另一个页面的调用点还按老语义传参 |
   | 4 | **有没有改多**?有没有顺手动了不该动的? | 顺带"优化"了不在本任务范围的代码 |
   | 5 | **写下的文字和实际代码一致吗**? | 注释说的是 A,代码做的是 B |

   > 💡 **最常见的失效不是不会做,是"写完就交、从不看第二遍"。**
   > 很多问题一点都不复杂,重读一遍就能发现——但没人重读。

   ### 7.2 验证——**跑命令,不是"我觉得应该没问题"**

   | # | 必做 | 命令示例 | 判据 |
   |---|---|---|---|
   | 1 | **语法过** | 每个改动的 JS:`node --check <文件>`;改了 PHP:经 ssh 把本地文件从标准输入喂给 101 上的 PHP 5.6(`ssh … '<php 路径> -l' < 本地文件`,**不把文件放到 101 上**);改了文档:按 TASK 完成判据里的 grep 跑一遍 | 全部通过。**语法不过 = 没做完**,不许返回 `done` |
   | 2 | **自己写的自测全绿** | `node <自测目录>/<脚本>.js`(纯逻辑模块;AMD 模块用最小 `define` 替身加载) | 全绿。红的先修好再回;纯页面代码没法在 node 里跑的,如实写 `not_applicable` 和原因 |
   | 3 | **没打破别人的**(改动既有 / 公共文件时必做) | `grep` 出该文件(或你改的函数)在其他页面的全部调用点,逐个确认老用法仍成立 | 列出调用点清单和结论 |
   | 4 | **改动范围就是声称范围** | **动手前**先跑一次 `svn status`(SOC 源码)+ `git status --short -uall`(本仓库),并给其中已是改动状态的文件各记一个 md5;交回前再跑一次 | 新出现的文件 + md5 变了的文件 = 你的实际改动,不该有你没在 `changes` 里报告的。⚠️ 工作区本来就有别的改动(开工从 101 拉的文件、前面 TK 的产物),所以比的是前后之差,不是整个工作区 |

   **返工轮:7.1 的第 1、3 句要对着核准清单逐条过**,并在 `regression_check.how_verified`
   里写明每条**怎么验证的**——不能只写"已修改"。

   ⚠️ **为什么这两件都是硬要求**:旧项目实测有一轮整改,7 条 finding 里 **4 条(57%)
   是前几轮整改自己造出来的**。"改一个问题引入两个"不是偶发,是默认状态。
   而其中相当一部分**语法是过的、测试是绿的**——只有重读 diff 才看得出来。

   主 Agent 会抽查,写了假的比不写更糟。
