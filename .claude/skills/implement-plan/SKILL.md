# implement-plan — 计划实现编排循环

> 设计取舍的来龙去脉见 [RATIONALE.md](RATIONALE.md)(只在要**改本 skill** 时读,日常执行不用读)。
>
> **移植说明**:本 skill 2026-10-21 从 soc-cascade-syslog(Java/Maven 项目)移植,已改成本项目
> 的形状——输入是 `plans/PL-NN` 计划本身(本项目没有 `/plan-to-task` 和 `tasks.md`)、
> 代码在 SOC 源码 svn 工作副本、测试靠 node 脚本和 101 浏览器实测。
> ⚠️ 文中「实测 / 事故 / 实证」引用的 **PL-01 I1 / I2 / W1、T0～T4、L4、F2** 都是**旧项目**
> (esm-data-kafka、soc-cascade-syslog)的事故编号,**与本项目 `plans/PL-01` 无关**,
> 留着是为了说明每条规矩为什么存在。

## 一句话

拿一份**用户已放行的 `plans/PL-NN-*.md`**,逐个子任务派 Executor 改代码 / 文档、派 Tester 独立写并跑验收、
派内审 Reviewer 查问题;全部完成后跑**一轮**整体审看跨子任务衔接;
主 Agent 亲自上传 101、实跑与自检,最后写 IMPL 报告。

**主 Agent 不写生产实现代码、不写验收测试 不写别人的代码**(那是 Executor / Tester 的活),
但**该写自己责任范围内的代码和文档**:自己的工具脚本、检查器、条款覆盖表、核准清单、changelog、IMPL 报告。
**它不碰的是别人写的代码,不是所有代码。**

**引文写法**(S1 用,全文通用):`文档简称 § 章节号`,如 `01 §8.8`、`PL-01 §四 4.3`、`PL-01 TK-2`;

**编码红线**(派活时原样给,完整版以 `CLAUDE.md` 为准):
- 后端 **PHP 5.6.15**,禁用 7.0+ 语法(`??`、标量 / 返回类型声明、`...` 展开等)。本机没有 php,
  语法检查用 101 上的 PHP 5.6:先确认解释器路径,再经 ssh 把本地文件从标准输入喂给它
  (`ssh … '<php 路径> -l' < 本地文件`),**不把文件放到 101 上**;计划写明 PHP 不改的不适用(如 PL-01 开头「PHP 后端：**一行不改**」)。

- 计划写了「不改」的公共文件一律不改;计划允许改的公共文件,要列出它在其他页面的调用点并做回归。

## 主 Agent 的权力(正面写死,不靠"没禁止就是能干")

主 Agent 是本流程的核心。**信任它的判断,允许它犯错**——犯错由内审、整体审、外审三层兜底
(本项目外审是可选的,见 3.3),而不是靠剥夺它的权力来预防。

**有权,不需要请示**:

1. **编排**:决定派谁、派几个、什么顺序、什么档位
2. **裁决**:判断任一 Reviewer 每条 finding 的真伪,**有权 kept / 降级 / 删除 / 升级**。
   唯一条件:**降级或删除时把设计原句那 1~3 行贴出来**(不是贴坐标)
3. **决策**:遇到歧义直接拍板,记一行进 changelog 即可(用户另有指示时从其指示)
4. **形式审查与验证**:跑 `node --check`、跑脚本、数用例、算 md5、比对文件、按计划上传 101、
   只读查库核对结果——**这些主 Agent 亲自做,不外包给 Reviewer**
5. **静态代码审查**:逐行读 Executor/Tester 交回的代码与测试,清理低级错误。
   **主 Agent 必须亲自做,不能全靠 Reviewer 兜底**;查什么、怎么留痕、怎么算通过,
   以 2.3 的「静态审查闸门」为唯一定义,这里不另抄清单
6. **收尾判断**:决定何时收尾、何时叫停、何时不派下一轮

**无权,只剩三条**:

1. 改基线文档(计划 / 设计 / 需求等)——要改就**停下问用户**。
   唯一例外是计划**明确列为某个子任务产出**的文档改动(如 PL-01 TK-1 改设计文档 01):
   那是 Executor 按计划原文做的子任务,照常走 Tester 和内审,**改的范围不许超出计划原文**。
   另一个例外:收尾第一次创建 `implement/` 时,主 Agent 在 `CLAUDE.md` 目录表**只加登记它的那一行**(阶段 4 第 5 步),别处一个字不动
2. **写生产实现代码、写验收测试,或直接改 Executor / Tester 写出来的东西**(理由见下)
3. 把任一角色的原始结论藏起来不给用户看

⚠️ **第 2 条容易被读得过宽,这里说清楚**——它禁的是**"自己生成、自己核准"**,不是"不许写东西":

| 主 Agent **可以**写和改 | 主 Agent **不可以**写和改 |
|---|---|
| 自己的工具脚本(检查器、证据生成、机械核对、计数对账) | 生产实现代码(SOC 源码) |
| 条款覆盖表、核准清单、裁决记录、changelog、IMPL 报告 | 计划级验收(Tester 的脚本和浏览器用例) |
| 自己写的脚本和文档的后续修订 | **Executor / Tester 交回来的代码、文档与测试** |
| 计划里属于开工准备 / 上传 / 收尾性质的机械动作(拉 101 基线、备份、比对 md5、上传) | 计划列给某个子任务的文档改动 |

**为什么不能碰别人的代码**(两条都成立才禁得住):
① 内审 Reviewer 审的 ACTUAL 锚的是子任务,主 Agent 混进去的改动**没有任何人审**;
② 它同时是核准者,改了就等于自己生成、自己放行——旧项目 L4 实测:主 Agent 亲自审自己拆的
4 个子任务,**全部 0 findings、0 返工**(确认偏差,审查退化成形式打勾)。
要改就**派回给原角色改**(走「返工怎么派」),不要自己上手。

⚠️ **这一条管的是"谁放行",不管"谁检查"** —— 它禁的是主 Agent 去改、去核准**别人写的东西**,
**不豁免任何人对自己产物的自检**(S3)。"反正后面有 Reviewer"从来不是不查自己的理由:
旧项目实测 I1 里主 Agent 写的派活脚本把一个字段的语义写错,被内审判成 blocker。
**"自己写的"不等于"不用查的"。**

## 三条硬约束(破了整个流程归零)

| | |
|---|---|
| **S1** | **派活逐字引原文**。给下游的设计要求必须是原句逐字摘录 + 引文写法(见「本项目的现场」,如 `01 §8.8`,不用行号)。主 Agent 的实现提示**另起一段**标明"以下是实现提示,不是设计要求"。派活是最上游,这里歪了下游全部在错框架里工作。 |
| **S2** | **每个角色都拿到完整基线文档**(给路径,自己完整 Read),不给摘要不给切片。发现主 Agent 偏离设计,角色可**熔断上报**(`blocked_questions`:我判不准,停下来问)或**拒绝执行**(`reject_directive`:这指令要我写偏离设计的东西,我不写)。 |
| **S3** | **「自检 + 验证」**<br/>**自检**：把改过的东西 diff 出来一处一处重读，回答「自检问题」。<br/>**验证**：按要求编写验证脚本 跑脚本 命令 测试用例，检查编译是否报错？测试是否通过？数字是否对不上？回答「自检问题」。<br/>**自检问题**：检查是否符合设计方案？是否符合计划？是否已解决已知问题？是否引入新问题？是否改了一处漏其他地方？是否存在逻辑矛盾？是否一致？是否还有其他问题？<br/>**触发时机**: ① 每次 Write｜Edit 任何文件后；② 派 subagent 前；③ 提交结果前，都要进行「自检 + 验证」。<br/>**自检循环**：自检和验证 (Round1) 未通过 -> 修正问题 (Round1) -> 再次自检和验证 (RoundN) -> 修正问题 (RoundN) -> 直到检查不出问题 为止 -> 进入下一步。<br/>**自检和验证铁律**：不自检和验证 不允许进入下一步；自检和验证通过后 才能进入下一步；自检和验证未通过 不允许进入下一步；<br>🛑 **查出红的就不许往下走**:能修的**当场修掉、重跑**;修不掉的**如实把结论降下来**(PASS→FAIL)。**不许带着红项说"做完了",也不许把红项写进"已知边界"糊弄过去**(第 ③ 个时刻管住每一次交出成果——收尾 PASS / FAIL / 中止 / **任何一次交用户拍板**)。 |

🛑 **S3 不因为"后面还有 Reviewer"而豁免——自检和独立审查是两道,不是二选一。**
自检清的是**自己一眼能看见**的低级问题;Reviewer 清的是**自己看不见**的隐蔽问题和自我偏袒。
**Reviewer 一轮成本极高,把它当低级错误的兜底器,等于用最贵的资源做最便宜的事。**

⚠️ **Reviewer 自己也归 S3 管,而且只有第 ③ 个时刻兜得住它**:它的产出是 JSON 报告、不落文件,
所以 `CLAUDE.md` 那条"每次 Write/Edit 任何文件后要自检"**对它永远不触发**——
报告里的坐标错、引文加字、误报,只能靠它交回前自己核一遍(见两份 review 模板的
「交回报告之前」段与 `self_check` 字段)。**报告错了,主 Agent 的裁决必然跟着错。**

> **实证(旧项目 esm-data-kafka PL-01 I2 T0)**:主 Agent 把自己写的 changelog 与设计文档直接交审、**自己一遍没读**,
> 结果跑满 **5 轮**内审(上限是 2 轮),**blocker 几乎全部落在主 Agent 自己写的留痕层**
> (changelog / 设计文档 / `CurrentStatus.md`),**代码与测试连续 5 轮零 blocker**。
> 也就是说:5 轮顶格 Reviewer,绝大部分产能花在替主 Agent 做它自己该做的自检上。
> ⚠️ 只有 Round 2 的一条 blocker 是例外(一处空白字符集的设计歧义,需用户拍板)——
> **那一条恰恰证明 Reviewer 用对地方是有产能的**,更说明不该拿它去清低级错误。

> 修正循环的细则(没过就修、修完重来、PASS 才进下一步)见全局 `CLAUDE.md` 的「自检和验证铁律」,
> 那是环境级规则、对所有角色生效,这里不重复。

### 「自检」和「验证」是两件事(全文通用定义,三个角色都照这个来)

| | **自检** | **验证** |
|---|---|---|
| 怎么做 | **把自己改过的东西 diff 出来,一处一处重新读一遍** | **跑命令**:语法检查、测试脚本、浏览器用例、计数、md5 |
| 谁在判 | **你自己读、自己判** | **机器判**,你只负责如实记录 |
| 能抓到什么 | 逻辑前后矛盾、改了一处漏了另一处、文字与实际不符、改多了改少了、**没真的解决要解决的那个问题** | 语法错、用例红、数字对不上、文件缺失 |
| **抓不到什么** | 跑起来才暴露的问题 | **上面那一整列**——代码能过语法检查、用例能全绿,照样可以自相矛盾、照样可以没解决问题 |

**顺序:先自检,再验证。**自检成本低、能先捞一批;先跑命令再读 diff,
读出问题一改,刚跑的结果就作废了。

🛑 **两者互相替代不了,这是本条最要紧的一句话。**旧项目实测:
- **只有读 diff 才能抓到的**:一处旧注释与刚改的新规则直接打架;
  给 prompt 加了一个槽位、正文却没说要填它——**这两处跑任何命令都是绿的**;
- **只有跑命令才能抓到的**:声称的行数与实际不符(连续三轮都是靠命令抓出来的)。

> ⚠️ 最常见的失效不是"不会做",而是**"写完了就交,没有再看第二遍"**。
> 很多问题一点都不复杂,重读一遍就能发现——但没人重读。
> 所以自检是**硬要求**,不是"有空就做"。

### 派活前自检清单(S3 的第 ② 个时刻,主 Agent 专用)

🛑 **派活前 主 Agent 必须进行一次自检和验证（S3）**

派活的 prompt 不是文件,`git diff` 看不见它,所以自检要照下面这七条走。
**每次派活之前都过一遍,并把勾选结果写进派活那一段**
——只写"已自检"等于没做(这正是 2.3 里判 `self_check` 空话的同一条标准,对主 Agent 一样适用)。
⚠️ **"派活"不只是 2.1/2.2/2.4/3.2 那四个小节**:2.4 的「返工怎么派」、3.3 的整改派发**同样是派活**,
一样要过这七条。

| # | 派出去之前问自己 | 真实翻车(旧项目) |
|---|---|---|
| 1 | 对应的 prompt 模板,**这一轮重新完整 Read 过**吗? | 凭记忆现编 prompt,槽位和措辞都漂了 |
| 2 | **角色名 / 档位 / 文件路径,从头到尾看一遍有没有串行**? | 复制上一个委派块只改了一半:「委派 Executor 时,要求 **Tester** 返回前自检」 |
| 3 | 每条设计要求都带引文写法(`01 §8.8` 一类)且**逐字**?**随机抽 1 条回原文比对** | 标称"逐字"的引文加了原文没有的字(I2 Round 2 blocker B2) |
| 4 | **必带材料逐项点名**——判据不是背清单,而是**对照两样实物**:该派活小节的整行「必带:」+ 模板里的**每个 `<<<` 槽位块**,逐项勾 | I2 首次派活只列了 8 份基线文档,漏掉其余的(S2 违反,当轮补发)。⚠️ 写死枚举会随材料增删失效,所以判据锚在实物上 |

| 7 | 🛑 **ACTUAL 里我自己写的那几份**(changelog / 状态页 / 条款覆盖表 / 工具脚本),**这一轮逐份重读过吗**?里面每个数值和 `文件:行号` 都是**这一轮跑命令重取**的吗? | **本清单事故规模最大的一条**:I2 的 T0 跑满 5 轮内审,blocker 几乎全部落在主 Agent 自己写的留痕层,代码侧连续 5 轮零 blocker。交审**不能代替**重读 |

## 兜底总则

**机械动作失败、判不准、环境不满足、进程崩了 → 停下 → 如实报告 → 交用户拍板。**

⚠️ 作用域:管**机械动作与异常**,**不管"审查发现问题"这种正常业务分支**。以下不适用:

| 情形 | 按哪条走 |
|---|---|
| 内审报 blocker → 返工重审 | 内审上限 2 轮,到限才交用户 |
| 静态审查闸门发现问题 → 发回修 | 同一次交付累计 2 轮,到限才交用户(见 2.3 闸门) |
| 实跑 / 验收红了 | **不停下**,如实记录交本轮 Reviewer 判 |
| 环境没就绪导致实跑失败 | 连续 3 次才交用户;前两次照常重试 |

**"环境未就绪"要有机械判据**,不能主 Agent 说了算:只有**连不上外部环境**
(101 的 ssh / scp 失败、MySQL / Redis 连不上、101 网页打不开、网络错误码)才算环境问题;
**浏览器停在登录页 = 登录态没了,不算重试次数,直接请用户在内置浏览器登录**(安全规则不允许 Agent 输密码)。
**语法错、用例红、页面报错一律算代码问题**,走"实跑红 → 交 Reviewer 判"。

**101 是同事共用的开发环境**,另有三条硬规矩:
- 上传前比对 md5 与基线(计划有上传规则的按计划);**不一致说明同事改过,不许直接覆盖**,
  按阶段 1 第 3 步「中途发现同事又改过」走(拉下来 → 更新拉取基线 → 派原 Executor 合并 → 过 2.3 → 再上传;
  合并后这次上传的比对基准改用新拉取基线的 md5,即计划上传规则里「拉下来合并」之后的那份);
  **新建文件**第一次上传前先确认 101 上没有同名文件,有就停下问用户;
- 测试写真库只限计划允许的范围(如 PL-01 只动 `PL01测试-` 开头的名单),同事已有的数据一条不动;
- 凭据只从 `CLAUDE.local.md` 读,**不写进派活 prompt、changelog、IMPL 报告**;需要访问 101 的角色自己去读那个文件。

其余:连不上外部环境的按上表「连续 3 次」;其他机械动作失败(命令报错、文件缺失等)不重试超过 1 次;不降标准放行;**不自行清理、不自行回滚、不执行破坏性
git / svn 命令**——只能把带路径作用域的命令交用户执行。**崩了的代价只是重跑一遍**,
不要为"精确续跑"发明恢复机制。

**页面层的先后**:Tester 跑 101 页面之前,主 Agent 先对 Executor 交付过完 2.3(自检字段 + 静态审查闸门),
再按计划上传规则**亲自上传**(比对 md5 → 覆盖 → 恢复属主权限 → 记新 md5),然后才让 Tester 跑。
内置浏览器和主会话共用一个面板和登录态:**同一时间只让一个角色操作浏览器**,Tester 跑的时候主 Agent 不碰浏览器;
停在登录页就交回 `blocked`,由主 Agent 请用户登录。

**铁律**:期望值**只来自设计原文**,每条断言注释标"依据 `引文写法`"(如 `01 §7.2`、`PL-01 §五`);
🚫 **严禁读 Executor 的实现逻辑反推期望**(那正是"代码错→断言跟着错→一起绿"的机制;
为了定位页面元素可以看 HTML 结构,但期望值不许从 JS 逻辑里抄);
**只走正式入口**;对"设计要求应被消除的旧行为"写**反向哨兵**
(出现即 fail / 调用数硬 =0,如「离开页面再进来,`RsCore.ajax` 不得被包两层」)。

**两条条件触发的验收判据**(命中才适用,不命中不用做;两条都出自旧项目 W1 外审真实 blocker,
内建三层审查全部漏过、靠目标机实测才暴露——它们的共同点是**验收只在理想态跑过**):

1. **宿主非干净态**:子任务的动作会在目标环境上**创建 / 占用命名资源或留下状态**的
   (101 上的文件、库里的同名记录、页面全局对象上的包裹或事件绑定、DOM id…),验收必须含
   **「目标已存在同名 / 残留状态」**分支用例,期望行为按基线原文——例如离开页面再进入不重复初始化(PL-01 S-11)、
   上一轮测试留下的 `PL01测试-` 残留名单、同一文件重复上传。基线没写该分支期望的,交主 Agent,不许自行择一。
   ⚠️ 计划明确排除在范围外的分歧不算(如 PL-01 F-6 ③ 名单可重名:计划写明「三处分歧不是本计划的范围」),
   照它写「应被拒绝」的用例只会造出假 blocker。
   只在干净状态下验收 = 该入口最现实的形状没被验收。(旧项目事故:W1 B2,
   安装入口对同名已有服务直接 stop/uninstall,而计划要求先判 BLOCKED。)
2. **可滚动载体禁单调计数**:验收判据要从**会滚动 / 轮转 / 截断的载体**(日志文件、
   按日切分的文件或表…)读"事件是否发生"的,🚫 禁用总数 / 单调计数,必须**执行前保存记录
   身份集合、执行后只认集合差里的新记录**,或实证跨一次滚动边界仍成立。(旧项目事故:W1 B3,
   日志跨午夜日切让活动日志 45→1,旧计数法把成功启动误判为超时。)

   ⚠️ 防过度审查:第 2 条升 blocker 需三条件同时成立——设计确实要求观察本次新事件、
   滚动在现有配置与目标环境中**现实发生**、误判直接阻断本计划;只是猜测"未来可能滚动"
   的,记 suggestion,不扩 blocker。
   (自包含执行版复写在 `references/prompt-tester.md` 任务清单第 2 条后——改本节必须同步那边,反之亦然。)

#### 2.3 处理返回

**先看 `self_check` 字段**(两个角色都必填,没填就是没做完 —— 发回去补,不要自己替它跑):

| 看什么 | 不合格怎么办 |
|---|---|
| **两边的 `self_check.reread`**(自检)填了吗?五句是不是**具体回答**? | 只写"已检查/没问题"这类空话 = 没做 → **发回真读一遍**。⚠️ 这项最容易被糊弄,也最容易被主 Agent 放过 |
| **`reread.found_and_fixed` 长期为空** | 单次为空正常;**连续几个子任务都为空**,基本说明没真读——下次派发时把这句话挑明 |
| Executor:每个改动的 JS 过了 `node --check` 吗?自己的自测脚本绿吗?改了公共文件的话,列出其他页面的调用点了吗? | 任一项红或缺失 → **发回同一实例修**,不进内审。带着语法错误去内审是浪费一整轮 |
| Executor(返工轮):`regression_check` 每条有 `how_verified` 吗? | 只写"已修改"没写怎么验证的 → 发回补验证 |
| Tester:用例真跑了吗?有没有没执行到的用例(浏览器用例被登录页挡住、脚本中途退出)? | 没真跑 → 发回跑(登录问题先请用户登录) |
| Tester:`red_tests` 里判 `impl_violates_design` 的 | ⚠️ **这不是 Tester 的失败,是重要产出** —— 逐条核实基线原句,成立的**直接进内审的重点输入**,别当成"测试没写好" |
| Tester:判 `unsure` 的 | 主 Agent 依基线原文拍板,判不了的交用户 |

> 🛑 **`self_check` 里写了假的比不写更糟**。抽查方式:它声称跑过的命令,主 Agent 挑一条自己重跑,
> 对不上就是编造 —— 按兜底总则停下报告。

然后:

- `reject_directive` 非空 → 按设计原文裁决:原文站得住就承认自己错了、修正指令重派;
  认为不冲突要**逐字引原文**反驳再重派。**不许无依据改写指令把拒绝架空。**
- `blocked_questions` 非空 → 能依据原文自己拍板的直接答复;**涉及改设计/改口径的交用户**。
- 都空、`self_check` 全绿(或红项已被判为 `impl_violates_design` 并登记)→ 过下面的静态审查闸门。

🛑 **静态审查闸门 —— Executor/Tester 每次交付(首轮和每次返工)都要过,过了才许进 2.4**:

主 Agent 必须对 Executor/Tester 写的代码和测试进行静态审查 **diff 逐行读一遍**
(SOC 源码:有对照基准的文件用 `diff <对照基准> <当前文件>`(取法见 2.4),其余用 `svn diff`,新文件逐个打开;本仓库用 `git diff`)
- 检查是否有低级错误？是否符合要求？是否存在逻辑矛盾？已知问题是否已解决？是否引入新问题？是否改了一处漏了别处？是否有其他问题？
- 返工循环：谁的问题，就派谁返工，直到静态审查通过为止（静态审查1 -> 发现问题1 -> 返工1 -> 静态审查N -> 发现问题N -> 返工N -> 静态审查通过）
(**这是全 skill 唯一一份静态审查检查单**,权力清单第 5 条和 2.4 返工段都指到这里,不另抄一份。)

- **留痕才算做过**:每次交付单独追加一段 `## 追加(…):TK-n 静态审查 第 k 次`,写审了哪些文件/diff、发现 N 条、逐条怎么处置;
  **N = 0 也要写审查范围**——只写「静态审查通过」= 没做(判 `self_check` 空话的同一条标准)。
- **分级处置**(防"少报好过闸"):blocker/important 级 → **发回同一实例修**
  (主 Agent 无权自己改,见权力清单;处置方式同上表对语法错的"发回同一实例修",
  带主 Agent 自己的发现清单,**不走 2.4 的「返工怎么派」**——那条走的是 Reviewer 核准清单),
  交回后**再过一遍本闸门**;suggestion 级观察 → 允许记「转内审判断」并**计为已处置**
- **同一次交付累计 2 轮**发回仍过不了 → 交用户拍板(计数按交付重置,与内审 2 轮上限互相独立)。
- 🛑 **不许带着已知未处置的 blocker/important 启动内审**——把问题推给 Reviewer 兜底, 等于用最贵的资源清最便宜的错。

🛑 **处理完返回、写完裁决记录之后,主 Agent 必须进行一次自检和验证（详见 S3）** —— 裁决记录和核准清单也是"自己刚写的东西",同样会前后打架。

#### 2.4 内审(每子任务最多 2 轮,每轮开新实例)

🛑 **内审前, 主 Agent 必须进行一次自检和验证（详见 S3）**, 自检和机械前置都要做，不允许二选一。

🛑 **派内审前的机械前置——全满足才许派;判据是留痕实物与命令输出,不是"主 Agent 觉得没问题"**:

1. 2.3 静态审查闸门的**留痕存在且格式完整**:受审文件清单 + 逐条发现与处置 +
   「人工必查项」逐条打钩(清单见下面「检查器随 finding 生长」;还没有登记项时写「人工必查项: 无」)+
   本段末行**逐字** `静态审查未处置: 0`——格式固定,检查器可 grep;**缺任一节 = 没做**;
2. **在册机械检查器全套 PASS**,留痕贴命令原始输出。「在册」= 仓库实物
   (`check_current_status.py`、`gen-index.py`,适用时)+ 本 loop 已建的检查器
   (核对与重建义务在**阶段 1 第 5 步**,不在这里现补)。
   🛑 **检查器不存在 ⇒ 本条前置不成立,不许派内审**——回阶段 1 第 5 步建出能红的检查器再派;
3. 检查器跑完之后**没有再编辑过任何留痕文件**(机械判法:留痕文件 mtime 早于检查器
   本次运行时刻)——写完必须重跑(实证:立完「样本行要加标记」的约定不到一分钟,
   主 Agent 写下一段就自己违反了;靠"记住"不行,只有"写完即跑"行)。
4. 主 Agent 必须做一次全面自检（S3 自检+验证）

> 前三条是"自检找不出问题"的**机械等价物**(第 4 条是 S3 本身,两样都要)。历史上主 Agent 每次委派前都"觉得没问题",
> 而旧项目 T0 五轮 / T1 三轮 / T3 两轮到限的 blocker 几乎全落在它自己的留痕层;
> "再仔细自检一遍"被用户批评 5 次仍复发,只有检查器 0 FAIL 是能红、能核的判据。

🛑 **派活前先过 S3 的「派活前自检清单」七条,勾选结果写进派活那一段。**
⚠️ 这里最容易犯的错是**把自己写的东西直接扔进 ACTUAL 交审、自己一遍没读**——
交审归交审(那是审自我偏袒),自检归自检(那是清低级错误),**两道都要走**。

prompt 完整 Read [references/prompt-internal-review.md](references/prompt-internal-review.md)。
必带:该子任务条目、基线文档路径清单、**该子任务全部新增/改动的代码 + 自测 + 验收产物与运行结果**、
**范围外清单**(见下)、**条款覆盖表**、**本子任务相关的裁决记录**、**本子任务的 101 上传记录**(文件、上传前后 md5)、
**Executor 与 Tester 返回的 `self_check` 原文**、编码红线、**计划允许写库的范围**(Reviewer 复跑页面用例时用)、
**范围外 ①②③ 判定用的 `start-md5.txt`、通过快照、拉取基线路径**(Reviewer 复算用)、**要接入的现有文件与 `101-ref/` 路径**(查调用点用)。

**ACTUAL 与范围外清单怎么派生(两者都必须机械可复算,不许手工挑选;本仓库和 SOC 源码两边分别算)**:

| | 内容 | 怎么来 |
|---|---|---|
| **ACTUAL** | 本子任务的产物 | 当前 `git status --short -uall`(本仓库)与 `svn status`(SOC 源码)**分别减去**范围外清单;再加 Tester 验收目录里的产物 |
| **范围外清单** | 不归本子任务、但确实在工作区里的改动 | ① 阶段 1 第 3 步**开工现场快照**里的文件中,当前内容仍与开工时一致(md5 与 `start-md5.txt` 相同)的(两边;开工后又被改过的就不再是 ①) ② 前面已内审 PASS 的子任务的文件中,**当前内容仍与它最近一次通过快照一致**(`diff` 无差异)的(每个 TK 内审 PASS 时把它改过的文件存一份到 `<scratchpad>/PL-NN/pass-snapshot/TK-n/`) ③ 从 101 拉下来、当前内容仍与拉取基线一致(`diff` 无差异)的文件(开工步骤拉的,如 PL-01 TK-0 的 4 个文件),拉取本身不算任何 TK 的产物;被本 TK 改过的就不再是 ③,进 ACTUAL |

⚠️ 文件级清单管"哪些文件归谁",**行级**靠对照基准:给 Reviewer 的差异是 `diff <对照基准> <当前文件>`,对照基准取**最近的一份**——
该文件的通过快照和拉取基线里**较新**的那份(中途因同事改动重拉过的,新拉取基线比之前的通过快照新);两样都没有的才用 `svn diff`(有拉取基线时不用 `svn diff`,它混着同事的改动)。

⚠️ **这两份清单必须一起给 Reviewer**,让它能独立复算 `工作区 = ACTUAL ∪ 范围外`
(Tester 验收目录在 scratchpad,不在两边工作区里,这部分产物单列,不进这条等式)。
只给 ACTUAL 会让 Reviewer 把前一个子任务的文件报成 blocker——
**本 loop 全程只在收尾 commit 本仓库一次、SOC 源码不提交,前面子任务的产物必然一直躺在工作区里**;
再加上工作区还可能有用户自己的并行改动。
旧项目上一代把「ACTUAL 必须等于完整工作区」写成不可豁免的硬规则,结果**每个子任务都被稳定制造出
一条假 blocker**,I1 的 T3 正是这样跑到轮次上限的。
> 这是两条各自正确的规则(「当前版本必须被审」vs「允许并行改动」)撞在一起,
> 靠执行者"更认真"消除不掉,只能在规则层裁掉——即上面这张表。
> 「当前版本必须被审」由 prompt 里"核对 ACTUAL 每个文件当前内容与你读到的一致"继续保证,强度不降。
> ⚠️ 同一个文件被多个 TK 先后改(如 `list.js` 在 TK-3 重写、TK-5 再加弹窗和按钮规则)时,它在后一个 TK 里和通过快照有差异,
> 于是**不再属于 ②、重新进 ACTUAL**,Reviewer 审的是 `diff <TK-3 通过快照> <当前文件>`;前一个 TK 的内审结论不覆盖新改动。

**必屏蔽**:主 Agent 拆这个子任务时的**叙事**(为什么这样拆、心里想解决什么)——
让 Reviewer 从零判断,不被主 Agent 的心智模型锚住。**屏蔽的是叙事,不是设计原文**,原文必须给足。

**主 Agent 核准**(不外包):**先看 Reviewer 自己的 `self_check`**(它有没有核对过自己报告里的
坐标与引文;空着或只写"已检查"= 没做,发回补)→ 按「向用户汇报的纪律」贴原始结论 →
逐条 Read/grep 核实真伪 → 定级 → 决定 kept/降级/删除/升级。**降级或删除必须贴出设计原句**。

🛑 **检查器必须跟着 finding 生长**(机械前置第 2 条的维护规则,触发点就在核准这一步):
内审或用户抓到一条**现有检查器射程之外**的 finding 时,当轮做**逃逸通道诊断**
(「我现有的检查器为什么没抓到它」):能机械化的**补断言 + 反向变异自证能红**;
不能机械化的(如裁决论证完整性)**以追加段 `## 追加(…):人工必查项` 登记**
(只往后追加,不回改前面的段),此后每次静态审查留痕都要对它逐条打钩(消费点 = 机械前置第 1 条,
登记而无人消费 = 白写)。旧项目实证:T1 五条 blocker 全部落在射程外、无一条是检查器判错——
盲区来自"被检查内容长大了,检查器没跟上",解法是按失效模式补断言,**不是加大自检力度**。

- 0 blocker + 0 important → PASS,存本 TK 的通过快照(见上表 ②),进下一子任务
- 否则派 Executor(实现类)或 Tester(测试类)**分别**返工,再开一轮全新内审
  (返工改了 SOC 源码的,重新上传 101 后再让 Tester 复跑页面用例)
- **第 2 轮仍不过 → 交用户拍板**(升档再来一轮 / 拆细子任务、改计划 / 用户直接给指令 / 中止)

**返工怎么派**(整体审整改也照这条走):
- **重新完整 Read** 对应的 `prompt-executor.md` / `prompt-tester.md`,填它的**返工轮**块
- **必带核准清单,不是 Reviewer 的原始报告** —— 主 Agent 可能降级或删过条目,
  给原始报告等于让返工者去改一堆已被判掉的东西
- 同时给设计原文与相关文件的当前内容
- **返工者不再判问题真伪,但核准清单要求它写偏离设计的东西时,它仍然可以拒绝**

🛑 **返工也是派活**:派发前过两件——S3 的「派活前自检清单」七条 + 下面「整改纪律」的第 4 条
(改完自检),核对这次核准清单/裁决记录有没有跟之前几轮写的东西打架,再派出去。

🛑 **返工交回后照过 2.3 的「静态审查闸门」**(闸门管的就是"每次交付",返工轮不豁免),
过了、且 2.4 开头的机械前置四条重新满足,才许开下一轮内审。

> ⚠️ 首轮就 0/0 则正常 PASS,不必凑轮次。但**不许因为"看着改不动了"提前收**。

每轮内审核准后**当回合**追加一段 Task 段(标题按 `update-changelog` 的追加格式写 `## 追加(YYYY-MM-DD HH:mm TZ):Task TK-n 内审第 k 轮`):Executor/Tester 摘要、上传记录(文件 + 前后 md5)、Reviewer verdict + 原始计数、
核准后计数、核准差异、返工摘要、结论,外加一行
`- 经验候选: <一句话跨任务可复用的教训 | 无>`(格式逐字固定,收尾时用 grep 机械取回;写「无」合法)。

### 阶段 3 — 整体审(**只 1 轮**)

#### 3.1 主 Agent 基线实跑(亲自做)

跑**计划完成判据和验收用例要求的全部检查**(计划里有「全量验收」TK 的,就是那个 TK,如 PL-01 TK-6 = §七 全部用例):
- 全部 node 脚本(Executor 自测 + Tester 验收)重跑;
- 每个改动的 JS `node --check`;改了 PHP 的按「编码红线」里的方法跑 `php -l`;
- 101 上每个上传文件的 md5 与本地工作副本一致(防止上传后又被别人改、或本地改了没传);
- 101 浏览器全量用例从头跑一遍(含回归和「离开页面再回来」这类非干净态用例);
- 计划要求的只读查库核对;
- 文档类判据的 grep / 检查脚本、`gen-index.py`、`check_current_status.py`(适用时)。

记录:每条命令原文和输出、用例通过数 / 总数、md5 清单、浏览器用例逐条结果。
**实跑红也如实记录交 Reviewer 判**,不得因为红就不给看。

🛑 **只跑 node 脚本不等于页面验过**——凡计划的验收落在 101 页面或真库上的,**必须有浏览器实测那一跑**,
否则就是"全绿但计划要验的根本没验":脚本全过、自检全绿、IMPL 每个数字都有出处,一个字没造假,
可是计划要证明的事一次都没执行。
> 这不是假想:旧项目一个门的外审 5 个真 blocker 里就有一条「只跑了默认测试、环境层测试被旁路」,同类问题咬过一次。

所以本步的检查清单**从计划的完成判据和验收用例推导**,不是照抄一条默认命令。

#### 3.2 派整体审 Reviewer

🛑 **派 Reviewer 前，主 Agent 必须进行一次自检和验证（详见 S3）**

🛑 **派活前先过 S3 的「派活前自检清单」七条,勾选结果写进派活那一段。**

prompt 完整 Read [references/prompt-overall-review.md](references/prompt-overall-review.md)。
必带:**计划路径**、全部子任务清单与各自产物(含上传到 101 的文件)、**条款覆盖表(全表)**、**本计划全部裁决记录**、
主 Agent 基线实跑的命令与输出(3.1 那份)、基线文档路径清单、**计划允许写库的范围**、**要接入的现有文件与 `101-ref/` 路径**、
**每个 SOC 源码改动文件的对照基准路径**(取法同 2.4;只是从 101 拉下来、本计划没改过的文件注明「未改」)。

**只审内审看不到的那一层**,即**跨子任务的衔接**:

1. **衔接契约**:某子任务提供的模块接口 / 全局函数 / 配置项 / 接口地址与参数,在其他子任务的调用点上契约一致吗?(列清单、grep 调用点)
2. **跨子任务口径**:同一条计划要求分散在多个子任务实现时,口径一致吗?
   横切关注点(`RsCore.ajax` 返回格式与回调约定、mock 开关和拦截范围、黑白名单共用配置、
   样式作用域、公共文件改动对其他页面的影响、接口名和字段名与计划约定一致)在所有落点上一致吗?
3. **整体对账**:拿设计原文对条款覆盖表**逐条回原文核实实际行为**
   ——用例绿了不等于行为符合设计。
   每条判定只有**完整兑现 / 未兑现**两态;"部分兑现 + 挂追踪清单 / 留后门 / 说留给下一步" = **未兑现**。
   条款覆盖表标了「按待确认项默认不做」的(如 Q8),照标注判,不算未兑现。

🚫 **明令不审**:单文件代码质量、单子任务合规、编码红线扫描(这三样内审已经审过,
它是唯一防线也是够用的防线);**账本格式、状态页数字、时间戳格式、引文标点**
(旧项目上一代在这上面烧掉了整整 3 轮,零代码收益)。

#### 3.3 核准与整改

同 2.4 的核准纪律——**先看整体审 Reviewer 自己的 `self_check`**(坐标与引文核对过没有、
有没有越界审明令不审的那几样;空着或只写"已检查"= 没做,发回补),再逐条核实真伪;
派发前先过「整改纪律」第 4 条的改完自检 + S3 的「派活前自检清单」七条。
有 blocker/important → 按归属派 Executor/Tester 整改
(**派法照 2.4 的「返工怎么派」**:重新 Read 模板、必带核准清单而非原始报告、返工者保留拒绝权)→
**整改产出的新代码必须回 2.4 过一轮全新内审**(单文件质量只有内审看得见)。

**这一轮内审的结果决定下一步**(不能不管判什么都往下走——整改是缺陷的主要来源,
而整体审不再开第 2 轮,这轮内审就是这批新代码交给外审前的最后一次审查):

- 核准 **0 blocker + 0 important** → 进阶段 4
- 非 0/0 → 按 2.4 的分支走(最多再返工一轮),**第 2 轮仍不过 → 交用户拍板**

> **整体审不再开第 2 轮。**整改后的跨子任务问题由独立外审兜底——
> 旧项目数据显示外审是唯一稳定抓到真代码缺陷的层,而整体审第 2 轮以后基本只在审自己。
> ⚠️ **本项目的外审是可选的**(没有 `review-impl`,只在收尾提醒)。用户不做外审时,整改后的跨子任务问题就没人兜底——
> 交用户拍板和收尾汇报时要把这一点说明白。

🛑 **整改完成后，主 Agent 必须进行一次自检和验证（详见 S3）**

**当回合**追加 changelog `## 追加(YYYY-MM-DD HH:mm TZ):整体审` 段:Reviewer 原始结论与计数、核准差异(降级的贴原句)、
整改摘要与整改后内审结果,外加一行 `- 经验候选: <一句话 | 无>`(格式同 Task 段)。

### 阶段 4 — 收尾

1. **重跑实跑**(整改过就必须重跑,不得拿旧结果配新代码;改了 SOC 源码的要先重新上传)。
2. **自检**——**把本 loop 自己写的东西 diff 出来重读一遍**
   (IMPL 报告、changelog、条款覆盖表、自己写的工具脚本;**不含 Executor/Tester 的代码,那不归你改**):

| # | 重读时问自己 |
|---|---|
| 1 | 报告里的**结论和证据对得上吗**?有没有哪句话是"听起来对但没依据"的? |
| 2 | 这个 loop 里做的**取舍和降级,都写进去了吗**?有没有对用户不利的事被略过了? |
| 3 | 自己写的工具脚本,**逻辑真对吗**?(旧项目实测主 Agent 写的脚本出过字段语义写错的 blocker) |
| 4 | 改过的地方,**同类的都改了吗**?(尤其数字——行数、计数、md5 最容易只改一处) |

3. **验证**——**先跑命令,贴输出,再写结论**
   (顺序不可倒置:旧项目实测编造留痕值——假时间戳、假 hash——全发生在"先写字后跑命令"时):

| # | 自检项 | 怎么跑 |
|---|---|---|
| 1 | **计划要求的检查全跑了**且全绿 | 逐条列出完成判据 / 验收用例要求的检查 + 各自结果与计数。**验收落在 101 页面的,必须有浏览器实测那一跑**,只有 node 脚本的直接判不过 |
| 2 | 每个 TK 的完成判据都已兑现 | 逐条列出 + 指到具体代码 / 文档 / 用例 + **该用例在第 1 项实跑里的执行记录**(指到一个从没跑过的用例不算兑现) |
| 3 | 条款覆盖表无遗漏 | 逐条核实实际行为,不是"有人认领"就算 |
| 4 | 改动集合就是预期集合 | 本仓库 `git status --short -uall`、SOC 源码 `svn status` 各自减去**开工现场快照**,剩下的应当**正好**是本计划各子任务的产物(加计划开工步骤拉下来的文件);101 上传清单与计划改动范围一致。多出来的就是没人认领的改动,要查清 |
| 5 | 报告里每个数字都有出处 | 每个计数 / md5 附产生它的命令 |
| 6 | 本轮改过的东西没有自相矛盾 | 只在本阶段做过整改时跑:改过的术语/字段/判据,grep 全文看别处是否同步、新旧写法有没有并存 |

🛑 **闸门(S3 第 ③ 个时刻): 主 Agent 必须进行一次自检和验证（详见 S3）,才能进第 4 步。**
任一项红 → 二选一,**没有第三个选项**:

- (a) 能当场修的 → 修掉,**重跑该项**(以及被它影响的其他项),全绿再往下;
- (b) 修不掉的 → **本计划结论从 PASS 改成 FAIL**,走下面的 FAIL 路径。

**不许带着红项继续走 PASS 收尾,也不许"红项写进边界声明"糊弄过去**——
自检表存在的全部意义就是它能拦住东西。

4. **经验沉淀**:先跑 `grep -n "^- 经验候选:" changelog/<本 loop 的 changelog>.md` 并**把输出原样贴出来**
   (收尾那一刻回忆整个 loop,早期教训已经随上下文流失了,这就是每轮记一行的理由)。
   每个 Task 段和整体审段恰好一行:`grep -cE '^## 追加.*:(Task|整体审)'` 的结果应等于经验候选行数(静态审查段、亲做型 TK 的记录段、
   条款覆盖表修订段不带这一行);对不上说明某段漏填,在文末追加补记。
   以非「无」的行为候选,至少写一条 insight,**走 `update-insights` skill**(与 memory 双向同步、重跑生成器)。
5. **落证据**:计划写了留证要求的照计划(如 PL-01 TK-6「截图留证」);计划没写放哪的,放
   `implement/PL-NN/`(脚本输出、md5 清单、浏览器用例的文本结果、只读查库结果)。
   **第一次创建 `implement/` 目录时,同回合在 `CLAUDE.md` 目录表登记它**(目录表只登记真实存在的目录)。
   - **所有数字直接取自第 1 步实跑的输出**,不得另算(这是 S3 的「验证」)
   - 内置浏览器的截图只回到对话、**不落盘**:证据形式按阶段 1 第 1 步开工时用户的答复执行;
     用户同意用文本替代的,落 `get_page_text` / `read_page` 文本结果,报告里写清「截图见对话」,不许声称有截图文件
   - Tester / Executor 放在 scratchpad 的脚本,收尾时**复制一份进 `implement/PL-NN/`**(scratchpad 会话结束就没了,外审要能重跑);
     **计划写了脚本不入库的照计划不复制**(如 PL-01 TK-2「scratchpad，不入库」),在 IMPL 报告里写明没保留、外审要重写
6. **写 IMPL 报告** `implement/IMPL-YYYYMMDD-HHmm-<PL-NN>.md`
   (时间戳取创建时刻 `date +%Y%m%d-%H%M`,系统时区,
   见 `CLAUDE.md`「时间戳命名规则」),主 Agent **亲写**,模板见 [references/report-template.md](references/report-template.md)。
   **所有数字必须附产生它的命令**(这是 S3 的「验证」;旧项目实测编造留痕值发生过三次,全是先写字后跑命令)。
   (`implement/` 的登记见第 5 步。)
7. **changelog 追加 `## 追加(…):Final PASS`**(走 `update-changelog` skill,重跑生成器);
   `update-current-status` 把结果写进「阶段与文档状态」、移除「当前进行中」的 loop 项。
   > 状态页在 loop 期间的写法(按 `CLAUDE.md`「CurrentStatus 与 changelog 更新规则」):每推进一个 TK 或一轮审查,
   > 只在「当前进行中」**覆盖同一个恢复点**(当前 TK、第几轮、下一步、本 loop changelog 链接、`<scratchpad>/PL-NN/` 绝对路径),**不写过程数字**;
   > 其他各节只在收尾这里更新一次。旧项目教训:每轮同步状态页数字,整体审 6 条 important 有 3 条是状态页对账,纯自造工作量。
   > 处在 git worktree 并行工作区时一律不写状态页,进展只写 changelog(见 `CLAUDE.md`)。
8. **计划状态**:计划文件是只读基线,主 Agent 无权自己改「已完成」之类的标记。
   把"建议把 PL-NN 的状态改成已完成"连同证据一起**报给用户,由用户决定**。
9. 本仓库 `git diff --stat` 后**询问用户是否 commit**,同意才 commit;带 `--push` 且 commit 成功才 push。
   SOC 源码只报 `svn status` 清单,**不提交**(要提交时用户另行指令,走 `svn-commit` skill)。
10. 提醒用户:**独立外审还没做**(本项目还没有 `review-impl` skill;可另派一个不参与本 loop 的 Reviewer,
    报告按 `CLAUDE.md` 命名为 `review/RV-impl-YYYYMMDD-HHmm-<PL-NN>.md`)。

**FAIL 路径**(内审到限用户确认未完成 / 整体审后用户叫停 / 自检闸门 (b)):
照样落 IMPL 报告(结论写"未完成",列清残留 + 最后一次实跑结果 + 建议人工介入点),
changelog 追加 `## 追加(…):Final FAIL`,`update-current-status` 写入阻塞项,**不 commit**。

> **FAIL 也要自检再交**(S3 第 ③ 个时刻同样管这条路径,只是查的东西不同):
> ① 残留清单是**当场跑命令列出来的**,不是凭印象写的;② 最后一次实跑结果是真的、贴了输出;
> ③ 报告里每个数字都有出处。**报"没做完"同样不许编造细节**——
> 用户要靠这份清单决定下一步怎么接。

**中止路径**(用户选择暂停 / 用户批准改基线文档):changelog 追加 `## 追加(…):Final ABORTED` + 原因,
附本仓库 `git status --short -uall`、SOC 源码 `svn status`、101 已上传文件清单的快照,并标注"产物可能是半成品",
**不主动回滚(本地和 101 都不回滚)、不落 IMPL**。101 上要不要用开工备份还原,交用户决定。
改基线的,改完计划后开新 loop。

> **中止也要自检再交**:快照必须是**当场跑的**(不是复用开工时那份),
> 中止原因如实写。半成品状态写错会让用户按错误现场去决定清理还是接着干。

## 向用户汇报的纪律

主 Agent 是唯一汇报通道——所有防线都能**发现**问题,但信号全要经它转述。所以:

1. **每个角色返回后,把原始结论原样贴进对话**(不是只写 changelog):
   角色 + 档位 + verdict + **blocker / important / suggestion 三级的标题清单(原文照抄,不改写不合并)**。
   > ⚠️ **suggestion 也要贴**。Reviewer 常把"这个公共弹窗进程管理页也在用,建议回归一下"
   > 这类真线索定成 suggestion,只贴 blocker 会让它彻底静默。
2. **核准差异要写清**:降级/删除了哪几条、依据哪段原文——
   **必须把原句那 1~3 行直接贴出来,不许只给「§8.8 第 14 条」这种坐标**。
   用户判断的对象是原句;只给坐标等于让用户自己去翻几百 KB。
3. **派发前后各一行**:派谁 / 什么档位 / 它的锚点是什么 /
   **「派活前自检清单」七条的勾选结果** → 返回后 verdict 是什么。
   > 目的:**该派而没派会立刻显形**(用户看到某个子任务没有内审记录);
   > 勾选结果**摆到用户眼前**才不会退化成"已自检"三个字——
   > **只写"已自检"等于没做**,这条对主 Agent 和对下游角色是同一个标准。
4. **每次交用户拍板前**(不只是收尾——内审到限、整体审整改后、兜底总则停下来问,都算),
   先花一分钟核实**要交上去的材料本身是不是真的**:轮次与计数是从 changelog/命令里取的吗?
   残留清单是当场列的吗?给用户的几个选项有没有漏掉一个真实存在的出路?
   > 用户是照着你给的材料做决定的。**材料错了,用户的决定必然错**,
   > 而这种错比代码 bug 更难被后面任何一层发现(下游只会看到"用户已裁决")。
5. **收尾前**当面回答三个问题,答完才能收尾(都答"无"时也要明说"无"):
   - 有没有任何角色报过设计冲突?怎么处置的?
   - 有没有任何 finding 被降级或删除?依据的原文分别是哪一段?
   - 有没有哪一步是我自己判断"可以不做"的?

## 整改纪律(每一次返工、每一次核准与裁决都适用)

**整改本身就是缺陷的主要来源**(旧项目实测某轮 7 条 finding 里 4 条是前两轮整改自己造的)。
⚠️ **"整改"不只是派 Executor/Tester 改代码——主 Agent 自己写核准清单、裁决记录、
范围外清单、changelog 条目,同样是在"改东西",同样会造出前后矛盾。**动手前过三条:

1. **回扫同类**:Reviewer 点名的是**样本,不是全集**。改"某类条目的某字段"时,
   把该字段的**全部条目**列出来逐一看。
2. **跑全链**:改了生成链上游就把整条链重跑,别只跑改动那一步——
   否则下游读的还是旧数据,**整改静默失效而自检还全绿**(旧项目实测犯过 3 次)。
   本项目里最常见的"链":改了本地文件 → 要重新上传 101 → 要重跑页面用例;改了 changelog → 要重跑 `gen-index.py`。
3. **不可逆动作先问两句**:「这个文件 git / svn 管不管它?」「改错了回得来吗?」
   版本管理之外的文件(`.gitignore` 里的、101 上的)没有版本兜底,覆盖 = 永久销毁,动手前先另存一份
   (101 上按计划的备份步骤)。

**改完之后、派下一轮 Reviewer 或往下走之前,过第 4 条(动手前是上面三条,这条是动手后)**:

4. **改完自检**——就是 S3 定义的那个「自检」:**把自己刚改的 diff 出来重新读一遍**。
   ⚠️ 它**不是**重审代码质量(那是 Reviewer 的活);
   查的是**自己刚写的东西自洽不自洽**。整改场景下重点看这三样:
   - 改了一个术语 / 字段 / 判据的**定义**?→ 读 diff + grep 全文这个词,
     **别处还在用旧定义吗、新旧两处打架吗**
   - 改了 SKILL 正文的某句"必带 XX"?→ 对应 prompt 模板里有没有接得住的占位符
   - 改了一个判据(比如"谁跟谁比")?→ 找一遍其余提到同一比较的地方,是不是都同步改了
   > 旧项目实证:上一次改 ACTUAL 判据时跳过这一步,自己新造了 2 处矛盾
   > (旧注释与新规则打架、返回字段定义没跟上新判据)——**两处跑命令都是绿的**,
   > 只有读 diff 才看得见。

整改完**当轮**把"改了什么、回扫了哪些同类、跑没跑全链、自检有没有过"写进 changelog。
