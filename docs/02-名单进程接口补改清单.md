## 1. `Procmanager/showWBList` — 查询

模型 `getWBListProcs`（12:19 版 `:2028`）已经是：

```php
$sql = "SELECT ID,PROCPATH,FILEHASH,ALGO,STATUS,CREATETIME FROM $procTable WHERE BWID=?";
// ID、STATUS、ALGO 转成整数
```

页面需要的「新增 / 移除」标签、+N / -M、恢复按钮都靠 `STATUS`，这个问题已经解决。还剩：

| # | 内容 | 说明 |
|---|---|---|
| ① | `FILEHASH` 统一小写 | 设计 K14 要求哈希全链路小写。101 库里 65 行有 60 行是大写（第 6 节）。前端显示时会自己转小写，但查重、和终端比对都要靠库里本身就是小写 |
| ② | 控制器注释还写着「返回字段：ID、PROCPATH、FILEHASH、CREATETIME」（`:1303-1306`） | 顺手改成实际返回的 6 个字段 |
| ③ | 可选：返回里带上这条名单的汇总 `info` | 内容就是 `getWBList` 列表里这条名单那一行（字段原样）。页面顶部信息条要显示发布状态、进程数、应用范围；有了它，增删以后重取一次就能刷新信息条。不带也行：前端现在的做法是每次增删后再重取一次 `getWBList`（不带条件），找到这条名单那一行来画信息条，多一次请求 |

## 2. `Procmanager/addProcToWBList` — 添加（11:27、12:19 版都没改）

### 现状的问题

1. **去重只看「路径 + 哈希」、不看状态**（`isExistWBListProc` `:1939`）。撞上一行「待移除」（`STATUS=2`）的，也只提示「该进程已存在。」（code 7）。页面上这行是划了删除线的，正确做法是点它的「恢复」，提示要说清楚。
2. **去重键少了 `ALGO`**：设计 5.4 的规则键是「算法 + 小写哈希 + 路径」。
3. **大小写**：`PROCPATH`、`FILEHASH` 列现在都是 `utf8_general_ci`，不分大小写。`WHERE PROCPATH=?` 会把 `/usr/bin/A` 和 `/usr/bin/a` 当成同一个，但 Linux 路径是区分大小写的。设计 5.8 第 2 条要求 `PROCPATH` 改成 `utf8_bin`。
4. **哈希不转小写、不校验路径格式**。设计 7.3 要求 Linux 路径以 `/` 开头、最后一段不为空。
5. **`algo` 的取值约定没写进接口文档**：传 `algo=1` 存进库是 0（P24 ⑭）。
6. **路径检查太严、长度按字节算**：`checkParams($procPath, 500)` 调 `Common::checkQuotation`（`library/Common.php:1890`），长度用 `strlen` 按字节算（一个汉字 3 字节，200 个汉字的路径就超了）；路径以 `'"=(){}@%&!<>,` 中任一字符结尾；或含（不分大小写）`select` / `insert` / `update` / `delete` 后面跟空格、两边带空格的 `and` / `or` / `join` / `like` / `regexp` / `where` / `union` / `into`、`#`、`'`、`*`、`../`、`./`、`load_file`、`outfile`，都会被拒成 code 100「搜索值包括非法字符」。这套规则是给搜索框防注入用的，进程路径是参数化写库，用不着这么严，正常的 Linux 路径（如 `/opt/Tom and Jerry/run`、以 `)` 结尾的文件名）会被误拒。

### 要改成

入参不变：`pid`、`policytype`、`propath`、`filehash`、`algo`（可省，省了按哈希长度认：32 位 = 0 MD5，64 位 = 8 SHA256）。规则按顺序：

| 步骤 | 规则 | 不通过时 |
|---|---|---|
| ① | `pid`、`policytype` 合法，名单存在 | 沿用现有 code 2 / 3 / 6 |
| ② | `propath` 去首尾空格后：以 `/` 开头、不以 `/` 结尾（最后一段是文件名）、长度不超过 500 **个字符**（`mb_strlen`，不按字节）；不再套用 `checkQuotation` 的搜索框字符规则（SQL 是参数化的）。按名单的 `EPTYPE` 分支写，一期只有 Linux，Windows 二期再补盘符规则，**不要写死** | code 4，msg「进程路径格式不对，Linux 名单请填写以 / 开头的完整路径」 |
| ③ | `filehash` 去首尾空格、**转小写**，必须是 32 位或 64 位十六进制；传了 `algo` 时要和长度对上（0 ↔ 32 位，8 ↔ 64 位） | code 5，msg「文件哈希应为 32 位（MD5）或 64 位（SHA256）十六进制字符」 |
| ④ | 按「`ALGO` + 小写 `FILEHASH` + `PROCPATH`（区分大小写）」在本名单里查重 | 撞上 `STATUS` 0 / 1：code 7，msg「名单里已有路径和哈希都相同的进程，不用重复添加」；撞上 `STATUS` 2：**新增 code 9**，msg「名单里已有路径和哈希都相同的进程，它已被标记移除，点它的「恢复」即可」 |
| ⑤ | 插入一行 `STATUS=1`，重算名单状态（第 5 节） | code 8「添加失败。」 |

出参不变：成功 `data = {ID: 新行 ID}`。

## 3. `Procmanager/delProcFromBW` — 移除（11:27、12:19 版都没改）

### 现状的问题

1. **ACL 没登记**：101 `conf/acl-login.php.conf` 里登记了 `showWBList`、`addProcToWBList`、`resProcFromBW`，**没有 `delProcFromBW`**（10-23 11:3x、12:14 CST 两次只读核实）。`controllers/My.php:36-37` 的规则是没登记的地址一律拒绝，所以页面现在调不通。
2. **没有「至少保留 1 个进程」的校验**：需求原文第 4 条、设计 7.3 都要求有：发布过的名单，不允许把进程删到 0。
3. **不记标记人和时间**：设计 5.8 第 4 条（标「必改」）要求名单进程表 `RPW_WPROC / BPROC` 加唯一键 `(BWID, FILEHASH, ALGO, PROCPATH)` 和 `UPDATEUSER varchar(30)`、`UPDATETIME datetime` 两列，页面「移除」标签悬停要显示「某某 于 某时间 标记移除」；`rpw.sql` 和 101 的表都还没加。

### 要改成

入参、分流规则、出参都不变（`STATUS=1` 直接删行、0 标成 2、已是 2 计入 `SKIPPED`；出参 `{MARKED, DELETED, SKIPPED}`）。

1. **ACL 登记** `Procmanager/delProcFromBW`（角色同其他名单接口），并刷新 ACL 缓存（Redis `hacl_login`）。
2. **新增校验**（在事务里、真正改数据之前）：名单**发布过**时（判断方法同第 5 节的 `isWBListPublished`），算「移除后剩下的有效进程数」= 本名单 `STATUS` 不为 2 的行数 − 这次要删或要标 2 的行数。**小于 1 就整个请求拒绝**，一条都不改，返回**新 code 6**，msg「至少保留 1 个进程；要清掉这条名单请直接删除它」。没发布过的名单可以删光，状态回到 1（空白名单）。
3. **按设计 5.8 第 4 条加唯一键和两列**（`rpw.sql` 和升级脚本一起改）；标记移除时写 `UPDATEUSER`（登录用户名）、`UPDATETIME`，恢复时清空（设计 7.3），`showWBList` 一并返回这两列。不急，前端先不显示，后端做完告诉前端再补。

## 4. `Procmanager/resProcFromBW` — 恢复（12:19 版改成单条）

已实现（控制器 `:1467`，模型 `restoreWBListProc` `:1646`），ACL 已登记。北京 12:19 版把它改成**一次恢复一条**，前端照现状用：

- 入参：`id`（进程行 ID，即 `showWBList` 返回的 `ID`，必填）、`policytype`（2 / 3，必填，决定查哪张表）；不收 `pid`、`ids`；
- 出参：`data = {CODE, MSG, ID, BWID, STATUS, LISTSTATUS}`，`LISTSTATUS` 是名单重算后的发布状态；
- 错误码：1 / 2 参数错误、3 恢复失败、4「进程记录不存在。」、5「该进程不是已删除状态，无需恢复。」；
- 恢复后按这行的 `BWID` 重算状态，没有待发布的改动时，发布过的名单回到「已发布」。

建议补 2 处（都不急）：

1. **校验这一行属于哪条名单**：现在只按 `id` 找行，不带名单 `pid`、也不查这行所属名单是不是进程管控的名单，页面传错 `id` 就会恢复到别的名单上。建议加可选入参 `pid`，传了就校验 `BWID = pid`；
2. 第 3 节第 3 条加了 `UPDATEUSER`、`UPDATETIME` 两列后，恢复时把这两列清空（设计 7.3）。

## 5. `refreshWBListStatus` — 状态重算还剩 1 处

11:27 版（模型 `:835`）新增了 `isWBListPublished()`（`:889`）：把 `POLICYJSON` 里的 `policymaincontent` 用 base64 解开，看里面的 `dpath` 是不是非空。这个判断能区分发布过、没发布过（10-23 只读核对：PID 37 是 `"dpath":"ruc/libs/w/u"`，PID 38、43、60 是 `"dpath":""`）。「加了再移除」「移除再恢复」这两种情况，现在都能正确回到「已发布」了。

还剩的问题出在判断顺序上：

```
没有任何行                    → 1 空白名单
有新增(1) 或 待移除(2)        → 3 有变更      ← 先走到这里，不管发布过没有
已是 4 或 发布过              → 4 已发布
其余                         → 2 待发布
```

结果是：**没发布过、但有新增行的名单都会被算成 3「有变更」**，正确的应该是 2「待发布」（从没发布过，谈不上「变更」）。例如空名单加第一个进程（P24 ⑬）、往 PID 43 再加一个进程（会从 2 变成 3）、从 PID 38 删掉一个新增（剩下的还有新增，仍是 3）。101 上 PID 38、41、42 的 `STATUS=3` 就是这么来的（第 6 节）。

改法：保留 `isWBListPublished` 的判断，**把「没发布过 → 2」挪到「有改动 → 3」前面**：

```php
$blnReleased = ($intStatus == 4) || $this->isWBListPublished(isset($row['POLICYJSON']) ? $row['POLICYJSON'] : '');
if ($intValid <= 0 && $intRemoved <= 0) {
    $intNew = 1;          // 空白名单
} elseif (!$blnReleased) {
    $intNew = 2;          // 没发布过：待发布（这时只可能有新增的行）
} elseif ($intAdd > 0 || $intRemoved > 0) {
    $intNew = 3;          // 发布过、有改动：有变更
} else {
    $intNew = 4;          // 发布过、没改动：已发布
}
```

改完以后，请按新规则把 PID 38、41、42 的 `STATUS` 重算一遍。
